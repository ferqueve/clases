Caso Práctico

Sistema de Reservas de Salas de Estudio Universitarias

Universidad Nacional del Progreso

Situación Actual

La Universidad Nacional del Progreso cuenta con 15 salas de estudio distribuidas en 3 edificios diferentes. Actualmente, los estudiantes deben ir físicamente a cada edificio para verificar la disponibilidad de las salas, lo que genera:

  • Pérdida de tiempo de los estudiantes
  • Conflictos por uso simultáneo de las salas
  • Falta de control sobre el uso de los espacios
  • Imposibilidad de obtener estadísticas de uso
  • Dificultad para planificar mantenimiento

Solución Propuesta

Desarrollar un sistema web de reservas que permita a los estudiantes consultar la disponibilidad de salas en tiempo real, realizar reservas, y a los administradores gestionar el uso de los espacios.

Objetivo: Optimizar el uso de las salas de estudio y mejorar la experiencia de los estudiantes mediante un sistema digital de reservas.

Identificación de Stakeholders

Los stakeholders son todas las personas o grupos que tienen interés en el proyecto. Identifiquemos quiénes son en nuestro caso:

Estudiantes

Rol: Usuarios principales del sistema

Intereses:

  • Reservar salas fácilmente
  • Ver disponibilidad en tiempo real
  • Cancelar reservas si es necesario
  • Sistema intuitivo y rápido

Administradores

Rol: Gestión del sistema y recursos

Intereses:

  • Control total sobre reservas
  • Estadísticas de uso
  • Gestión de salas y horarios
  • Reportes administrativos

Docentes

Rol: Usuarios secundarios

Intereses:

  • Reservar salas para tutorías
  • Prioridad en ciertas reservas
  • Facilidad de uso

Equipo de Mantenimiento

Rol: Mantenimiento de salas

Intereses:

  • Bloquear salas para mantenimiento
  • Programación de limpieza
  • Reportes de problemas

Equipo de Desarrollo

Rol: Construcción del sistema

Intereses:

  • Requerimientos claros
  • Tecnología apropiada
  • Mantenibilidad del código

Autoridades Universitarias

Rol: Patrocinadores del proyecto

Intereses:

  • Optimización de recursos
  • Mejora del servicio estudiantil
  • Retorno de inversión

Requerimientos Funcionales

Los requerimientos funcionales describen las funciones específicas que el sistema debe realizar:

Gestión de Usuarios

RF-01: El sistema debe permitir el registro de usuarios con credenciales universitarias (email institucional).
RF-02: El sistema debe autenticar usuarios mediante usuario y contraseña.
RF-03: El sistema debe diferenciar entre tres tipos de usuarios: Estudiante, Docente y Administrador.

Gestión de Reservas

RF-04: El sistema debe mostrar la disponibilidad de salas en tiempo real.
RF-05: El sistema debe permitir a los usuarios reservar una sala especificando fecha, hora de inicio y hora de fin.
RF-06: El sistema debe permitir cancelar reservas con al menos 2 horas de anticipación.
RF-07: El sistema debe limitar a los estudiantes a un máximo de 2 reservas activas simultáneas.
RF-08: El sistema debe enviar notificaciones por email de confirmación de reserva.
RF-09: El sistema debe enviar recordatorios 30 minutos antes de la reserva.

Gestión de Salas

RF-10: El sistema debe permitir a los administradores agregar, modificar y eliminar salas.
RF-11: El sistema debe permitir bloquear salas por mantenimiento.
RF-12: El sistema debe registrar la capacidad de cada sala.

Reportes y Estadísticas

RF-13: El sistema debe generar reportes de uso de salas por período.
RF-14: El sistema debe mostrar estadísticas de usuarios más activos.
RF-15: El sistema debe permitir exportar reportes en formato PDF y Excel.

Requerimientos No Funcionales

Los requerimientos no funcionales describen las cualidades y restricciones del sistema:

Rendimiento

RNF-01: El sistema debe cargar la interfaz principal en menos de 2 segundos.
RNF-02: El sistema debe soportar al menos 500 usuarios concurrentes.
RNF-03: El tiempo de respuesta para consultas de disponibilidad debe ser menor a 1 segundo.

Seguridad

RNF-04: El sistema debe cifrar las contraseñas usando algoritmos de hash seguros (bcrypt o similar).
RNF-05: El sistema debe implementar protección contra ataques de inyección SQL.
RNF-06: El sistema debe cerrar sesiones automáticamente después de 30 minutos de inactividad.

Usabilidad

RNF-07: El sistema debe ser intuitivo y no requerir capacitación para usuarios finales.
RNF-08: El sistema debe ser responsive y funcionar en dispositivos móviles.
RNF-09: El sistema debe cumplir con estándares de accesibilidad WCAG 2.1.

Disponibilidad

RNF-10: El sistema debe tener una disponibilidad del 99.5% mensual.
RNF-11: El sistema debe realizar respaldos automáticos diarios de la base de datos.

Escalabilidad

RNF-12: El sistema debe poder escalar para soportar hasta 10,000 usuarios sin degradación significativa.

Mantenibilidad

RNF-13: El código debe estar documentado siguiendo estándares de la industria.
RNF-14: El sistema debe usar arquitectura modular para facilitar actualizaciones.

Legales y Regulatorios

RNF-15: El sistema debe cumplir con leyes de protección de datos personales.
