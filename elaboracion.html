Introducción

Conceptos fundamentales del análisis de requerimientos

¿Qué es el Análisis de Requerimientos?

El análisis de requerimientos es el proceso de determinar las necesidades y condiciones que debe cumplir un nuevo sistema o modificación de un sistema existente. Es fundamental para el éxito de cualquier proyecto de software.

Tres Conceptos Clave:

Business Event

Evento que ocurre en el entorno del negocio y que requiere una respuesta del sistema.

BUC

Describe cómo el negocio responde a un evento específico, sin considerar la tecnología.

PUC

Define cómo el sistema/producto soporta o automatiza el BUC correspondiente.

Flujo de Trabajo

Business Event → BUC → PUC

Primero identificamos el evento, luego definimos la respuesta del negocio, y finalmente especificamos cómo el producto lo implementará.

Business Event

Definición y características

Definición

Un Business Event (Evento de Negocio) es una ocurrencia en el mundo real que sucede fuera del control del sistema pero que requiere que el sistema responda de alguna manera. Es el punto de partida para identificar los requerimientos funcionales.

Características Principales:

  • Externo al sistema: Ocurre en el entorno del negocio, no dentro del sistema
  • Detectable: El sistema debe ser capaz de detectar cuando ocurre
  • Requiere respuesta: El negocio debe responder de alguna forma
  • Atómico: Representa un evento único y completo
  • Significativo: Tiene relevancia para el negocio
Ejemplos de Business Events
  • Cliente realiza un pedido
  • Producto llega al stock mínimo
  • Cliente solicita devolución
  • Empleado solicita vacaciones
  • Llega la fecha de pago de factura
Importante

Los Business Events NO describen lo que hace el sistema, solo identifican qué está pasando en el negocio que requiere atención.

Tipos de Business Events

Clasificación según su naturaleza

Eventos Externos

Iniciados por actores externos al sistema (clientes, proveedores, etc.)

Ejemplos:
  • Cliente hace un pedido
  • Proveedor envía factura
  • Usuario se registra
Eventos Temporales

Ocurren en momentos específicos del tiempo o después de cierto período

Ejemplos:
  • Fin de mes (cierre contable)
  • Vencimiento de póliza
  • Hora de backup programado
Eventos Internos

Disparados por condiciones dentro del sistema o del negocio

Ejemplos:
  • Stock llega al mínimo
  • Temperatura excede límite
  • Capacidad alcanza 90%
Nota Importante

Cada tipo de evento requiere un enfoque diferente para su detección y manejo. Los eventos externos suelen requerir interfaces de usuario, los temporales necesitan programación de tareas, y los internos requieren monitoreo constante de condiciones.

Cómo Elaborar un Business Event

Proceso paso a paso

1
Identificar el Contexto del Negocio

Analizar el dominio del negocio y entender los procesos existentes. Realizar entrevistas con stakeholders y observar las operaciones diarias.

2
Buscar Ocurrencias Significativas

Identificar momentos donde algo sucede que requiere que el negocio responda. Preguntarse: "¿Qué pasa en el negocio que nos obliga a actuar?"

3
Nombrar el Evento Claramente

Usar la estructura: "Actor + Acción + Objeto" o "Condición + Ocurre". El nombre debe ser claro, específico y describir el evento, no la respuesta.

4
Documentar Información Asociada

Registrar: actor que lo dispara, frecuencia, datos involucrados, condiciones previas, y restricciones temporales.

5
Validar con Stakeholders

Confirmar que el evento es real, relevante y completo. Asegurar que todos los interesados estén de acuerdo con la definición.

Ejemplo Práctico

Contexto: Sistema de gestión de biblioteca

Evento Identificado: "Usuario solicita préstamo de libro"

  • Actor: Usuario registrado
  • Tipo: Evento externo
  • Frecuencia: Múltiples veces al día
  • Datos: ID usuario, ID libro, fecha

Business Use Case (BUC)

Definición y características

Definición

Un Business Use Case (Caso de Uso de Negocio) describe cómo el negocio responde a un Business Event específico. Se enfoca en QUÉ hace el negocio, no en CÓMO lo hace el sistema. Es independiente de la tecnología y describe el proceso del negocio.

Características Principales:

  • Orientado al negocio: Describe procesos desde la perspectiva del negocio
  • Independiente de tecnología: No menciona sistemas, pantallas o bases de datos
  • Valor para el negocio: Produce un resultado significativo para el negocio
  • Completo: Describe el proceso de inicio a fin
  • Actor principal: Siempre hay un actor (stakeholder) que inicia o se beneficia
BUC Incluye:
  • Nombre del caso de uso
  • Actores involucrados
  • Descripción narrativa
  • Flujo básico de eventos
  • Flujos alternativos
  • Precondiciones y postcondiciones
Ejemplo

BUC: Procesar Pedido de Cliente

Descripción: El negocio recibe un pedido de un cliente, verifica la disponibilidad de productos, confirma el pedido, y programa la entrega.

Nota: No menciona cómo se hace técnicamente

Componentes de un BUC

Elementos que conforman un Business Use Case

1. Nombre del BUC

Debe ser un verbo + sustantivo que describa claramente el proceso del negocio.

Ejemplos: Procesar Devolución, Gestionar Inventario, Aprobar Préstamo
2. Actores

Personas, organizaciones o sistemas externos que interactúan con el caso de uso.

  • Actor primario: Inicia el BUC o recibe el valor
  • Actores secundarios: Apoyan en el proceso
3. Descripción

Breve resumen (2-4 líneas) de lo que hace el BUC y su propósito para el negocio.

4. Flujo de Eventos

Flujo Básico: Secuencia normal de pasos cuando todo va bien

Flujos Alternativos: Variaciones y excepciones del flujo básico

5. Pre y Postcondiciones

Precondición: Estado que debe existir antes de ejecutar el BUC

Postcondición: Estado resultante después de ejecutar el BUC exitosamente

Importante

Todos estos componentes se describen desde la perspectiva del negocio, sin mencionar detalles técnicos o de implementación del sistema.

Cómo Elaborar un BUC

Proceso paso a paso

1
Partir del Business Event

Cada BUC responde a un Business Event específico. Identificar primero el evento que dispara este caso de uso.

2
Identificar Actores

Determinar quién inicia el proceso (actor primario) y quiénes participan o apoyan (actores secundarios).

3
Nombrar el BUC

Usar formato: Verbo + Sustantivo que capture el objetivo del negocio. Debe ser orientado a resultados.

4
Describir el Flujo Básico

Escribir los pasos secuenciales desde la perspectiva del negocio. Usar lenguaje de negocio, no técnico. Numerar cada paso.

5
Identificar Flujos Alternativos

Documentar excepciones, errores y variaciones. Cada alternativa debe indicar en qué paso del flujo básico se desvía.

6
Definir Pre y Postcondiciones

Establecer el estado inicial requerido y el estado final esperado del negocio.

7
Revisar y Validar

Verificar con stakeholders que el BUC refleja correctamente el proceso del negocio. Asegurar que no incluye detalles técnicos.

Ejemplo Completo de BUC

Caso práctico detallado

BUC: Procesar Pedido de Cliente

Business Event: Cliente realiza un pedido

Actores:

  • Primario: Cliente
  • Secundarios: Vendedor, Almacén

Descripción:

Este caso de uso describe cómo el negocio procesa un pedido desde que el cliente lo solicita hasta que se confirma la entrega.

Precondición:

  • El cliente está registrado en el sistema
  • Existen productos en el catálogo

Flujo Básico:

  1. Cliente selecciona productos del catálogo
  2. Cliente especifica cantidades deseadas
  3. Vendedor verifica disponibilidad en almacén
  4. Vendedor calcula el total del pedido
  5. Cliente confirma el pedido
  6. Vendedor registra el pedido
  7. Almacén prepara los productos para envío
  8. Se notifica al cliente la confirmación y fecha estimada de entrega

Flujos Alternativos:

  • 3a. Si un producto no está disponible, vendedor ofrece alternativas o agenda reposición
  • 5a. Si cliente cancela, se termina el caso de uso
  • 7a. Si hay problemas en almacén, se contacta al cliente para ajustar pedido

Postcondición:

  • El pedido queda registrado en el sistema
  • Los productos están reservados para el cliente
  • Se ha programado la entrega

Product Use Case (PUC)

Definición y características

Definición

Un Product Use Case (Caso de Uso de Producto) describe cómo el sistema/producto de software soporta o automatiza un Business Use Case específico. Se enfoca en CÓMO el sistema implementa la funcionalidad requerida por el negocio.

Características Principales:

  • Orientado al sistema: Describe interacciones con el software
  • Técnicamente específico: Incluye pantallas, validaciones, y procesos del sistema
  • Implementable: Proporciona suficiente detalle para ser programado
  • Derivado del BUC: Se crea basándose en uno o más BUCs
  • Interacción usuario-sistema: Describe el diálogo entre usuario y aplicación
PUC Incluye:
  • Nombre del caso de uso
  • Actores (usuarios del sistema)
  • Flujo de interacción detallado
  • Interfaces de usuario
  • Validaciones y reglas de negocio
  • Mensajes de error
  • Condiciones y restricciones técnicas
Ejemplo

PUC: Registrar Pedido en Sistema

Descripción: El sistema permite al usuario ingresar los datos del pedido, valida la información, verifica disponibilidad en la base de datos, y genera un número de pedido único.

Nota: Menciona detalles técnicos y de implementación

BUC vs PUC

Diferencias fundamentales

Aspecto Business Use Case (BUC) Product Use Case (PUC)
Perspectiva Negocio Sistema/Producto
Enfoque QUÉ hace el negocio CÓMO lo hace el sistema
Audiencia Stakeholders del negocio Desarrolladores y testers
Lenguaje Términos del dominio del negocio Términos técnicos y de interfaz
Detalle Alto nivel, abstracto Detallado, específico
Tecnología Independiente de tecnología Especifica implementación técnica
Actores Roles de negocio Usuarios del sistema
Cambios Más estable en el tiempo Puede cambiar con la tecnología
Ejemplo BUC

Paso 3: "Vendedor verifica disponibilidad de productos"

Describe la acción del negocio

Ejemplo PUC

Paso 3: "Sistema consulta tabla INVENTARIO, verifica campo CANTIDAD_DISPONIBLE > CANTIDAD_SOLICITADA, y muestra mensaje 'Disponible' en pantalla"

Describe la implementación técnica

Cómo Elaborar un PUC

Proceso paso a paso

1
Partir del BUC Correspondiente

Identificar el BUC que este PUC va a automatizar o soportar. Un BUC puede generar uno o más PUCs.

2
Definir Actores del Sistema

Identificar los usuarios que interactuarán con el sistema (no roles de negocio, sino usuarios del software).

3
Nombrar el PUC

Usar formato similar al BUC pero con enfoque en la funcionalidad del sistema: Verbo + Sustantivo + "en Sistema"

4
Describir el Flujo de Interacción

Detallar paso a paso la interacción entre el usuario y el sistema. Usar formato: "Usuario hace X", "Sistema responde Y".

5
Especificar Interfaces y Pantallas

Describir las pantallas, formularios, botones y elementos de interfaz involucrados. Incluir wireframes si es posible.

6
Definir Validaciones y Reglas

Especificar todas las validaciones de datos, reglas de negocio implementadas en el sistema, y restricciones técnicas.

7
Documentar Flujos Alternativos y Excepciones

Incluir mensajes de error específicos, manejo de excepciones, y comportamiento del sistema ante situaciones anómalas.

8
Especificar Requisitos No Funcionales

Incluir performance esperado, seguridad, usabilidad, y otros requisitos técnicos relevantes.

Ejemplo Completo de PUC

Caso práctico detallado

PUC: Registrar Pedido en Sistema

Deriva del BUC: Procesar Pedido de Cliente

Actores:

  • Primario: Usuario Vendedor
  • Secundario: Sistema de Inventario

Descripción:

El sistema permite al vendedor registrar un nuevo pedido, validando datos y disponibilidad de productos en tiempo real.

Precondición:

  • Usuario autenticado con rol "Vendedor"
  • Cliente existe en base de datos
  • Sistema de inventario disponible

Flujo Básico:

  1. Sistema muestra pantalla "Nuevo Pedido"
  2. Usuario hace clic en botón "Buscar Cliente"
  3. Sistema muestra modal de búsqueda
  4. Usuario ingresa DNI o nombre del cliente
  5. Sistema consulta tabla CLIENTES y muestra resultados
  6. Usuario selecciona cliente de la lista
  7. Sistema carga datos del cliente en formulario
  8. Usuario hace clic en "Agregar Producto"
  9. Sistema muestra catálogo de productos con campo de búsqueda
  10. Usuario selecciona producto e ingresa cantidad
  11. Sistema valida: cantidad > 0 y cantidad ≤ stock disponible
  12. Sistema agrega producto a tabla "Detalle del Pedido" con precio actual
  13. Sistema recalcula subtotal, impuestos y total automáticamente
  14. Usuario repite pasos 8-13 para agregar más productos
  15. Usuario hace clic en "Confirmar Pedido"
  16. Sistema valida: al menos 1 producto agregado
  17. Sistema genera número de pedido único (formato: PED-YYYYMMDD-####)
  18. Sistema inserta registro en tabla PEDIDOS y DETALLE_PEDIDOS
  19. Sistema actualiza campo STOCK_RESERVADO en tabla PRODUCTOS
  20. Sistema muestra mensaje de éxito con número de pedido
  21. Sistema envía email de confirmación al cliente

Flujos Alternativos:

  • 5a. Si no se encuentra cliente: Sistema muestra "Cliente no encontrado" con opción "Registrar Nuevo Cliente"
  • 11a. Si cantidad > stock: Sistema muestra error "Stock insuficiente. Disponible: X unidades" y no agrega el producto
  • 11b. Si cantidad ≤ 0: Sistema muestra error "Cantidad debe ser mayor a 0"
  • 16a. Si no hay productos: Sistema muestra error "Debe agregar al menos un producto"
  • 18a. Si falla grabación en BD: Sistema muestra "Error al guardar pedido" y mantiene datos en pantalla

Validaciones:

  • Todos los campos numéricos aceptan solo dígitos
  • Precio unitario >= 0
  • Total pedido >= monto mínimo configurado ($100)
  • Tiempo de sesión: 30 minutos de inactividad cierra sesión

Postcondición:

  • Pedido registrado en tabla PEDIDOS con estado "CONFIRMADO"
  • Detalle guardado en tabla DETALLE_PEDIDOS
  • Stock reservado en tabla PRODUCTOS
  • Email enviado al cliente
  • Log de auditoría registrado

Mejores Prácticas

Consejos para elaborar Events, BUCs y PUCs de calidad

DO - Hacer
  • Usar lenguaje claro y consistente
  • Mantener Business Events atómicos
  • BUCs independientes de tecnología
  • PUCs con suficiente detalle para desarrollar
  • Validar con stakeholders regularmente
  • Documentar excepciones y flujos alternativos
  • Usar diagramas para complementar texto
  • Mantener trazabilidad Event→BUC→PUC
  • Revisar y actualizar documentación
DON'T - Evitar
  • Mezclar perspectivas (negocio y sistema)
  • Usar jerga técnica en BUCs
  • Omitir precondiciones y postcondiciones
  • Hacer PUCs muy abstractos o muy específicos
  • Duplicar casos de uso
  • Ignorar flujos de error
  • Asumir conocimiento implícito
  • Copiar y pegar sin adaptar
  • Documentar solo el flujo feliz
Tip Profesional

Comienza siempre por los Business Events. Son la base de todo el análisis. Un evento bien identificado facilita la elaboración de BUCs y PUCs precisos. Invierte tiempo en esta etapa inicial.

Herramientas Recomendadas
  • Visual Paradigm: Para diagramas UML
  • Balsamiq: Para wireframes de PUCs
  • Confluence/Notion: Para documentación colaborativa
  • Jira: Para trazabilidad de requerimientos
  • Lucidchart: Para modelado de procesos

Errores Comunes

Qué evitar al elaborar Events, BUCs y PUCs

Error 1: Confundir Event con BUC

Incorrecto: Business Event = "Procesar pedido del cliente"

Correcto: Business Event = "Cliente realiza pedido"

El evento es lo que sucede, no la respuesta del negocio

Error 2: BUC con detalles técnicos

Incorrecto: "Sistema consulta tabla CLIENTES en MySQL y ejecuta SELECT..."

Correcto: "Vendedor verifica datos del cliente"

Los BUCs deben ser independientes de tecnología

Error 3: PUC muy vago

Incorrecto: "Sistema guarda los datos"

Correcto: "Sistema inserta registro en tabla PEDIDOS con campos: ID_PEDIDO, ID_CLIENTE, FECHA, TOTAL, ESTADO"

Los PUCs necesitan suficiente detalle para desarrollar

Error 4: Omitir flujos alternativos

Problema: Solo documentar el escenario perfecto (happy path)

Solución: Incluir qué pasa cuando hay errores, datos inválidos, o situaciones excepcionales

Los sistemas deben manejar tanto éxitos como fallos

Error 5: No trazar la relación Event→BUC→PUC

Problema: PUCs huérfanos sin conexión clara con el negocio

Solución: Mantener matriz de trazabilidad que muestre de dónde deriva cada elemento

La trazabilidad facilita el mantenimiento y validación

Cómo Evitar Estos Errores
  • Revisar la documentación con múltiples stakeholders
  • Usar plantillas estandarizadas para cada tipo de documento
  • Realizar sesiones de validación cruzada entre analistas
  • Mantener un glosario de términos del proyecto

Caso de Estudio Completo

Sistema de Gestión de Biblioteca

Contexto del Sistema

Una biblioteca universitaria necesita automatizar el proceso de préstamo de libros. Actualmente todo se hace manualmente con fichas de papel.

BUSINESS EVENT

"Estudiante solicita préstamo de libro"

BUC: Procesar Préstamo de Libro

Actores: Estudiante (primario), Bibliotecario (secundario)

Flujo Básico:

  1. Estudiante presenta su carnet y solicita el libro
  2. Bibliotecario verifica que el estudiante esté activo
  3. Bibliotecario verifica disponibilidad del libro
  4. Bibliotecario registra el préstamo
  5. Bibliotecario calcula la fecha de devolución (7 días)
  6. Bibliotecario entrega el libro al estudiante
  7. Estudiante firma el comprobante

Flujos Alternativos:

  • 2a. Si estudiante tiene préstamos vencidos, no se permite nuevo préstamo
  • 3a. Si libro no está disponible, se ofrece realizar una reserva

Postcondición: El préstamo queda registrado y el libro marcado como prestado

PUC: Registrar Préstamo en Sistema

Actores: Usuario Bibliotecario, Sistema de Control Académico

Flujo Básico:

  1. Usuario accede al módulo "Préstamos" desde menú principal
  2. Sistema muestra pantalla "Nuevo Préstamo"
  3. Usuario ingresa código de estudiante en campo "Carnet"
  4. Sistema consulta API del Sistema Académico para validar estudiante
  5. Sistema verifica en tabla PRESTAMOS si hay préstamos vencidos (WHERE fecha_devolucion < CURDATE() AND estado='ACTIVO')
  6. Sistema muestra datos del estudiante: nombre, carrera, foto
  7. Usuario escanea código de barras del libro
  8. Sistema consulta tabla LIBROS por ISBN
  9. Sistema verifica campo ESTADO = 'DISPONIBLE'
  10. Sistema muestra información del libro
  11. Sistema calcula automáticamente fecha_devolucion = CURDATE() + 7 días
  12. Usuario hace clic en "Confirmar Préstamo"
  13. Sistema inserta registro en tabla PRESTAMOS
  14. Sistema actualiza LIBROS.ESTADO = 'PRESTADO'
  15. Sistema genera comprobante PDF con código QR
  16. Sistema muestra mensaje "Préstamo registrado exitosamente"
  17. Sistema imprime comprobante automáticamente

Flujos Alternativos:

  • 4a. Si API no responde: Sistema muestra "Error de conexión" y guarda en cola de sincronización
  • 5a. Si hay préstamos vencidos: Sistema muestra ventana modal con lista de préstamos vencidos y bloquea nuevo préstamo
  • 9a. Si ESTADO != 'DISPONIBLE': Sistema muestra "Libro no disponible" con opción "Ver disponibilidad" que muestra fecha estimada de devolución

Validaciones:

  • Carnet debe ser numérico de 8 dígitos
  • ISBN debe ser válido (formato 13 dígitos)
  • Estudiante no puede tener más de 3 préstamos activos simultáneos
  • Tiempo de respuesta de consultas < 2 segundos

El Camino del Requerimiento

Business Event → BUC → PUC → Código → Sistema Funcionando

Cada etapa agrega más detalle y especificidad, transformando una necesidad del negocio en software funcional.

Factores de Éxito
  • Clara separación de perspectivas
  • Trazabilidad completa
  • Validación con stakeholders
  • Documentación detallada
  • Revisión continua
Beneficios
  • Requerimientos claros y completos
  • Mejor comunicación equipo-cliente
  • Menos cambios durante desarrollo
  • Estimaciones más precisas
  • Mayor calidad del software
