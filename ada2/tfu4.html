La cuenta

Monolito (o app no-microservicios): 2 + 2 + 2 + 1 = 7 patrones.

Con microservicios bien definidos: se puede omitir el grupo 4 → 6 patrones.

Letra chica (nota al pie)
Cada contenedor debe implementar un servicio surgido de una partición de dominio de primer nivel. Separar en contenedores frontend / backend / base de datos es una partición técnica: no cuenta como microservicios.
Ojo: Competing Consumers aparece en disponibilidad y en rendimiento. Pueden usarlo, pero cuenta para un solo grupo. Justifiquen en cuál y por qué.

Disponibilidad

Health Endpoint Monitoring

¿Cómo logra disponibilidad?

Expone endpoints que un agente externo (Docker, un balanceador, un monitor) consulta periódicamente. Así detecta fallas rápido (reduce el MTTD) y puede sacar de rotación o reiniciar la instancia enferma (reduce el MTTR).

  • /health/live → ¿el proceso responde? (si no: reiniciar)
  • /health/ready → ¿puede atender? Chequea DB, Redis, cola (si no: no enviarle tráfico)
Trade-off: el chequeo consume recursos y no debe exponer información sensible. En producción conviene restringir /health/ready a la red interna.

Health Endpoint · implementación y prueba

api/src/health.js
import { Router } from 'express';
import { pool } from './db.js';
import { redis } from './cache.js';
import { getChannel } from './queue.js';

export const health = Router();

// Liveness: solo dice "el proceso responde"
health.get('/health/live', (req, res) =>
  res.json({ status: 'UP' }));

// Readiness: chequea dependencias con timeout
const conTimeout = (p, ms = 1000) => Promise.race([
  p, new Promise((_, rej) => setTimeout(() => rej(new Error('timeout')), ms))
]);

health.get('/health/ready', async (req, res) => {
  const checks = {
    postgres: () => pool.query('SELECT 1'),
    redis:    () => redis.ping(),
    rabbitmq: async () => { if (!getChannel()) throw new Error('sin canal'); }
  };
  const detalle = {};
  for (const [nombre, fn] of Object.entries(checks)) {
    try { await conTimeout(fn()); detalle[nombre] = 'UP'; }
    catch { detalle[nombre] = 'DOWN'; }
  }
  const ok = Object.values(detalle).every(v => v === 'UP');
  res.status(ok ? 200 : 503).json({
    status: ok ? 'UP' : 'DOWN', checks: detalle, ts: new Date().toISOString()
  });
});

Disponibilidad

Circuit Breaker + Retry

¿Cómo logra disponibilidad?

Retry resuelve fallas transitorias: reintenta con espera exponencial y jitter.

Circuit Breaker resuelve fallas persistentes. Tras N fallas "abre" y falla rápido sin llamar al servicio. Así evita agotar conexiones e hilos esperando timeouts, y la falla no se propaga al resto de la API.

Orden correcto: retry( breaker.fire(...) ). Si el circuito está abierto, no se reintenta.

Circuit Breaker + Retry · implementación

api/src/resilience.js
const sleep = ms => new Promise(r => setTimeout(r, ms));

export class CircuitBreaker {
  constructor(fn, { failureThreshold = 3, resetTimeout = 10000, timeout = 2000 } = {}) {
    Object.assign(this, { fn, failureThreshold, resetTimeout, timeout });
    this.state = 'CLOSED'; this.failures = 0; this.nextAttempt = 0;
  }
  async fire(...args) {
    if (this.state === 'OPEN') {
      if (Date.now() < this.nextAttempt) throw new Error('CIRCUIT_OPEN');
      this.state = 'HALF_OPEN';            // dejo pasar una de prueba
    }
    try {
      const r = await Promise.race([
        this.fn(...args),
        sleep(this.timeout).then(() => { throw new Error('TIMEOUT'); })
      ]);
      this.onSuccess(); return r;
    } catch (e) { this.onFailure(); throw e; }
  }
  onSuccess() { this.failures = 0; this.state = 'CLOSED'; }
  onFailure() {
    this.failures++;
    if (this.state === 'HALF_OPEN' || this.failures >= this.failureThreshold) {
      this.state = 'OPEN';
      this.nextAttempt = Date.now() + this.resetTimeout;
    }
  }
}

export async function retry(fn, { retries = 2, base = 200 } = {}) {
  for (let i = 0; ; i++) {
    try { return await fn(); }
    catch (e) {
      if (e.message === 'CIRCUIT_OPEN' || i >= retries) throw e;
      await sleep(base * 2 ** i + Math.random() * 100); // backoff + jitter
    }
  }
}
api/src/pagos.js
import { Router } from 'express';
import { CircuitBreaker, retry } from './resilience.js';
import { config } from './config.js';

const llamarPagos = async (body) => {
  const r = await fetch(`${process.env.PAGOS_URL}/cobrar`, {
    method: 'POST', headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify(body)
  });
  if (!r.ok) throw new Error(`PAGOS_${r.status}`);
  return r.json();
};

// umbrales leídos del External Configuration Store
export const breaker = new CircuitBreaker(llamarPagos, config.cb);

export const pagos = Router();

pagos.post('/pagos', async (req, res) => {
  try {
    const out = await retry(() => breaker.fire(req.body));
    res.json(out);
  } catch (e) {
    // Fallback: no se pierde el pedido, queda pendiente de cobro
    res.status(503).set('Retry-After', '10').json({
      estado: 'PAGO_PENDIENTE', motivo: e.message, circuito: breaker.state
    });
  }
});

// Endpoint de observación para las pruebas
pagos.get('/pagos/circuito', (req, res) =>
  res.json({ state: breaker.state, failures: breaker.failures }));

Rendimiento

Cache-Aside

¿Cómo logra rendimiento?

La aplicación consulta primero la caché. Si no está el dato (MISS), lo lee de la base y lo guarda con un TTL. Las lecturas siguientes (HIT) salen de memoria: menor latencia y menos carga en la base, lo que aumenta el throughput.

Al escribir: se actualiza la base y se invalida la clave (DEL).

Trade-off: consistencia eventual. Durante el TTL se puede leer un dato viejo si otro proceso escribió sin invalidar. Elegir el TTL según cuán "fresco" debe ser el dato.

Cache-Aside · implementación y prueba

api/src/productos.js
import { Router } from 'express';
import { pool } from './db.js';
import { redis } from './cache.js';
import { config } from './config.js';

export const productos = Router();

productos.get('/productos/:id', async (req, res) => {
  const key = `producto:${req.params.id}`;

  if (config.cacheEnabled) {
    const cached = await redis.get(key);
    if (cached) {
      res.set('X-Cache', 'HIT');
      return res.json(JSON.parse(cached));
    }
  }

  const { rows } = await pool.query(
    'SELECT id, nombre, precio, stock FROM productos WHERE id = $1',
    [req.params.id]);
  if (!rows.length) return res.status(404).json({ error: 'no existe' });

  if (config.cacheEnabled)
    await redis.set(key, JSON.stringify(rows[0]), { EX: config.cacheTtl });

  res.set('X-Cache', config.cacheEnabled ? 'MISS' : 'BYPASS').json(rows[0]);
});

productos.put('/productos/:id', async (req, res) => {
  const { nombre, precio, stock } = req.body;
  await pool.query(
    'UPDATE productos SET nombre=$1, precio=$2, stock=$3 WHERE id=$4',
    [nombre, precio, stock, req.params.id]);
  await redis.del(`producto:${req.params.id}`);   // invalidación
  res.status(204).end();
});

Rendimiento

Queue-Based Load Leveling + Competing Consumers

¿Cómo logra rendimiento?

La cola actúa como buffer: desacopla la tasa de llegada de la tasa de procesamiento. Ante un pico, la API solo encola y responde 202 Accepted en milisegundos. Los workers procesan a un ritmo que la base soporta.

Competing Consumers: varios workers consumen la misma cola. Se escala horizontalmente con --scale worker=N.

El 202 + Location es también Asynchronous Request-Reply: el cliente consulta GET /pedidos/:id.

Trade-off: el procesamiento es asincrónico, así que el cliente no tiene el resultado inmediato. Requiere idempotencia y manejo de mensajes fallidos (DLQ).

api/src/pedidos.js (productor)
import { Router } from 'express';
import { randomUUID } from 'node:crypto';
import { pool } from './db.js';
import { getChannel } from './queue.js';

export const pedidos = Router();

pedidos.post('/pedidos', async (req, res) => {
  const id = randomUUID();
  await pool.query(
    "INSERT INTO pedidos(id, estado, payload) VALUES ($1,'PENDIENTE',$2)",
    [id, req.body]);
  getChannel().sendToQueue('pedidos',
    Buffer.from(JSON.stringify({ id, ...req.body })),
    { persistent: true });
  res.status(202).location(`/pedidos/${id}`)
     .json({ id, estado: 'PENDIENTE' });
});

pedidos.get('/pedidos/:id', async (req, res) => {
  const { rows } = await pool.query(
    'SELECT id, estado, worker FROM pedidos WHERE id=$1',
    [req.params.id]);
  rows.length ? res.json(rows[0]) : res.status(404).end();
});
worker/index.js (consumidor)
import amqp from 'amqplib';
import pg from 'pg';
import os from 'node:os';

const pool = new pg.Pool({ connectionString: process.env.DATABASE_URL });
const conn = await amqp.connect(process.env.AMQP_URL);
const ch = await conn.createChannel();

await ch.assertQueue('pedidos.dlq', { durable: true });
await ch.assertQueue('pedidos', {
  durable: true,
  deadLetterExchange: '',
  deadLetterRoutingKey: 'pedidos.dlq'
});
ch.prefetch(1);   // reparto justo entre consumidores

ch.consume('pedidos', async (msg) => {
  const p = JSON.parse(msg.content.toString());
  try {
    await procesar(p);  // validar stock, totales, etc.
    await pool.query(
      "UPDATE pedidos SET estado='PROCESADO', worker=$2 " +
      "WHERE id=$1 AND estado='PENDIENTE'",  // idempotente
      [p.id, os.hostname()]);
    ch.ack(msg);
  } catch (e) {
    console.error(e);
    ch.nack(msg, false, false);  // va a la DLQ
  }
});

async function procesar(p) {
  await new Promise(r => setTimeout(r, 100)); // trabajo simulado
}

Seguridad

Gatekeeper

¿Cómo logra seguridad?

Un host dedicado, expuesto, que autentica, valida y sanea cada solicitud antes de reenviarla al host de confianza (la API). La API vive en una red interna sin puertos publicados.

  • Reduce la superficie de ataque: la API no es alcanzable desde afuera.
  • Limita el radio de impacto: si comprometen el gatekeeper, no tiene credenciales de la base ni lógica de negocio.
Trade-off: agrega un salto de red (latencia) y es un posible punto único de falla. Mitigación: réplicas del gatekeeper.

Seguridad

Gateway Offloading

¿Cómo logra seguridad?

Mueve al gateway las funciones transversales que cada servicio tendría que repetir:

  • Terminación TLS y redirección HTTP → HTTPS
  • Cabeceras de seguridad (HSTS, nosniff, frame-options)
  • Límite de tasa → 429
  • Compresión, X-Request-Id para trazabilidad

Un solo lugar configurado y auditado: menos chances de que un servicio quede mal configurado. Los certificados se gestionan en un único punto.

¿Gatekeeper y Offloading son lo mismo? No. El offloading quita responsabilidades de infraestructura; el gatekeeper valida el contenido y aísla al host de confianza. Acá viven en contenedores distintos para que se vea la separación.
nginx/nginx.conf
events {}
http {
  limit_req_zone $binary_remote_addr zone=api:10m rate=10r/s;
  server_tokens off;

  upstream gatekeeper { server gatekeeper:4000; }

  server {                              # HTTP -> HTTPS
    listen 80;
    return 301 https://$host$request_uri;
  }

  server {
    listen 443 ssl;
    http2 on;
    ssl_certificate     /etc/nginx/certs/cert.pem;
    ssl_certificate_key /etc/nginx/certs/key.pem;
    ssl_protocols TLSv1.2 TLSv1.3;

    gzip on; gzip_types application/json; gzip_min_length 256;

    add_header Strict-Transport-Security "max-age=31536000" always;
    add_header X-Content-Type-Options "nosniff" always;
    add_header X-Frame-Options "DENY" always;

    location / {
      limit_req zone=api burst=20 nodelay;
      limit_req_status 429;
      proxy_pass http://gatekeeper;
      proxy_set_header X-Request-Id $request_id;
      proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
      proxy_set_header X-Forwarded-Proto https;
    }
  }
}

Modificabilidad y despliegue

External Configuration Store

¿Cómo logra modificabilidad?

La configuración sale del paquete desplegado y pasa a un almacén externo compartido. Cambiar TTLs, umbrales del breaker o feature flags no requiere recompilar, reconstruir la imagen ni redesplegar. Todas las réplicas leen la misma fuente.

sequenceDiagram
  participant Op as Operador
  participant CS as config-server
  participant A as api x N
  A->>CS: GET /config/api al arrancar
  loop cada 10 s
    A->>CS: GET /config/api
    CS-->>A: json
  end
  Op->>CS: edita api.json
  A->>CS: GET /config/api
  CS-->>A: nuevo valor
  Note over A: aplica sin reiniciar
Trade-off: nueva dependencia en runtime. Si el store cae, la API sigue con el último valor conocido. Los secretos van a un vault, no aquí.

Estrategias de despliegue

Aparecen junto al grupo 4. Complementan al patrón elegido; todas reducen el riesgo de introducir una versión nueva.

Blue/green

Dos entornos idénticos. Se despliega en green, se prueba y se cambia el tráfico de golpe. El rollback es volver a blue.

En Compose: api-blue y api-green; nginx cambia el upstream + nginx -s reload.

Rolling upgrade

Se reemplazan las instancias de a una; siempre hay réplicas atendiendo. Requiere compatibilidad entre versiones.

Swarm/K8s: update_config: parallelism: 1. Se apoya en los health checks.

Canary

Una fracción pequeña del tráfico (p. ej. 10 %) va a la versión nueva. Se observan errores y latencia antes de ampliar.

nginx: split_clients o weight= en el upstream.

A/B testing

Dos variantes funcionales a segmentos de usuarios para medir cuál cumple mejor un objetivo de negocio. No es de riesgo técnico.

Feature flag por usuario, que puede venir del External Configuration Store.
Ejemplo canary en nginx
upstream gatekeeper {
  server gatekeeper-v1:4000 weight=9;
  server gatekeeper-v2:4000 weight=1;   # ~10 % del tráfico a la versión nueva
}

¿Mi app cuenta como microservicios?

Solo si la partición es de dominio de primer nivel. Cada servicio es dueño de una capacidad de negocio y de sus datos.

Partición técnica (NO cuenta)

flowchart LR
  F[frontend] --> B[backend con TODO el dominio] --> D[(base)]

Tres contenedores, pero un único servicio de negocio dividido por capas. → 7 patrones.

Partición de dominio (cuenta)

flowchart LR
  GW[gateway] --> CA[catálogo] --> D1[(db catálogo)]
  GW --> PE[pedidos] --> D2[(db pedidos)]
  GW --> PA[pagos] --> D3[(db pagos)]

Cada servicio = un subdominio con su propia base. → pueden omitir el grupo 4: 6 patrones.

La solución de referencia de esta presentación es un monolito modular con contenedores de infraestructura (gateway, cola, caché). Por eso incluye el patrón del grupo 4.

Errores frecuentes que restan puntos

Patrón "de papel"

Está en el documento pero no en el código, o el código no se ejecuta en ningún endpoint.

Prueba que no prueba

"Hago un GET y da 200". Hay que provocar la condición (caída, pico, ataque) y medir.

UML genérico

Copiar el diagrama del catálogo de Microsoft. El UML debe tener sus clases, servicios y nodos.

Contar doble

Competing Consumers en dos grupos, o Rate Limiting + Throttling siendo el mismo limit_req.

Gatekeeper con puerta trasera

La API sigue con ports: 3000:3000 publicado. El gatekeeper no sirve de nada.

"En mi máquina anda"

Rutas absolutas, imágenes locales, pasos manuales no documentados. Probar en una máquina limpia.

Ignorar la retroalimentación

El enunciado pide incorporar las devoluciones de la TFU anterior. Indiquen qué cambiaron.

Sin trade-offs

Todo patrón tiene un costo. No mencionarlo muestra que no se analizó.

Secretos en el repo

Commitear .env real o claves privadas. Usar .env.example.
