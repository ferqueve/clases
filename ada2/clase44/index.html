Conceptos · Teórico 2.7

¿Qué es un estilo de arquitectura?

Un estilo de arquitectura es la forma macro de organizar una aplicación: define su topología (qué piezas hay y cómo se conectan) y las características típicas que resultan de esa organización.

Un patrón de arquitectura, en cambio, es una solución reusable a un problema recurrente dentro de esa topología, con sus fuerzas, consecuencias y trade-offs.

Los estilos describen cómo se estructura un sistema; los patrones describen cómo resolver problemas dentro de esa estructura.

Elegir un estilo es elegir un conjunto de trade-offs: ningún estilo es bueno en todo. Por eso se justifica comparando las características del estilo con los drivers del caso: requerimientos no funcionales y restricciones.

Monolíticos

Una sola unidad de despliegue: los componentes interactúan localmente, dentro del mismo proceso. Más simples y baratos, pero escalan y toleran fallos peor. Layered, Pipes & Filters y Microkernel.

Distribuidos

Varios componentes desplegados por separado que se comunican por invocación remota o mensajería. Service-Based, Event-Driven, Space-Based, SOA y Microservicios. Hay que tener en cuenta las falacias de la computación distribuida (próximas slides).

Conceptos · Teórico 2.7 · Los estilos

Los estilos de arquitectura de un vistazo

Para descartar alternativas hay que conocerlas. Una línea por estilo, según el teórico de ANDIS.

Monolíticos una unidad de despliegue

Layered: capas lógicas con roles definidos; cada capa usa la inmediata inferior.

Pipes & Filters: filtros independientes que transforman datos, conectados por tuberías, de la entrada a la salida.

Microkernel: núcleo mínimo más plug-ins; típico de aplicaciones de producto instaladas en el cliente.

Distribuidos ojo con las falacias de la computación distribuida

Service-Based: pocos servicios de dominio; distribuido pero sin el costo y la complejidad de microservicios o eventos.

Event-Driven: componentes independientes que procesan eventos de forma asíncrona; alta escalabilidad y rendimiento.

Space-Based: datos replicados en memoria entre unidades de procesamiento que se inician y detienen según la carga.

Orchestration-Driven SOA: servicios empresariales coordinados por un motor de orquestación; nació en grandes corporaciones de fines de los 90.

Microservicios: cada servicio es una unidad separada con su propia base de datos, comunicado por API livianas.

Conceptos · Formas de comunicarse

Sincrónica vs asincrónica

Sincrónica (petición/respuesta)

Quien llama espera la respuesta para seguir, como una llamada telefónica. Ejemplos: REST, RPC. Si el otro está caído o lento, quien llama también queda bloqueado.

Asincrónica (enviar y seguir)

Quien envía deja el mensaje y sigue trabajando, como un correo. El receptor lo procesa cuando puede. No necesitan estar disponibles al mismo tiempo.

La mensajería asincrónica es una solución pragmática a los problemas de los sistemas distribuidos: reconoce la latencia de las comunicaciones remotas y baja el acoplamiento entre las partes.

Conceptos · Teórico 2.13.4 Messaging

Mensajería y broker de mensajes

La mensajería permite integrar aplicaciones construidas de forma independiente transfiriendo paquetes de datos de forma frecuente, inmediata, confiable y asíncrona.

  • Remitente y receptor: quien envía y quien recibe el mensaje.
  • Canal de mensajes (message channel): conecta al remitente con el receptor.
  • Enrutador (message router): decide a qué receptor va cada mensaje.
  • Traductor (message translator): convierte el mensaje al formato que necesita el receptor.
  • Endpoint: el código de la aplicación que se conecta al sistema de mensajería para enviar y recibir.
El broker

Es el servidor intermediario que implementa los canales: recibe, guarda y entrega los mensajes. Remitente y receptor solo conocen al broker, no se conocen entre sí. Ejemplos: Apache Kafka, RabbitMQ, Azure Service Bus, Amazon SNS/SQS.

Qué se gana
  • Los dos lados no necesitan estar disponibles al mismo tiempo: el broker guarda el mensaje.
  • Varias aplicaciones pueden recibir el mismo mensaje.
  • Si llegan más pedidos de los que se pueden procesar, el broker absorbe el pico (nivelación de carga con colas).
Conceptos · Patrones de canal

Publicar/suscribir vs punto a punto

Punto a punto (cola)

Cada mensaje lo procesa un solo receptor. Si hay varios escuchando la misma cola, compiten y se reparten los mensajes.

Emisor cola Receptor A o B

Uso típico: comandos y reparto de trabajo.

Publicar/suscribir (tópico)

El publicador envía a un tópico; cada suscriptor recibe su propia copia. El publicador no sabe quiénes ni cuántos son.

Publicador tópico Pagos y Inventario y Notificaciones

Uso típico: eventos. Agregar un suscriptor nuevo no toca al publicador.

Los brokers modernos combinan los dos: un tópico con grupos de consumidores. Entre grupos funciona como pub/sub (cada grupo recibe todo) y dentro de un grupo como cola (las instancias se reparten el trabajo). Es lo que pide la consigna: varios procesadores de pago.
Conceptos · Teórico 2.7.5 + Richards & Ford

Arquitectura dirigida por eventos

Estilo distribuido, ampliamente usado para crear aplicaciones altamente escalables y de alto rendimiento. Se basa en componentes de procesamiento de eventos que operan de manera independiente y procesan los eventos de forma asíncrona.

En lugar de que un componente llame a otro y espere, cada componente reacciona a lo que pasó y, al terminar, anuncia lo que hizo con un nuevo evento.

Contraste con el modelo basado en peticiones (request-based): ahí un orquestador recibe la solicitud y llama, en orden y esperando, a cada componente. Sirve para consultas y flujos deterministas; event-driven sirve para reaccionar a hechos con alto volumen.

eventos de procesamiento los que generan los procesadores al terminar: PagoAprobado, StockReservado.

orquestador / mediador «orchestrator» solo en la topología con mediador (siguiente slide). El teórico usa estos dos estereotipos.

Conceptos · Dos topologías

Topología broker vs topología mediador

Broker (coreografía)

No hay coordinador central. Cada procesador escucha eventos, hace su parte y publica un nuevo evento. El flujo surge de esa cadena, como una coreografía donde cada bailarín conoce sus pasos.

  • Muy desacoplado
  • Mejor escalabilidad, rendimiento y tolerancia a fallos
  • Nadie controla el flujo completo
  • Manejo de errores y reintentos más difícil
  • Difícil saber en qué estado está un pedido
Mediador (orquestación)

Un mediador («orchestrator») recibe el evento iniciador y envía, en orden, los pasos a cada procesador («processor»). Como un director de orquesta.

  • Control del flujo y del estado
  • Mejor manejo de errores y recuperación
  • Mejor consistencia de datos
  • Más acoplamiento con el mediador
  • El mediador puede ser un cuello de botella
  • Menor escalabilidad y rendimiento
La plantilla del teórico dibuja la topología con mediador («orchestrator» y «processor»). La elección es un trade-off: más control (mediador) o más escalabilidad y tolerancia a fallos (broker). Se pueden combinar: broker para lo general, mediador para un flujo crítico.
Conceptos · Escalar consumidores

Grupos de consumidores y consumidores competidores

Un grupo de consumidores es un conjunto de instancias del mismo tipo de procesador que comparten el trabajo:

  • Entre grupos: cada grupo recibe todos los eventos (pub/sub).
  • Dentro de un grupo: cada evento lo procesa una sola instancia (consumidores competidores).
  • Escalar es agregar instancias al grupo.
  • Si una instancia cae, el broker reparte su trabajo entre las demás (rebalanceo): tolerancia a fallos.

En Kafka el trabajo se reparte por partición (lo vemos en la próxima slide).

Conceptos · Restricción: claves de partición

Particiones y claves de partición

Un tópico se divide en particiones: secuencias ordenadas e independientes de eventos. Permiten paralelismo: cada partición la atiende una instancia del grupo.

Al publicar se indica una clave. El broker calcula hash(clave) mod N y así la misma clave siempre va a la misma partición.

  • Orden garantizado solo dentro de una partición. Con clave = pedidoId, los eventos de un pedido se procesan en orden.
  • Límite de escala: en un grupo no puede haber más instancias activas que particiones.
  • Clave caliente: si una clave concentra muchos eventos, su partición se satura. Hay que elegir claves que repartan bien.

Conceptos · ¿Cuántas veces llega un mensaje?

Garantías de entrega

A lo sumo una vez
at-most-once

Se confirma antes de procesar. Si el consumidor se cae a la mitad, el mensaje se pierde. Aceptable para métricas, nunca para un pago.

Al menos una vez
at-least-once

Se confirma después de procesar. Si se cae antes de confirmar, el broker lo reenvía: nada se pierde, pero puede llegar duplicado. Es lo más usado.

Exactamente una vez
exactly-once

Lo ideal, pero caro y limitado: algunos brokers lo ofrecen solo dentro de su propio ecosistema. En la práctica se logra el efecto con al-menos-una-vez + idempotencia.

Confirmación (ack / offset)

El consumidor le avisa al broker que terminó con un mensaje. En Kafka se guarda el offset: la posición hasta donde se leyó cada partición. Si el consumidor reinicia, sigue desde ahí.

El problema de la doble escritura

Guardar en la base y publicar el evento son dos operaciones; si falla una, quedan inconsistentes. Solución habitual: outbox transaccional: el evento se guarda en una tabla en la misma transacción y otro proceso lo publica.

Conceptos · Restricción: idempotencia

Idempotencia

Una operación es idempotente si ejecutarla una vez o muchas deja el sistema en el mismo estado. Con entrega al-menos-una-vez los duplicados van a llegar: cada consumidor tiene que tolerarlos.

  • Registro de eventos procesados: guardar el eventId y descartar si ya está.
  • Operaciones idempotentes por naturaleza: "estado = PAGADO" sí; "saldo = saldo − 100" no.
  • Clave de idempotencia hacia afuera: la pasarela de pagos recibe pedidoId y no cobra dos veces.
  • Productor idempotente: el broker descarta reenvíos del mismo productor.
public async Task Handle(PedidoCreado e)
{
    if (await db.YaProcesado(e.EventId)) return;  // duplicado
    var r = await pasarela.Cobrar(e.PedidoId, e.Total,
                 idempotencyKey: $"pedido-{e.PedidoId}");
    await db.GuardarJuntos(e.EventId, r);  // misma transacción
}

Conceptos · BASE y teorema de Brewer

Consistencia fuerte vs consistencia eventual

Consistencia fuerte

Toda lectura devuelve el último valor escrito: todos ven los mismos datos en el mismo orden. Es lo que dan las transacciones ACID en una sola base de datos.

Consistencia eventual

Forma de consistencia débil: si no hay nuevas actualizaciones, eventualmente todas las lecturas devuelven el último valor. El tiempo hasta lograrlo es la ventana de inconsistencia. El ejemplo clásico es el DNS.

BASE vs ACID

Basic Availability, Soft state, Eventual consistency: sistemas que priorizan la disponibilidad y aceptan inconsistencias temporales.

Teorema de Brewer (CAP)

Entre consistencia fuerte (C), alta disponibilidad (A) y tolerancia a la partición de red (P), solo se pueden garantizar dos a la vez. En un sistema distribuido las particiones de red pasan, así que, cuando ocurren, hay que elegir entre C y A. Event-driven elige A y acepta consistencia eventual.

Conceptos · Cuando algo sale mal

Sagas, compensaciones y colas de mensajes muertos

Sin una transacción ACID que abarque todos los servicios, no se puede hacer rollback de un pedido que ya pasó por varios procesadores.

Saga

Una transacción larga dividida en pasos locales, cada uno con su acción compensatoria que deshace su efecto. En la topología broker la saga es coreografiada: cada procesador reacciona al evento de fallo y compensa lo suyo.

Ejemplo: el pago se rechaza después de reservar stock.

PagoRechazado → Inventario libera la reserva (compensa) → Notificaciones avisa al cliente → Pedidos marca el pedido como cancelado.

Reintentos

Ante un error transitorio (la pasarela no responde), se reintenta con espera creciente (backoff). Los reintentos solo son seguros si el consumidor es idempotente.

Dead letter queue (DLQ)

Un mensaje que falla siempre (poison message, por ejemplo con datos corruptos) bloquearía su partición. Después de N intentos se mueve a una cola de mensajes muertos para revisarlo aparte, y el resto sigue fluyendo.

Observabilidad

Con el correlationId en cada evento se puede reconstruir el recorrido completo de un pedido entre todos los procesadores.

Conceptos · Criterio de elección

Cuándo usar event-driven y cuándo no

Conviene cuando…
  • Hay mucho volumen y picos de carga
  • Varias partes tienen que reaccionar al mismo hecho
  • Se necesita alta disponibilidad: que una parte caída no frene a las demás
  • El negocio tolera consistencia eventual
  • Se quiere sumar consumidores nuevos sin tocar a los productores
No conviene cuando…
  • Se necesita consistencia fuerte inmediata en todo el flujo
  • El usuario necesita una respuesta sincrónica con el resultado final
  • El equipo es chico o el presupuesto bajo: es el estilo más complejo
  • El flujo es simple y de poco volumen: sería sobreingeniería
  • Se necesita mucho control del flujo paso a paso (ahí, mediador u orquestación)
Comparalo con las TA anteriores: el gimnasio (TA1) pedía simplicidad y bajo costo → monolito. Acá los drivers son desempeño, escala y tolerancia a fallos → hay que pagar el costo de distribuir.

Conceptos · Lectura de un diagrama

Cómo se lee un diagrama de despliegue

Ejemplo genérico: una aplicación de escritorio que usa un motor de base de datos en otro equipo.

  1. Anidamiento = despliegue. Lo que está dentro de un nodo está desplegado en él: app.exe corre en .NET 8, que corre en Windows, que corre en la notebook.
  2. Cada línea entre nodos es una comunicación por red, con su protocolo. Si dos piezas están en el mismo nodo y proceso, se llaman localmente.
  3. La multiplicidad (*, 1) dice cuántas instancias participan: muchas notebooks, un servidor.
  4. "Distribuir" es poner componentes en nodos distintos conectados por red. Un estilo monolítico tiene su aplicación en un solo ambiente de ejecución; uno distribuido, como event-driven, en muchos.
Conceptos · Despliegue distribuido

Cómo dibujar réplicas y clústeres

En un sistema distribuido hay varias instancias del mismo nodo. UML ofrece formas de mostrarlo sin dibujar cada copia:

  • Multiplicidad en el nodo: un número o rango en la esquina, por ejemplo 3 o 2..* instancias.
  • Instancias con nombre: pagos-a : NodoPagos, pagos-b : NodoPagos, cuando importa distinguirlas.
  • Multiplicidad en las rutas: * clientes contra 1 servicio, o 2..* procesadores contra un clúster.
  • Estereotipos propios como «cluster» para agrupar nodos que actúan como uno solo (por ejemplo, los 3 nodos del broker).
¿QUÉ TIENE QUE SER VISIBLE EN EL DIAGRAMA DE ESTA TAREA?
  • Qué nodos son independientes entre sí (se distribuyen)
  • Que hay más de una instancia de los procesadores de pago
  • Que el broker es un clúster (sin punto único de falla)
  • Qué base de datos es de cada procesador
  • Por dónde viajan los eventos: todo pasa por el broker; los procesadores no se llaman entre sí

Resolución · Parte 1 · Riesgos

Riesgos del estilo y cómo mitigarlos

Eventos duplicados

Mitigación: consumidores idempotentes y clave de idempotencia en la pasarela de pagos.

Eventos fuera de orden

Mitigación: clave de partición pedidoId; versión del pedido en el evento para descartar eventos viejos.

Mensajes venenosos

Mitigación: reintentos con backoff y DLQ para no bloquear la partición.

Flujo difícil de seguir

Mitigación: correlationId, trazas distribuidas y un estado del pedido que Pedidos va actualizando con cada evento.

Cambios en el formato de los eventos

Mitigación: schemaVersion, cambios compatibles hacia atrás y registro de esquemas.

El cliente ve datos viejos

Mitigación: diseñar la interfaz para la consistencia eventual: "Pedido recibido, estamos procesando el pago".

Resolución · Parte 1 · Respuesta modelo

Cómo lo redactaríamos

El estilo event-driven es el más adecuado porque el problema es, en esencia, una cadena de reacciones a hechos del dominio: un pedido creado desencadena pago, actualización de inventario, logística y notificaciones. Los requerimientos funcionales piden explícitamente publicación y suscripción a eventos de dominio y varios consumidores del mismo tipo, que se resuelven con tópicos y grupos de consumidores en el broker.

Sus características coinciden con los no funcionales: es el estilo con mejor desempeño, escalabilidad y tolerancia a fallos, porque los procesadores trabajan de forma asíncrona, en paralelo y sin llamarse entre sí; cada uno escala agregando instancias y, si uno falla, los eventos esperan en el broker. La consistencia eventual que pide el caso es la consistencia propia del estilo, y los fallos parciales se resuelven con sagas y compensaciones.

La restricción del broker con claves de partición se cumple usando el pedidoId como clave, lo que garantiza el orden de los eventos de cada pedido y el paralelismo entre pedidos; la de idempotencia, con entrega al-menos-una-vez y consumidores que descartan eventos ya procesados. Se elige la topología broker porque maximiza estas características. Su costo —baja simplicidad y testeabilidad— es aceptable porque el caso no prioriza ni simplicidad ni bajo costo.

Diagrama de despliegue UML

Resolución · Parte 2 · ¿Qué se distribuye y qué no?

Lectura del diagrama

ElementoEstereotipoQué representa
Dispositivo del cliente«device»Navegador o app móvil con el carrito. Habla por HTTPS solo con el servicio de Pedidos.
Nodos de Pedidos 2..*«device»El productor: recibe la compra, guarda el pedido y publica PedidoCreado (con outbox). Tiene su propia base.
Clúster del broker 3«cluster»Tres nodos con los tópicos particionados y replicados: si uno cae, los otros siguen. Incluye la DLQ.
topics.yaml«deploymentSpec»Tópicos, cantidad de particiones, factor de replicación, retención.
Nodos de Pagos 3, Inventario, Logística, Notificaciones 2..*«device» «processor»Procesadores independientes, cada uno en sus propios nodos y con su propia base. Solo se comunican a través del broker.
Pasarela de pagos · proveedor de email/SMS«node»Sistemas externos, llamados por HTTPS con clave de idempotencia.
A diferencia de las TA1 y TA2, acá todo se distribuye: cada procesador es una unidad de despliegue separada, con varias instancias. Lo que no se distribuye entre procesadores es la base de datos: cada uno tiene la suya.

El diagrama en PlantUML

Pegalo en plantuml.com o en la extensión de VS Code para generar la imagen.

@startuml
' UT5 TA3 - Plataforma de pedidos - Event-Driven (topología broker)
node "Dispositivo del cliente" <<device>> as cli {
  node "Navegador / app" <<executionEnvironment>> as nav
}
node "Nodo de Pedidos (2..*)" <<device>> as nPed {
  artifact "pedidos-api" as ped
  database "pedidos_db + outbox" as dbPed
}
node "Clúster del broker (3 nodos)" <<cluster>> as brk {
  node "Kafka" <<executionEnvironment>> as kafka {
    artifact "pedidos (12 particiones)" as tPed
    artifact "pagos" as tPag
    artifact "inventario" as tInv
    artifact "envios" as tEnv
    artifact "dlq" as tDlq
    artifact "topics.yaml" <<deploymentSpec>> as cfg
  }
}
node "Nodo de Pagos (3)" <<device>> as nPag {
  artifact "pagos-processor" <<processor>> as pPag
  database "pagos_db" as dbPag
}
node "Nodo de Inventario (2..*)" <<device>> as nInv {
  artifact "inventario-processor" <<processor>> as pInv
  database "inventario_db" as dbInv
}
node "Nodo de Logística (2..*)" <<device>> as nLog {
  artifact "logistica-processor" <<processor>> as pLog
  database "logistica_db" as dbLog
}
node "Nodo de Notificaciones (2..*)" <<device>> as nNot {
  artifact "notificaciones-processor" <<processor>> as pNot
}
node "Pasarela de pagos (externa)" <<node>> as pay
node "Proveedor email/SMS (externo)" <<node>> as msg

nav "*" -- "1" nPed : HTTPS
nPed -- brk : TCP (protocolo Kafka)
brk -- nPag : TCP
brk -- nInv : TCP
brk -- nLog : TCP
brk -- nNot : TCP
nPag -- pay : HTTPS + idempotency key
nNot -- msg : HTTPS
