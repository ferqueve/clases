Conceptos · Teórico 2.7

¿Qué es un estilo de arquitectura?

Un estilo de arquitectura es la forma macro de organizar una aplicación: define su topología (qué piezas hay y cómo se conectan) y las características típicas que resultan de esa organización.

Un patrón de arquitectura, en cambio, es una solución reusable a un problema recurrente dentro de esa topología, con sus fuerzas, consecuencias y trade-offs.

Los estilos describen cómo se estructura un sistema; los patrones describen cómo resolver problemas dentro de esa estructura.

Elegir un estilo es elegir un conjunto de trade-offs: ningún estilo es bueno en todo. Por eso se justifica comparando las características del estilo con los drivers del caso: requerimientos no funcionales y restricciones.

Monolíticos

Una sola unidad de despliegue: los componentes interactúan localmente, dentro del mismo proceso. Más simples y baratos, pero escalan y toleran fallos peor. Layered, Pipes & Filters y Microkernel.

Distribuidos

Varios componentes desplegados por separado que se comunican por invocación remota o mensajería. Hay que tener en cuenta las falacias de la computación distribuida: la red no es confiable, la latencia no es cero, el ancho de banda no es infinito…

Conceptos · Teórico 2.7 · Los estilos

Los estilos de arquitectura de un vistazo

Para descartar alternativas hay que conocerlas. Una línea por estilo, según el teórico de ANDIS.

Monolíticos una unidad de despliegue

Layered: capas lógicas con roles definidos; cada capa usa la inmediata inferior.

Pipes & Filters: filtros independientes que transforman datos, conectados por tuberías, de la entrada a la salida.

Microkernel: núcleo mínimo más plug-ins; típico de aplicaciones de producto instaladas en el cliente.

Distribuidos ojo con las falacias de la computación distribuida

Service-Based: pocos servicios de dominio; distribuido pero sin el costo y la complejidad de microservicios o eventos.

Event-Driven: componentes independientes que procesan eventos de forma asíncrona; alta escalabilidad y rendimiento.

Space-Based: datos replicados en memoria entre unidades de procesamiento que se inician y detienen según la carga.

Orchestration-Driven SOA: servicios empresariales coordinados por un motor de orquestación; nació en grandes corporaciones de fines de los 90.

Microservicios: cada servicio es una unidad separada con su propia base de datos, comunicado por API livianas.

Conceptos · Teórico 2.7.3 + Richards & Ford

Microkernel: definición y origen

El estilo microkernel (también llamado arquitectura de plug-ins) divide la aplicación en dos tipos de componentes:

  • un núcleo («core») con la funcionalidad mínima para que el sistema funcione, y
  • plug-ins («plugin»): componentes independientes que agregan, especializan o extienden esa funcionalidad.

El teórico lo define como un estilo monolítico, adecuado para aplicaciones basadas en productos: empaquetadas, disponibles para descargar e instalar como una única implementación, generalmente en el sitio del cliente.

También se usa en aplicaciones de negocio a medida cuando hay un proceso general estable con muchas variantes (por ejemplo, reglas que cambian según el país o el cliente).

¿Por qué "microkernel"?

El nombre viene de los sistemas operativos: un micronúcleo deja en el kernel solo lo esencial (planificación, memoria, comunicación) y saca los drivers y sistemas de archivos a módulos separados. La aplicación copia la idea: núcleo mínimo y todo lo demás afuera.

Monolítico ≠ un solo archivo

El núcleo y los plug-ins pueden ser archivos distintos (un .exe y varias .dll), pero en ejecución forman una sola unidad: un proceso, un despliegue. Por eso se dice que tiene un único cuanto de arquitectura.

Conceptos · El núcleo

El núcleo: la funcionalidad mínima y el "camino feliz"

Hay dos formas complementarias de definir qué va en el núcleo:

1. Lo mínimo para funcionar

En Eclipse, el núcleo es un editor de texto básico: abrir, editar y guardar. Todo lo que lo convierte en un IDE (lenguajes, depuración, Git) son plug-ins.

2. El camino feliz (happy path)

El núcleo contiene el flujo general del proceso, con poco o nada de procesamiento particular. Las variaciones se delegan en plug-ins.

Beneficio: se elimina la complejidad ciclomática (los if/else encadenados) del núcleo y el código volátil queda aislado. Internamente, el núcleo puede organizarse en capas o como monolito modular.

Ejemplo de Richards & Ford: una empresa de reciclaje que evalúa dispositivos electrónicos usados.

// SIN microkernel: el núcleo conoce cada modelo
public decimal Evaluar(Dispositivo d)
{
    if (d.Modelo == "iPhone 6s")      { /* 40 líneas de reglas */ }
    else if (d.Modelo == "Galaxy S5") { /* otras 40 líneas */ }
    else if (d.Modelo == "Pixel 3")   { /* … */ }
    // cada modelo nuevo obliga a tocar y redesplegar el núcleo
}

// CON microkernel: el núcleo solo recorre el camino feliz
public decimal Evaluar(Dispositivo d)
{
    var plugin = registro.Buscar(d.Modelo);  // ¿quién sabe evaluarlo?
    return plugin.Evaluar(d);                // la variación vive en el plug-in
}
Conceptos · Los plug-ins

Los plug-ins

Son componentes autónomos e independientes que contienen procesamiento especializado, funcionalidades adicionales o código a medida que mejora o extiende el núcleo. Sirven para aislar el código volátil: lo que más cambia queda fuera del núcleo.

Independientes entre sí

Un plug-in no debería depender de otro. Si dependen, deja de poder agregarse o quitarse por separado y el sistema se vuelve frágil.

En compilación

Se incluyen al compilar. Agregar o cambiar uno obliga a recompilar y redesplegar toda la aplicación. Más simple.

En tiempo de ejecución

Se agregan y quitan con la aplicación funcionando, sin redesplegar el núcleo. Se apoyan en frameworks como OSGi (Java) o la carga dinámica de ensamblados (.NET).

Granularidad

Un plug-in puede ser una biblioteca compartida (JAR, DLL), o un paquete o namespace dentro del mismo código, por ejemplo App.Plugins.Evaluacion.IPhone.

La regla práctica: si una funcionalidad varía (por cliente, país, modelo, lenguaje) o es opcional, es candidata a plug-in. Si es imprescindible para el flujo general, va al núcleo.
Conceptos · Cómo se comunican

Conexión entre el núcleo y los plug-ins

Punto a punto (lo habitual)

El núcleo invoca un método o función del plug-in, normalmente de una clase de entrada, dentro del mismo proceso.

  • Rápido: no hay red ni serialización
  • Simple de desplegar y depurar
  • El sistema sigue siendo monolítico
Acceso remoto

El plug-in corre como un servicio aparte y el núcleo lo llama por REST o mensajería. El núcleo sigue siendo una unidad, pero el sistema pasa a ser distribuido.

  • Mayor desacoplamiento
  • El plug-in escala por separado; con mensajería puede ser asíncrono
  • Despliegue y mantenimiento más difíciles
  • Un plug-in remoto puede no responder (fallas de red)
  • Más difícil de probar
La elección es un trade-off: se usa acceso remoto solo cuando sus beneficios (escalar o aislar un plug-in) justifican el costo de distribuir.
Conceptos · Acceso a datos

¿Quién accede a la base de datos?

Los plug-ins no suelen conectarse directamente a la base de datos central compartida. El núcleo es el responsable de esa base: obtiene los datos que el plug-in necesita y se los pasa a través del contrato.

Así se evita que un cambio en el esquema de la base rompa a todos los plug-ins, y el plug-in sigue siendo independiente: solo conoce su contrato.

Un plug-in sí puede tener su propio almacenamiento, al que solo accede él. Por ejemplo, el plug-in de evaluación de un modelo puede guardar sus reglas en una base embebida o un archivo propio.

Conceptos · El registro

El registro de plug-ins

El núcleo necesita saber qué plug-ins hay disponibles y cómo usarlos, sin conocerlos de antemano. Esa información vive en el registro.

Para cada plug-in, el registro guarda:

  • Nombre o identificador y versión
  • Contrato que implementa (qué datos recibe y devuelve)
  • Detalles de acceso: una referencia en memoria si es punto a punto, o la URL y el protocolo si es remoto

Implementación: puede ser tan simple como un diccionario dentro del núcleo, o tan compleja como una herramienta de registro y descubrimiento (Apache ZooKeeper, Consul) cuando los plug-ins son remotos.

// Registro simple, punto a punto, dentro del núcleo
public record PluginEntry(
    string Id,          // "evaluador-iphone6s"
    Version Version,    // 1.2.0
    string Contrato,    // "IEvaluador"
    IEvaluador Acceso); // referencia en memoria

public sealed class PluginRegistry
{
    private readonly Dictionary<string, PluginEntry> _plugins = new();

    public void Registrar(PluginEntry e) => _plugins[e.Id] = e;
    public void Quitar(string id)         => _plugins.Remove(id);
    public PluginEntry? Buscar(string id)  => _plugins.GetValueOrDefault(id);
}
Conceptos · Los contratos

Contratos y adaptadores

El contrato es el acuerdo entre el núcleo y los plug-ins. Define:

  • el comportamiento esperado (qué operación se invoca),
  • los datos de entrada que envía el núcleo, y
  • los datos de salida que devuelve el plug-in.

Suele ser estándar para todos los plug-ins de un mismo tipo, y se implementa como interfaces y objetos, o como XML o JSON si el acceso es remoto.

Contratos a medida → adaptador

Cuando un plug-in de terceros trae su propio contrato y no se puede modificar, se escribe un adaptador (patrón Adapter) que lo traduce al contrato estándar. El núcleo nunca se entera.

// Contrato estándar que define el núcleo
public record Dispositivo(string Modelo, int Antiguedad, bool PantallaRota);
public record Evaluacion(decimal Valor, string Detalle);

public interface IEvaluador
{
    Evaluacion Evaluar(Dispositivo d);
}

// Plug-in de un tercero, con OTRO contrato (no lo podemos cambiar)
public class CotizadorExterno
{
    public double Cotizar(string json) { /* … */ }
}

// Adaptador: traduce el contrato del tercero al estándar
public sealed class CotizadorExternoAdapter(CotizadorExterno ext) : IEvaluador
{
    public Evaluacion Evaluar(Dispositivo d)
    {
        var valor = ext.Cotizar(JsonSerializer.Serialize(d));
        return new((decimal)valor, "Cotizado por proveedor externo");
    }
}
Conceptos · Dónde se usa

Ejemplos de microkernel en el mundo real

Aplicaciones de producto

Eclipse, VS Code, IntelliJ: editor como núcleo; lenguajes, depuradores, temas y control de versiones como extensiones.

Navegadores (Chrome, Firefox): el visor de páginas es el núcleo; las extensiones agregan funciones.

Jenkins: núcleo de integración continua; cada herramienta (Git, Maven, Docker) llega como plug-in.

Jira, PMD: núcleo de gestión o análisis con reglas y funciones extensibles.

Aplicaciones de negocio

Procesamiento de siniestros de seguros: el flujo de un reclamo es igual en todos lados, pero las reglas cambian según la jurisdicción. Cada jurisdicción es un plug-in; agregar una no toca el núcleo.

Software de declaración de impuestos: el núcleo maneja el formulario principal y el cálculo general; cada formulario anexo o regla particular es un plug-in que se activa si corresponde.

El patrón común: un proceso general estable y muchas variantes o extensiones que cambian a otro ritmo.

Cómo leer las características

Richards & Ford califican cada estilo de 1 a 5 estrellas en cada característica. Las estrellas son relativas entre estilos: 5 es lo mejor (en costo, 5 = más barato). Para justificar un estilo, se buscan muchas estrellas en las características que son drivers del caso.

Simplicidad

Qué tan fácil es entenderlo y construirlo.

Modularidad

Cuánto se divide en partes independientes.

Testeabilidad

Facilidad para probar el todo y las partes.

Evolutividad

Facilidad para incorporar cambios y funcionalidades nuevas.

Facilidad de despliegue

Qué tan fácil y seguro es desplegar un cambio.

Confiabilidad

Que funcione correctamente de forma consistente.

Rendimiento

Tiempo de respuesta y capacidad de procesamiento.

Escalabilidad

Crecer en usuarios o carga sostenida.

Elasticidad

Responder a picos repentinos de carga.

Tolerancia a fallos

Seguir funcionando si falla una parte.

Conceptos · Criterio de elección

Cuándo usar microkernel y cuándo no

Conviene cuando…
  • Es un producto que se instala y se configura distinto según el cliente
  • Hay un proceso general estable y muchas variantes (reglas, modelos, países)
  • Se necesita que terceros puedan extender el sistema
  • Se quiere agregar funcionalidad sin tocar ni redesplegar el núcleo
  • El presupuesto y el equipo piden un estilo simple y barato
No conviene cuando…
  • Se necesita alta escalabilidad o elasticidad (muchos usuarios, picos de carga)
  • Una falla no puede afectar al resto: tolerancia a fallos alta
  • No se puede separar un núcleo de sus variantes: todo es "núcleo"
  • Los plug-ins necesitarían comunicarse mucho entre sí
  • El contrato cambia todo el tiempo y rompería los plug-ins

Conceptos · Plug-ins en tiempo de ejecución

Carga y descarga dinámica

Para agregar un plug-in sin reiniciar, el núcleo carga su código mientras se está ejecutando, y para quitarlo lo descarga de memoria.

Cada plug-in se carga en un contexto aislado: en Java, un ClassLoader propio (u OSGi, que gestiona todo el ciclo de vida); en .NET, un AssemblyLoadContext "coleccionable", que se puede descargar.

CICLO DE VIDA (inspirado en OSGi)
Instalado Resuelto Activo Detenido Desinstalado

Resuelto significa que se verificó que sus dependencias (por ejemplo, la versión de la API del núcleo) están disponibles.

// .NET 8: cargar un plug-in en un contexto aislado
var ctx = new AssemblyLoadContext("lang-python", isCollectible: true);
var asm = ctx.LoadFromAssemblyPath(rutaDll);

// buscar la clase de entrada que implementa el contrato
var tipo = asm.GetTypes()
              .First(t => typeof(IPlugin).IsAssignableFrom(t));
var plugin = (IPlugin)Activator.CreateInstance(tipo)!;

plugin.Activate(core);           // pasa a "Activo"
registro.Registrar(plugin);

// descarga dinámica
plugin.Deactivate();
registro.Quitar(plugin.Id);
ctx.Unload();                    // libera el código de memoria
Conceptos · Compatibilidad entre versiones

Versionado semántico y compatibilidad

Con versionado semántico (SemVer), el número de versión MAYOR.MENOR.PARCHE comunica qué tipo de cambio hubo:

MAYORCambios incompatibles en el contrato: los plug-ins viejos pueden romperse.
MENORFuncionalidad nueva compatible hacia atrás.
PARCHECorrecciones compatibles.

Cada plug-in declara qué versión de la API del núcleo necesita, por ejemplo >=2.3.0 <3.0.0: "cualquier 2.x desde la 2.3". Antes de activarlo, el núcleo lo verifica. Para no romper plug-ins viejos al subir de versión mayor, el núcleo puede mantener el contrato anterior con un adaptador.

PROBALO

El plug-in lang-python 1.4.0 requiere la API del núcleo >=2.3.0 <3.0.0. ¿Con qué versión del núcleo funciona?

Conceptos · Catálogo firmado

Firma digital de paquetes

Un plug-in es código de terceros que va a correr dentro del IDE. La firma digital permite comprobar quién lo publicó y que nadie lo modificó en el camino.

El publicador
  1. Calcula el hash del paquete (por ejemplo, SHA-256): una "huella" que cambia si cambia un solo byte.
  2. Firma ese hash con su clave privada, que solo él tiene. El resultado es el archivo .sig.
  3. Publica .plugin + .sig en el catálogo.
El IDE
  1. Descarga el paquete y la firma.
  2. Recalcula el hash del paquete.
  3. Verifica la firma con la clave pública confiable del publicador. Si no coincide, el plug-in se rechaza.

Garantiza: integridad (no fue alterado) y autenticidad (viene de quien dice).

No garantiza que el código sea bueno o seguro: solo quién lo firmó. Por eso el catálogo además revisa lo que publica.

Conceptos · Facilidad de testeo

Testear aislando componentes

Como cada plug-in solo depende del contrato, se puede probar sin el sistema completo, reemplazando al núcleo por un doble de prueba.

  • Stub: devuelve respuestas fijas.
  • Fake: implementación simple que funciona de verdad (por ejemplo, en memoria).
  • Mock: verifica que se lo llamó como se esperaba.

Y al revés: el núcleo se prueba con plug-ins falsos, sin depender de ningún lenguaje real.

Pruebas de contrato: un conjunto de tests que todo plug-in de un tipo debe pasar. Si un plug-in nuevo los pasa, cumple el contrato y el núcleo lo puede usar.

// xUnit: el linter se prueba sin abrir el IDE
public sealed class FakeCore : ICoreApi
{
    public List<string> Salida { get; } = new();
    // … resto de ICoreApi con implementaciones mínimas
}

public class LongLineLinterTests
{
    [Fact]
    public void Analyze_LineaDe100Caracteres_DevuelveUnaAdvertencia()
    {
        var linter = new LongLineLinter(maxLength: 80);
        linter.Activate(new FakeCore());

        var diags = linter.Analyze(new SourceFile("a.py", new string('x', 100)));

        Assert.Single(diags);
    }
}

Conceptos · Lectura de un diagrama

Cómo se lee un diagrama de despliegue

Ejemplo genérico: una aplicación de escritorio que usa un motor de base de datos en otro equipo.

  1. Anidamiento = despliegue. Lo que está dentro de un nodo está desplegado en él: app.exe corre en .NET 8, que corre en Windows, que corre en la notebook.
  2. Cada línea entre nodos es una comunicación por red, con su protocolo. Si dos piezas están en el mismo nodo y proceso, se llaman localmente.
  3. La multiplicidad (*, 1) dice cuántas instancias participan: muchas notebooks, un servidor.
  4. "Distribuir" es poner componentes en nodos distintos conectados por red. Un estilo monolítico tiene su aplicación en un solo ambiente de ejecución.

Los contratos de extensión (C#)

// Contratos publicados por el núcleo (IdeCore.Contracts.dll)
public interface IPlugin {
    string Id { get; }               // "lang-python"
    Version Version { get; }          // 1.4.0
    Version RequiredCoreApi { get; }  // compatibilidad
    void Activate(ICoreApi core);
    void Deactivate();
}
public interface ILanguagePlugin : IPlugin {
    IReadOnlyList<string> Extensions { get; } // [".py"]
    BuildResult Build(SourceFile file);
    RunHandle Run(BuildResult build, RunOptions opts);
}
public interface ILinterPlugin : IPlugin {
    IEnumerable<Diagnostic> Analyze(SourceFile file);
}
public interface IDebuggerPlugin : IPlugin {
    DebugSession Start(BuildResult build, IEnumerable<Breakpoint> bps);
}
// API que el núcleo expone a los plug-ins
public interface ICoreApi {
    IEditor Editor { get; }  IOutput Output { get; }  IEventBus Events { get; }
}
El núcleo no conoce a Python ni a Java

Solo conoce ILanguagePlugin. Sumar un lenguaje no toca el núcleo: extensibilidad sin modificar (OCP a nivel de arquitectura).

Compatibilidad entre versiones

RequiredCoreApi + versionado semántico: el núcleo rechaza plug-ins de una API mayor incompatible y mantiene contratos viejos con adaptadores.

Testeo aislado

Cada plug-in se prueba contra un ICoreApi simulado (mock), sin el IDE completo ni otros plug-ins.

5

Activar

SIMULADOR

Recorré los pasos. Probá también un plug-in sin firma válida.

Descarga dinámica: Deactivate(), se quita del registro y se descarga el contexto. El núcleo sigue funcionando.

Resolución · Parte 1 · Trade-offs

Fortalezas y debilidades

Los mismos puntajes que vimos en los conceptos, ahora marcando cuáles son drivers del caso del IDE.

Lo que gana

Bajo costo y simplicidad alta (sigue siendo un monolito), con modularidad, testeabilidad y evolutividad mejores que en Layered, justamente gracias a los plug-ins.

Lo que pierde

Escalabilidad, elasticidad y tolerancia a fallos bajas. En un IDE que corre en la PC del estudiante, con un solo usuario, no son prioridad.

Resolución · Parte 1 · Riesgos

Riesgos del estilo y cómo mitigarlos

Un plug-in tira todo

En el mismo proceso, una excepción o un bucle infinito de un plug-in puede colgar el IDE.

Mitigación: capturar errores en el límite del contrato, timeouts y correr el programa del estudiante en un proceso aparte.

Contratos que cambian

Un cambio en el contrato rompe todos los plug-ins publicados.

Mitigación: versionado semántico, deprecación gradual y adaptadores.

Código de terceros

Un plug-in malicioso corre con los permisos del IDE.

Mitigación: catálogo firmado, verificación en la instalación y permisos declarados por plug-in.

Núcleo que engorda

La tentación de meter funciones "comunes" en el núcleo lo vuelve inestable.

Mitigación: regla de oro: si no es imprescindible para editar y ejecutar, va a un plug-in.

Resolución · Parte 1 · Respuesta modelo

Cómo lo redactaríamos

El estilo microkernel es el más adecuado porque el problema ya está planteado en sus términos: un núcleo que provee edición y ejecución, y lenguajes y herramientas como plug-ins. Es el estilo típico de las aplicaciones basadas en productos que se instalan en la máquina del usuario, como los IDE.

La restricción de un núcleo estable con contratos de extensión se cumple con el «core» mínimo que publica interfaces (ILanguagePlugin, ILinterPlugin, IDebuggerPlugin) y una API para compilar y ejecutar. El registro de plug-ins permite la carga y descarga dinámica y el despliegue en runtime sin modificar ni redesplegar el núcleo. Como cada plug-in es un artefacto independiente con versión propia, se puede publicar en un catálogo versionado y firmado.

Satisface los no funcionales: extensibilidad y modularidad, porque sumar un lenguaje es sumar un plug-in independiente; testeo aislado, porque cada plug-in se prueba contra el contrato con un núcleo simulado; y compatibilidad entre versiones, mediante contratos versionados y adaptadores.

Sus debilidades —baja escalabilidad, elasticidad y tolerancia a fallos— son aceptables en un IDE que corre localmente para un usuario. El riesgo de que un plug-in afecte al núcleo se mitiga con validación de firmas y aislando la ejecución del código del estudiante.

Resolución · Parte 2 · ¿Qué se distribuye y qué no?

Lectura del diagrama

ElementoEstereotipoQué representa
PC del estudiante«device»Donde se instala el IDE (aplicación de producto, en el sitio del cliente).
Runtime del IDE (.NET 8)«executionEnvironment»Un único proceso donde corren el núcleo y todos los plug-ins. Núcleo y plug-ins NO se distribuyen.
ide-core«artifact» «core»Editor, Execution API, PluginManager, registro y contratos.
lang-python, lang-java, linter, debugger«artifact» «plugin»Artefactos separados, versionados, que se despliegan y retiran en runtime.
plugins.lock.json · trust.pem«deploymentSpec»Qué plug-ins y versiones están activos, y la clave para verificar firmas.
Toolchains locales«executionEnvironment»Intérpretes y compiladores que invocan los plug-ins de lenguaje en un proceso aparte (aísla el código del estudiante).
Servidor del catálogo«device»Lo único remoto. Publica los .plugin firmados y su índice de versiones. Se usa al instalar o actualizar, no para ejecutar.

@startuml
' UT5 TA2 - IDE educativo - Microkernel
node "PC del estudiante" <<device>> as pc {
  node "Windows / Linux / macOS" <<executionEnvironment>> as os {
    node "Runtime del IDE (.NET 8)" <<executionEnvironment>> as rt {
      artifact "ide-core" <<core>> as core
      artifact "lang-python 1.4.0" <<plugin>> as pPy
      artifact "lang-java 2.1.0" <<plugin>> as pJava
      artifact "linter 0.9.2" <<plugin>> as pLint
      artifact "debugger 1.2.0" <<plugin>> as pDbg
      artifact "plugins.lock.json" <<deploymentSpec>> as lock
      artifact "trust.pem" <<deploymentSpec>> as trust
    }
    node "Toolchains locales" <<executionEnvironment>> as tc {
      artifact "python 3.12" as py
      artifact "JDK 21" as jdk
    }
  }
}
node "Servidor del catálogo" <<device>> as cat {
  node "Servidor web + API" <<executionEnvironment>> as web {
    artifact "catalog-api" as api
  }
  node "Almacenamiento" <<executionEnvironment>> as store {
    artifact "*.plugin + *.sig" as pkgs
    artifact "index.json" <<deploymentSpec>> as idx
  }
}
