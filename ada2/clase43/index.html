Conceptos · Teórico 2.7.3 + Richards & Ford

Estilo microkernel (micronúcleo)

Estilo monolítico adecuado para aplicaciones basadas en productos: empaquetadas, disponibles para descargar e instalar como una única implementación, generalmente en el sitio del cliente.
Núcleo «core»

Funcionalidad mínima para que el sistema funcione. Debe ser estable y cambiar poco.

Plug-ins «plugin»

Componentes independientes que agregan o especializan funcionalidad. No dependen entre sí.

Registro

El núcleo sabe qué plug-ins hay, su nombre, versión, contrato y cómo acceder a ellos.

Contratos

Interfaz estándar entre núcleo y plug-in: datos de entrada, salida y formato. Si cambian, se rompen los plug-ins.

EJEMPLOS CONOCIDOS

Eclipse, VS Code, IntelliJ: editor base y extensiones de lenguaje, linters y depuradores. ← nuestro caso

Navegadores: el visor más las extensiones.

Jenkins: núcleo de CI y plug-ins para cada herramienta.

Conceptos · Características de arquitectura

Cómo leer las características

Richards & Ford califican cada estilo de 1 a 5 estrellas en cada característica. Las estrellas son relativas entre estilos: 5 es lo mejor (en costo, 5 = más barato). Para justificar un estilo, se buscan muchas estrellas en las características que son drivers del caso.

Costo total

Desarrollo, infraestructura y operación.

Simplicidad

Qué tan fácil es entenderlo y construirlo.

Modularidad

Cuánto se divide en partes independientes.

Testeabilidad

Facilidad para probar el todo y las partes.

Evolutividad

Facilidad para incorporar cambios y funcionalidades nuevas.

Facilidad de despliegue

Qué tan fácil y seguro es desplegar un cambio.

Confiabilidad

Que funcione correctamente de forma consistente.

Rendimiento

Tiempo de respuesta y capacidad de procesamiento.

Escalabilidad

Crecer en usuarios o carga sostenida.

Elasticidad

Responder a picos repentinos de carga.

Tolerancia a fallos

Seguir funcionando si falla una parte.

Conceptos · Teórico 2.7

Los estilos de arquitectura de un vistazo

Para descartar alternativas hay que conocerlas. Una línea por estilo, según el teórico de ANDIS.

Monolíticos una unidad de despliegue

Layered: capas lógicas con roles definidos; cada capa usa la inmediata inferior.

Pipes & Filters: filtros independientes que transforman datos, conectados por tuberías, de la entrada a la salida.

Microkernel: núcleo mínimo más plug-ins; típico de aplicaciones de producto instaladas en el cliente.

Distribuidos ojo con las falacias de la computación distribuida

Service-Based: pocos servicios de dominio; distribuido pero sin el costo y la complejidad de microservicios o eventos.

Event-Driven: componentes independientes que procesan eventos de forma asíncrona; alta escalabilidad y rendimiento.

Space-Based: datos replicados en memoria entre unidades de procesamiento que se inician y detienen según la carga.

Orchestration-Driven SOA: servicios empresariales coordinados por un motor de orquestación; nació en grandes corporaciones de fines de los 90.

Microservicios: cada servicio es una unidad separada con su propia base de datos, comunicado por API livianas.

Conceptos · Teórico 2.3.4

Diagrama de despliegue UML: elementos

Modela la arquitectura física: nodos, los artefactos desplegados en ellos y las rutas de comunicación.

«node» / «device»

Recurso computacional. «device» es hardware: servidor, PC, móvil.

«executionEnvironment»

Nodo de software que aloja artefactos: SO, runtime, servidor web, SGBD.

«artifact»

Elemento físico desplegado: ejecutable, paquete, script, esquema.

«deploymentSpec»

Archivo de configuración de un artefacto.

ruta de comunicación

Asociación entre nodos, con protocolo (HTTPS, TCP/IP) y multiplicidad.

«deploy» / «manifest»

«deploy»: el nodo soporta el artefacto (o se dibuja contenido). «manifest»: el artefacto materializa un componente.

En microkernel, el teórico usa los estereotipos «core» para el núcleo y «plugin» para los complementos; los vamos a usar sobre los artefactos.

Resolución · Parte 1 · Núcleo estable con contratos

Los contratos de extensión (C#)

// Contratos publicados por el núcleo (IdeCore.Contracts.dll)
public interface IPlugin {
    string Id { get; }               // "lang-python"
    Version Version { get; }          // 1.4.0
    Version RequiredCoreApi { get; }  // compatibilidad
    void Activate(ICoreApi core);
    void Deactivate();
}
public interface ILanguagePlugin : IPlugin {
    IReadOnlyList<string> Extensions { get; } // [".py"]
    BuildResult Build(SourceFile file);
    RunHandle Run(BuildResult build, RunOptions opts);
}
public interface ILinterPlugin : IPlugin {
    IEnumerable<Diagnostic> Analyze(SourceFile file);
}
public interface IDebuggerPlugin : IPlugin {
    DebugSession Start(BuildResult build, IEnumerable<Breakpoint> bps);
}
// API que el núcleo expone a los plug-ins
public interface ICoreApi {
    IEditor Editor { get; }  IOutput Output { get; }  IEventBus Events { get; }
}
El núcleo no conoce a Python ni a Java

Solo conoce ILanguagePlugin. Sumar un lenguaje no toca el núcleo: extensibilidad sin modificar (OCP a nivel de arquitectura).

Compatibilidad entre versiones

RequiredCoreApi + versionado semántico: el núcleo rechaza plug-ins de una API mayor incompatible y mantiene contratos viejos con adaptadores.

Testeo aislado

Cada plug-in se prueba contra un ICoreApi simulado (mock), sin el IDE completo ni otros plug-ins.

Resolución · Parte 1 · Catálogo firmado + despliegue en runtime

Instalar un plug-in con el IDE abierto

1
Descubrir
El PluginManager consulta el catálogo remoto por HTTPS y lista versiones disponibles.
2
Descargar
Baja lang-python-1.4.0.plugin y su firma .sig.
3
Verificar firma
Valida la firma con la clave pública confiable del núcleo. Si falla, se rechaza.
4
Chequear compatibilidad
Compara RequiredCoreApi con la versión de la API del núcleo.
5
Cargar y registrar
Carga el ensamblado en un contexto aislado y lo anota en el registro.
6
Activar
Activate(core): el editor ya reconoce archivos .py. Sin reiniciar.
SIMULADOR

Recorré los pasos. Probá también un plug-in sin firma válida.

Descarga dinámica: Deactivate(), se quita del registro y se descarga el contexto. El núcleo sigue funcionando.

Resolución · Parte 1 · Trade-offs

Fortalezas y debilidades

Puntajes del estilo microkernel según Richards & Ford (2020). Se marcan los atributos que son drivers del caso.

Lo que gana

Bajo costo y simplicidad alta (sigue siendo un monolito), con modularidad, testeabilidad y evolutividad mejores que en Layered, justamente gracias a los plug-ins.

Lo que pierde

Escalabilidad, elasticidad y tolerancia a fallos bajas. En un IDE que corre en la PC del estudiante, con un solo usuario, no son prioridad.

Resolución · Parte 1 · Riesgos

Riesgos del estilo y cómo mitigarlos

Un plug-in tira todo

En el mismo proceso, una excepción o un bucle infinito de un plug-in puede colgar el IDE.

Mitigación: capturar errores en el límite del contrato, timeouts y correr el programa del estudiante en un proceso aparte.

Contratos que cambian

Un cambio en el contrato rompe todos los plug-ins publicados.

Mitigación: versionado semántico, deprecación gradual y adaptadores.

Código de terceros

Un plug-in malicioso corre con los permisos del IDE.

Mitigación: catálogo firmado, verificación en la instalación y permisos declarados por plug-in.

Núcleo que engorda

La tentación de meter funciones "comunes" en el núcleo lo vuelve inestable.

Mitigación: regla de oro: si no es imprescindible para editar y ejecutar, va a un plug-in.

Resolución · Parte 1 · Respuesta modelo

Cómo lo redactaríamos

El estilo microkernel es el más adecuado porque el problema ya está planteado en sus términos: un núcleo que provee edición y ejecución, y lenguajes y herramientas como plug-ins. Es el estilo típico de las aplicaciones basadas en productos que se instalan en la máquina del usuario, como los IDE.

La restricción de un núcleo estable con contratos de extensión se cumple con el «core» mínimo que publica interfaces (ILanguagePlugin, ILinterPlugin, IDebuggerPlugin) y una API para compilar y ejecutar. El registro de plug-ins permite la carga y descarga dinámica y el despliegue en runtime sin modificar ni redesplegar el núcleo. Como cada plug-in es un artefacto independiente con versión propia, se puede publicar en un catálogo versionado y firmado.

Satisface los no funcionales: extensibilidad y modularidad, porque sumar un lenguaje es sumar un plug-in independiente; testeo aislado, porque cada plug-in se prueba contra el contrato con un núcleo simulado; y compatibilidad entre versiones, mediante contratos versionados y adaptadores.

Sus debilidades —baja escalabilidad, elasticidad y tolerancia a fallos— son aceptables en un IDE que corre localmente para un usuario. El riesgo de que un plug-in afecte al núcleo se mitiga con validación de firmas y aislando la ejecución del código del estudiante.

Lectura del diagrama

ElementoEstereotipoQué representa
PC del estudiante«device»Donde se instala el IDE (aplicación de producto, en el sitio del cliente).
Runtime del IDE (.NET 8)«executionEnvironment»Un único proceso donde corren el núcleo y todos los plug-ins. Núcleo y plug-ins NO se distribuyen.
