Fundamentos

¿Qué es un Diagrama de Secuencia?

El diagrama de comportamiento más utilizado en UML para modelar interacciones.

Definición

Un diagrama de secuencia muestra cómo los objetos o actores interactúan entre sí a lo largo del tiempo, a través del intercambio de mensajes.

Eje vertical = tiempo. Los mensajes bajan de arriba a abajo. Lo que ocurre primero está arriba.
Eje horizontal = participantes. Cada columna representa un actor o sistema.
Elementos principales
Actor / Participante
Entidad que interviene en la interacción. Se representa con un rectángulo en la parte superior y una línea de vida (lifeline) vertical.
Línea de vida
Línea vertical punteada que representa la existencia del objeto en el tiempo. Empieza con el objeto activo y termina cuando muere.
Mensaje
Comunicación entre participantes. Puede ser síncrono (flecha sólida ─▶) o asíncrono. Los retornos usan línea punteada (─ ─▷).
Activación
Rectángulo estrecho sobre la lifeline. Indica el período en que el objeto está procesando (tiene control de ejecución).
Fragmento combinado
alt (alternativas), loop (repetición), opt (opcional), ref (referencia). Modelan control de flujo.
Orden temporal
A diferencia de otros diagramas, el tiempo importa: el mensaje más alto ocurre antes. Los diagramas se leen de arriba a abajo.
Mensajes y Fragmentos

Tipos de Mensajes y Fragmentos Combinados

Los bloques fundamentales para construir diagramas de secuencia expresivos.

Tipos de Mensajes
──▶
Llamada síncrona
El emisor espera la respuesta antes de continuar. Es el más común. Ej: Cliente->>Sistema: seleccionarVuelo()
- -▷
Retorno / Respuesta
Devuelve el control al llamador. Línea punteada con flecha abierta. Ej: Sistema-->>Cliente: resultado
─ ─▶
Mensaje asíncrono
El emisor no espera respuesta. Típico en sistemas de eventos y notificaciones. Ej: Sistema de notificaciones.
──▶ (self)
Auto-mensaje
Un participante se envía un mensaje a sí mismo. Modela procesamiento interno. Ej: SRV->>SRV: verificarDisp()
Fragmentos Combinados
alt

Alternativa — equivale a if / else. Separa flujos mutuamente excluyentes con [condición]. Usado en el Ej.1 para transacción aprobada vs rechazada.

loop

Bucle — equivale a while / for. Se repite mientras se cumpla la condición. Ej: loop [mientras quede stock].

opt

Opcional — bloque que sólo ocurre si se cumple una condición (sin rama else). Equivale a if sin else.

ref

Referencia — delega a otro diagrama de secuencia. Permite modularizar diagramas complejos.

Diferencia con Diagrama de Clases
Diagrama de Clases → estructura estática. Modela qué existe en el sistema: clases, atributos, métodos y relaciones. No muestra tiempo.
Diagrama de Secuencia → comportamiento dinámico. Modela cómo interactúan los objetos en un escenario específico a lo largo del tiempo.
Ejercicio 1

Sistema de Reservas de Vuelos

Interacción entre Cliente, Sistema de Reservas, Sistema de Pago y Sistema de Notificaciones.

Actores
Cliente
Sistema de Reservas de Vuelos
Sistema de Pago
Sistema de Notificaciones
Flujo de Pasos
1
El Cliente selecciona un vuelo y proporciona info personal y de pago al SRV
2
El SRV verifica disponibilidad y envía solicitud de reserva al cliente
3
El Cliente confirma la reserva
4
El SRV solicita inicio del proceso de pago al SP, indicando la URL de callback
5
El SP devuelve una WebApi donde el usuario completa la tarjeta
6
El SP procesa el pago y devuelve resultado (aprobado o rechazado) al SRV
7
El SP devuelve control al SRV via redirect al callback
8
[Aprobado] El SRV confirma reserva y solicita notificación al SN
9
El SN envía notificación al cliente sobre estado de reserva y pago
10
[Rechazado] El SRV informa al cliente y solicita otra forma de pago o cancelación

Fragmento alt
El resultado del pago tiene dos caminos: aprobado o rechazado. Se modela con alt, el equivalente a un if/else en el diagrama.
Patrón Callback
El Sistema de Pago opera de forma semi-independiente (WebApi externa) y retorna el control al SRV vía redirect a URL de callback. Patrón común en integraciones de pago.
Desacoplamiento
El Sistema de Notificaciones es un actor separado. El SRV delega el envío de mensajes al cliente: bajo acoplamiento y alta cohesión.
Mensajes síncronos
La mayoría de los mensajes son síncronos (─▶): el emisor espera la respuesta. Los retornos usan flecha punteada (──).

Sistema Gestión de Perfiles
Sistema de Recomendaciones

El Usuario se registra en el SS con su información personal

Notas / Notes
Se puede usar Note over A,B para agrupar pasos en fases: "Registro" y "Login+Recomendaciones". Clarifica el flujo sin agregar actores.
Auto-mensaje interno
Pasos 2, 3 y 8: el sistema se envía mensajes a sí mismo (SS->>SS, SR->>SR) para modelar procesamiento interno sin intervención externa.
Arquitectura de Microservicios
SGP y SR son sistemas independientes. El SS orquesta la comunicación. Este patrón refleja una arquitectura orientada a servicios.
Motor de Recomendaciones
El SR encapsula la lógica de análisis del perfil. El SS no sabe cómo funciona: solo envía el perfil y recibe la lista. Encapsulamiento entre sistemas.

Patrón similar al Ej.2
Los pasos 1–6 son idénticos al sistema de Streaming. Esto refleja un patrón de arquitectura reutilizable: registro → perfil → login. Reconocer patrones ahorra modelado.
Persistencia delegada
El SRSC delega la persistencia de recetas al SGR. El sistema principal no guarda datos directamente: responsabilidad única (SRP).
Confirmación explícita
El paso 10 modela la confirmación de guardado. Es buena práctica en UML incluir los retornos de confirmación para mostrar que la operación fue exitosa.
Difusión social (broadcast)
El paso 11 ("comparte con seguidores") podría expandirse con un fragmento loop sobre cada seguidor, o con un mensaje asíncrono a un sistema de feed.

Chatbot como Mediador
El Chatbot centraliza todas las interacciones. El usuario nunca habla directamente con BDR o Maps. Patrón Mediator/Facade.
Integración con API externa
La API de Google Maps es un sistema externo. El chatbot adapta la respuesta al formato de WhatsApp (paso 13). Patrón Adapter.
Datos contextuales
La ubicación del usuario es un dato contextual esencial. El chatbot la solicita explícitamente (paso 4) antes de consultar la BD.
Dos fases bien delimitadas
Se pueden identificar dos subflujos: búsqueda de restaurantes y obtención de ruta. Cada uno podría modelarse en un ref separado para mayor claridad.

Buenas Prácticas

Incluir siempre los mensajes de retorno (─ ─▷) cuando la respuesta tiene información relevante

Comparativa

Diagrama de Clases vs Diagrama de Secuencia

Cuándo usar cada uno, cómo se complementan y qué modela cada tipo de diagrama UML.

Diagrama de Clases (TA5)
Modela la estructura estática del sistema.
¿Qué entidades existen en el sistema?
¿Qué atributos y métodos tienen las clases?
¿Cómo se relacionan las clases entre sí? (herencia, composición…)
Responde: "¿Qué hay en el sistema?"
NO muestra el orden temporal de los mensajes
Se usa en la fase de diseño de la arquitectura del sistema.
Diagrama de Secuencia (TA6)
Modela el comportamiento dinámico del sistema.
¿En qué orden ocurren las interacciones?
¿Qué mensajes se intercambian entre actores?
¿Cuándo ocurre cada evento en el tiempo?
Responde: "¿Cómo y cuándo pasa?"
NO muestra atributos ni herencia entre clases
Se usa para modelar casos de uso y validar la lógica de negocio.
¿Cuándo se usan juntos?

En un proyecto real, ambos diagramas son complementarios. El Diagrama de Clases define el vocabulario del sistema (las entidades), y el Diagrama de Secuencia define cómo esas entidades colaboran para realizar un caso de uso. Los métodos que aparecen en los mensajes del diagrama de secuencia (procesarPago(), obtenerPerfil()) deben existir como operaciones en las clases del diagrama de clases.
