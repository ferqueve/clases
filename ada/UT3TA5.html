Fundamentos

¿Qué es un Diagrama de Clases?

El diagrama más utilizado en UML para modelar la estructura estática de un sistema.

Definición

Un diagrama de clases es un tipo de diagrama estructural en UML que describe la estructura de un sistema mostrando sus clases, atributos, operaciones y las relaciones entre los objetos.

¿Para qué sirve? Representar el "plano" del software: qué entidades existen y cómo se relacionan entre sí.
Usos principales
Modelar el dominio del problema (análisis)
Diseñar la arquitectura de clases (diseño)
Generar código esqueleto (forward engineering)
Documentar código existente (reverse engineering)
Comunicar diseño entre equipo de desarrollo
Estructura de una Clase en UML
<<clase>>NombreClase
– atribPrivado : Tipo
# atribProtegido : Tipo
+ atribPublico : Tipo
+ metodoPublico() : void
– metodoPriv() : bool
Nombre de clase

Identificador único. Por convención: PascalCase. Aparece en el compartimento superior.

Atributos

Compartimento medio. Formato: visibilidad nombre : Tipo

Operaciones

Compartimento inferior. Métodos y comportamientos de la clase.

Visibilidad

+ público   – privado   # protegido

Relaciones

Tipos de Relaciones entre Clases

Las relaciones definen cómo las clases se conectan y dependen entre sí.

Herencia (Generalización)
Una clase hija hereda atributos y métodos de una clase padre. Notación: flecha con triángulo hueco ──▷. Ej: Administrador hereda de Empleado
Realización (Interfaz)
Una clase implementa los métodos definidos en una interfaz. Notación: flecha de línea punteada con triángulo hueco - - ▷. Ej: TarjetaCredito implementa MedioPago
Asociación
Relación estructural entre dos clases. Ambas pueden existir de forma independiente. Notación: línea sólida ──. Se incluye multiplicidad. Ej: Estudiante se inscribe en Curso
Agregación
Relación "tiene un" débil. La parte puede existir sin el todo. Notación: rombo hueco en el todo ◇──. Ej: Universidad agrega Profesores (el profesor puede existir sin la universidad)
Composición
Relación "parte de" fuerte. La parte NO puede existir sin el todo. Notación: rombo sólido ◆──. Ej: Cuenta contiene Transacciones (la transacción no existe sin la cuenta)
Dependencia
Relación débil y temporal. Una clase usa a otra pero no la contiene. Notación: flecha punteada - - →. Ej: EmpleadoAdmin usa temporalmente un Informe
Multiplicidad – Cardinalidad
1 exactamente uno 0..1 cero o uno 1..* uno o muchos 0..* cero o muchos * muchos (sin límite) 3..5 entre 3 y 5
Ejercicio 1

Sistema de Gestión de Biblioteca

Modelado de una biblioteca con libros, autores, miembros, préstamos y empleados.

Análisis de Requisitos
La biblioteca tiene varios Libros, cada uno con múltiples Autores
Los libros se clasifican en distintos Géneros (Ficción, No Ficción, etc.)
Los libros pueden ser prestados a Miembros. Un miembro tiene un límite máximo de préstamos
El Préstamo registra la relación entre miembro y libro con fechas
Los Empleados gestionan préstamos y devoluciones
Los Administradores son empleados con privilegios adicionales para agregar/eliminar libros
Clases Identificadas
Libro Autor Género Miembro Préstamo Empleado Administrador
Relaciones Clave
Administrador → Empleado Libro ↔ Autor (muchos a muchos) Libro → Género Miembro → Préstamo Préstamo → Libro Empleado → Préstamo

Herencia
Administrador extiende Empleado. Hereda todos sus atributos y métodos, y agrega capacidades adicionales de gestión del sistema.
Asociación M:M
Un Libro puede tener múltiples Autores y un autor puede haber escrito múltiples libros → relación muchos a muchos.
Clase Asociativa
Préstamo actúa como clase asociativa: materializa la relación entre Miembro y Libro, agregando atributos propios (fechas, estado).
Multiplicidad
Un Miembro puede tener entre 0 y maxPrestamos libros prestados. Esta restricción se modela en la relación Miembro → Préstamo.
Ejercicio 2

Sistema de Gestión de Universidad

Departamentos, cursos, módulos, docentes y estudiantes bajo una jerarquía de herencia.

Análisis de Requisitos
La universidad tiene varios Departamentos (CS, Matemáticas, etc.)
Cada departamento ofrece múltiples Cursos
Un Profesor imparte el curso; múltiples Estudiantes se inscriben
Profesores y Estudiantes son subtipos de Persona
Los cursos se componen de Módulos con temas y recursos (slides, lecturas)
Los Empleados administrativos gestionan inscripciones
Clases Identificadas
Persona Profesor Estudiante Departamento Curso Módulo EmplAdmin
Relaciones Clave
Profesor → Persona Estudiante → Persona Depto ◆→ Cursos Curso ◆→ Módulos Estudiante ↔ Curso (M:M) Profesor → Curso (1:N)

Jerarquía de Herencia
Persona es la clase base (abstracta). Profesor y Estudiante heredan sus atributos comunes y agregan los propios de su rol.
Composición
Departamento ◆→ Curso y Curso ◆→ Módulo: composición. Si se elimina el curso, los módulos dejan de existir.
Relación M:M
Un Estudiante puede inscribirse en muchos cursos y un Curso tiene muchos estudiantes. En implementación se usa tabla intermedia (Inscripción).
Atributo Multivalorado
Módulo.recursos puede representarse como multivalorado o con una clase separada Recurso si necesitamos tipificar (presentación, lectura, video).
Ejercicio 3

Sistema de Gestión de Barberías

Cadena de sucursales con barberos, servicios por pasos, citas y gerentes.

Análisis de Requisitos
La cadena tiene varias Sucursales
Cada sucursal tiene múltiples Barberos
Los barberos ofrecen Servicios (corte, afeitado, barba)
Los servicios se componen de Pasos (proceso + productos)
Los Clientes reservan Citas con un barbero, en una sucursal, para un servicio
Cada sucursal tiene un Gerente (que es un barbero con rol especial)
Clases Identificadas
Sucursal Barbero Gerente Servicio Paso Cliente Cita
Relaciones Clave
Gerente → Barbero Sucursal ◇→ Barberos Servicio ◆→ Pasos Cliente → Cita (1:N) Cita → Barbero, Servicio, Sucursal

classDiagram direction LR class Sucursal { +String direccion +String telefono +String ciudad } class Barbero { +String nombre +String especialidad +atenderCliente() } class Gerente { +supervisar() +gestionarPersonal() } class Servicio { +String nombre +float precio +int duracionMin } class Paso { +int orden +String descripcion +String productos } class Cliente { +String nombre +String telefono +String email +reservarCita() } class Cita { +Date fecha +String hora +String estado +confirmar() +cancelar() } Gerente --|> Barbero Sucursal "1" o-- "1..*" Barbero : emplea Sucursal "1" -- "1" Gerente : dirigida por Barbero "1..*" -- "1..*" Servicio : ofrece Servicio "1" *-- "1..*" Paso Cliente "1" -- "0..*" Cita : reserva Cita -- Barbero Cita -- Servicio Cita -- Sucursal
Composición vs Agregación
Servicio ◆→ Paso: composición (un paso no existe sin su servicio). Sucursal ◇→ Barbero: agregación (el barbero puede trabajar en otra sucursal).
Herencia de Rol
Gerente hereda de Barbero: es un barbero con responsabilidades adicionales. Aplica el principio "is-a" de la OOP.
Clase Mediadora
Cita conecta Cliente, Barbero, Servicio y Sucursal. Es un ejemplo de clase que centraliza una interacción compleja entre múltiples entidades.
Restricción de Negocio
Un cliente solo puede tener una cita simultánea con el mismo barbero. Esta regla de negocio puede modelarse como restricción OCL o en el método reservarCita().
Ejercicio 4

Sistema de Gestión Bancario

Banco con departamentos, cuentas, transacciones, clientes y empleados administrativos.

Análisis de Requisitos
Banco: nombre, dirección, teléfono. Contiene departamentos.
Departamento: Banca Personal, Corporativa, Inversión. Ofrece cuentas.
Cuenta: número, saldo, tipo. Tiene composición con Transacciones.
Cliente: nombre, número ID, dirección. Tiene agregación con Cuentas.
Transacción: fecha, monto, tipo (depósito, retiro, transferencia).
EmpleadoAdministrativo: gestiona clientes y realiza transacciones.
Relaciones Especificadas
Cuenta ◆→ Transacción: composición. La transacción no existe sin la cuenta.
Cliente ◇→ Cuenta: agregación. El cliente existe aunque no tenga cuentas.
EmplAdmin ◇→ Cliente: agregación. Gestiona clientes pero no los posee.
EmplAdmin ◇→ Transacción: agregación. Realiza transacciones.
Banco ◇→ Departamento: agregación (los depto. podrían ser independientes).

classDiagram direction TB class Banco { +String nombre +String direccion +String telefono } class Departamento { +String nombre +String tipo } class Cuenta { +String numeroCuenta +float saldo +String tipoCuenta +depositar() +retirar() } class Cliente { +String nombre +String numeroId +String direccion +String email } class Transaccion { +Date fecha +float monto +String tipoTransaccion +String referencia } class EmpleadoAdministrativo { +String nombre +String cargo +abrirCuenta() +realizarTransaccion() +actualizarCliente() } Banco "1" o-- "1..*" Departamento Departamento "1" -- "1..*" Cuenta : ofrece Cliente "1" o-- "1..*" Cuenta : posee Cuenta "1" *-- "1..*" Transaccion EmpleadoAdministrativo "1" o-- "0..*" Cliente : gestiona EmpleadoAdministrativo "1" o-- "0..*" Transaccion : realiza
Composición Cuenta–Transacción
Una Transacción solo tiene sentido dentro de una Cuenta. Si la cuenta se elimina, las transacciones también. Ciclo de vida compartido.
Agregación Cliente–Cuenta
Un Cliente puede existir aunque cierre todas sus cuentas. Una cuenta también puede existir transitoriamente sin cliente activo. Ciclo de vida independiente.
Atributo Discriminador
Cuenta.tipoCuenta y Transaccion.tipoTransaccion son discriminadores. Podrían modelarse con herencia (CuentaAhorro, CuentaCorriente) si los comportamientos difieren.
Empleado como Agente
EmpleadoAdministrativo actúa como agente intermediario: gestiona entidades del sistema pero no las posee (agregación débil en ambas relaciones).
Ejercicio 5

Sistema de Tienda Online

E-commerce con productos, categorías, pedidos, medios de pago y promociones.

Análisis de Requisitos
Producto: nombre, descripción, precio, stock. Pertenece a una categoría.
Categoría: electrónica, hogar, moda, etc.
Los Clientes realizan Pedidos con número de seguimiento para rastreo.
Se puede pagar con Tarjeta de Crédito o PayPal (polimorfismo).
Las Promociones aplican descuentos a productos en fechas especiales.
El pedido tiene un estado de envío rastreable.
Clases Identificadas
Producto Categoria Cliente Pedido MedioPago TarjetaCredito PayPal Promocion
Patrón Clave
MedioPago (abstracta/interfaz)

TarjetaCredito y PayPal realizan la interfaz MedioPago. Esto permite polimorfismo: el Pedido no necesita saber qué medio de pago se usa.

Interfaz + Realización
MedioPago es una interfaz. TarjetaCredito y PayPal la realizan (→ línea punteada). Permite agregar nuevos medios de pago sin modificar Pedido (OCP).
Polimorfismo
pedido.pagar(medioPago) funciona sin conocer si es tarjeta o PayPal. El tipo concreto se resuelve en tiempo de ejecución. Esto es polimorfismo de subtipo.
Asociación Temporal
Promoción se asocia a Producto con vigencia temporal. En código esto requiere verificar estaVigente() antes de aplicar el descuento.
Línea de Pedido (Refinamiento)
La relación M:M entre Pedido y Producto puede refinarse con clase LineaPedido (cantidad, precioUnitario) para no perder contexto del momento de compra.
Ejercicio 6

Sistema de Software Factory

Empresa de desarrollo con equipos, programadores, proyectos por fases y clientes.

Análisis de Requisitos
La Empresa tiene varios Equipos de desarrollo
Cada equipo tiene varios Programadores con habilidades específicas
Los Proyectos se dividen en Fases (análisis, diseño, desarrollo, pruebas)
Los Clientes solicitan proyectos. Cada proyecto está asignado a un cliente.
El proyecto tiene nombre, descripción y fecha de inicio
El Personal Administrativo asigna proyectos, coordina recursos y hace seguimiento
Clases Identificadas
Empresa Equipo Programador Proyecto Fase Cliente EmplAdmin
Relaciones Clave
Empresa ◆→ Equipos Equipo ◇→ Programadores Proyecto ◆→ Fases Cliente → Proyecto (1:N) Equipo ↔ Proyecto (M:M)

Doble Composición
Empresa ◆→ Equipo: un equipo no existe fuera de la empresa. Proyecto ◆→ Fase: una fase no tiene sentido sin su proyecto.
Agregación Equipo–Programador
Un Programador puede reasignarse a otro equipo. El programador existe independientemente del equipo al que pertenece actualmente.
Asociación M:M Equipo–Proyecto
Un equipo puede trabajar en múltiples proyectos y un proyecto puede necesitar múltiples equipos. En implementación: tabla de asignación con atributos (rol, porcentaje de dedicación).
Enum para Fase.estado
Fase.estado y Proyecto.estado son candidatos a enumeraciones UML: {pendiente, en progreso, completada, cancelada} garantizando valores válidos.

Tabla Comparativa de Relaciones

Cuándo usar cada tipo de relación y cómo identificarla en el dominio.

Relación Notación Pregunta clave Ejemplo en TA5 Ciclo de vida
Herencia ──▷ ¿"Es un" tipo de? Administrador es un Empleado —
Realización - -▷ ¿Implementa el contrato de? TarjetaCredito impl. MedioPago —
Composición ◆── ¿La parte muere con el todo? Cuenta ◆→ Transacción Compartido (fuerte)

Tips para el examen
Si decís "es un" → Herencia. Si decís "tiene un" → Agregación o Composición.
Si al borrar el todo, la parte ya no tiene sentido → Composición (◆).
Las interfaces siempre usan realización (línea punteada + triángulo hueco).
Siempre anotar multiplicidad en los extremos de las asociaciones.
Una clase con solo atributos puede necesitar métodos constructores y getters.
