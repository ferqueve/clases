Tema 1

Tipos de Interfaz de Usuario

Clasificación, evolución histórica, casos de uso y análisis comparativo

CLI — Interfaz de Línea de Comandos
El usuario interactúa exclusivamente mediante texto. Fue la primera forma de interacción con computadoras (años 60-70). Requiere memorizar comandos específicos pero ofrece control total y máxima automatización.

Ventajas: velocidad extrema, automatizable con scripts, bajo consumo de recursos, acceso remoto sencillo (SSH).
Desventajas: curva de aprendizaje alta, no intuitiva para no-técnicos, difícil de descubrir funcionalidades.
Windows CMDBash/ZshPowerShellSSHGit CLI
GUI — Interfaz Gráfica de Usuario
Surgió con el Xerox Star (1981) y se popularizó con Mac (1984) y Windows. Usa el modelo WIMP: Ventanas (Windows), Íconos, Menús y Puntero. Es la interfaz más extendida en software de escritorio.

Ventajas: intuitiva, fácil de aprender, aprovecha metáforas visuales.
Desventajas: más lenta que CLI para expertos, mayor consumo de recursos.
Windows OSmacOSPhotoshopWord
NUI — Interfaz Natural de Usuario
Elimina dispositivos intermediarios: el usuario interactúa con gestos táctiles, movimiento corporal o reconocimiento de objetos. El término "natural" implica que la curva de aprendizaje es mínima porque el input es similar al mundo físico.

Subtipos: táctil (touchscreen), gestual (Kinect, cámaras), tangible (objetos físicos como token).
iPhone / AndroidSurfaceKinectLeap Motion
VUI — Interfaz de Usuario por Voz
Usa reconocimiento de voz (ASR) y síntesis de texto a voz (TTS). Permite interacción en lenguaje natural hablado. Ideal para contextos de manos libres o para usuarios con discapacidades visuales o motrices.

Desafíos: ambigüedad del lenguaje, acentos y dialectos, ruido ambiental, privacidad.
SiriAlexaGoogle AssistantCortana
Web UI
Interfaces accesibles vía navegador. Combinan HTML, CSS y JavaScript. Con las SPAs (Single Page Applications) y PWAs se acercan al rendimiento de apps nativas. El modelo dominante del software empresarial moderno.

Estándares clave: WCAG 2.1, Web Vitals (LCP, CLS, FID), REST/GraphQL.
GmailFigma WebNotionTrello
Mobile UI
Diseñadas para smartphones y tablets. Priorizan el tacto sobre el ratón. Tienen restricciones únicas: pantalla pequeña, uso con una sola mano, batería limitada, conectividad variable, sensores (GPS, cámara, acelerómetro).

Guías oficiales: Material Design 3 (Google), Human Interface Guidelines (Apple).
WhatsAppInstagramSpotifyUber
AR / VR — Realidad Aumentada y Virtual
AR superpone información digital en el entorno real (cámara + pantalla). VR crea entornos completamente inmersivos. Requieren nuevos paradigmas de interacción: mirada, gestos 3D, controladores, voz.

Desafíos UX: mareo por movimiento (motion sickness), fatiga ocular, peso del dispositivo.
Meta QuestApple Vision ProPokémon GOIKEA Place
CUI — Interfaz Conversacional
El usuario dialoga en lenguaje natural (texto o voz) con el sistema. Basada en NLP/IA. Elimina la necesidad de aprender menús o formularios. Puede ser guiada (flujos predefinidos) o libre (IA generativa).

Tipos: chatbots con reglas, chatbots con IA, asistentes virtuales empresariales.
ChatGPTCopilotSoporte bancario AIIntercom
Caso 1 — GitHub y la combinación CLI + GUI
Situación: GitHub ofrece simultáneamente una CLI (gh), una GUI web y una app de escritorio. Esta decisión de producto no es arbitraria: responde a que distintos perfiles de usuario tienen necesidades distintas.

Análisis: Un developer experimentado prefiere gh pr create --title "Fix bug" porque no necesita abrir el navegador, autenticarse y navegar menús. Un colaborador no-técnico prefiere la GUI web con su formulario visual.

Conclusión: La elección del tipo de interfaz debe basarse en el perfil del usuario, la frecuencia de uso y el contexto de uso. No existe una única interfaz "mejor": existen interfaces más adecuadas para cada caso.
Caso 2 — Amazon Alexa y los límites de la VUI
Situación: Amazon invirtió billones en Alexa como reemplazo de interfaces tradicionales. En 2023 reportaron que el uso mayoritario se limitaba a: reproducir música, preguntar el clima y configurar alarmas.

Problemas identificados: Los usuarios no recuerdan qué frases exactas funcionan ("wake words"), el error de reconocimiento rompe la confianza, y la VUI no es viable para tareas complejas con muchas opciones.

Lección: La VUI es excelente para comandos simples y frecuentes en contextos manos libres (cocina, auto). Es pobre para tareas de exploración o con muchas variables. Se debe diseñar VUI para casos de uso específicos, no como reemplazo general de GUI.
❌ Caso de uso inadecuado para VUI
"Alexa, mostrame las facturas del mes de marzo filtradas por proveedor mayor a $5000 y exportalas en Excel" — demasiado complejo, múltiples parámetros.
✅ Caso de uso ideal para VUI
"Alexa, poneme una alarma para las 7 AM" — simple, frecuente, sin ambigüedad, contexto manos libres (dormitorio).
Caso 3 — Apple Vision Pro: UI espacial y sus desafíos
Situación: Apple Vision Pro (2024) introdujo un nuevo paradigma de UI: los ojos como puntero, los dedos como clicks, y la voz como entrada de texto.

Problemas de UX reportados en primeros usuarios: fatiga ocular tras 30-45 minutos de uso continuo, incomodidad al escribir texto (teclado virtual lento), y aislamiento social al usar el dispositivo en público.

Implicación para diseñadores: Cada nuevo tipo de interfaz crea nuevos problemas de usabilidad que los principios clásicos (Nielsen, Tognazini) no siempre anticipan. El diseño de UI espacial requiere considerar: campo visual, profundidad, fatiga muscular de brazos, y cómo el usuario "señala" sin mouse físico.
Caso 4 — Chatbots bancarios: cuando la CUI falla
Situación: Muchos bancos reemplazaron sus líneas de atención con chatbots. Los primeros intentos (basados en palabras clave) tuvieron tasas de abandono del 70%+.

Error de diseño: Tratar la CUI como un formulario disfrazado de conversación. Preguntar "¿Cuál es tu número de cliente?" en un chat no mejora la experiencia respecto al formulario web.

Buenas prácticas actuales: Diseñar flujos conversacionales que se adapten a cómo los usuarios expresan naturalmente sus necesidades. Incluir siempre opción de derivar a agente humano. Usar botones rápidos para opciones frecuentes.

Criterio de elección clave: No existe la "mejor" interfaz. La decisión debe basarse en: (1) perfil y contexto del usuario, (2) complejidad de la tarea, (3) frecuencia de uso, (4) entorno físico de uso, (5) necesidades de accesibilidad. Las mejores aplicaciones combinan múltiples tipos según la tarea.
1960s–1970s: Tarjetas perforadas y terminales de texto
Los primeros usuarios (científicos y militares) ingresaban datos en tarjetas perforadas o escribían en terminales de texto sin pantalla gráfica. La "interfaz" era el lenguaje mismo de la máquina.
1981–1984: GUI y el modelo WIMP
Xerox Star (1981) inventó el concepto de ventanas y ratón. Apple Macintosh (1984) lo popularizó. Microsoft Windows (1985) lo masificó. Por primera vez la computadora era accesible para no-técnicos.
1991–2000: World Wide Web y las Web UI
Tim Berners-Lee creó la WWW en 1991. Las interfaces web democratizaron el acceso: sin instalación, multiplataforma. El desafío: diseñar para el navegador con limitaciones de HTML.
2007: iPhone y la revolución táctil
Steve Jobs presentó el iPhone como "internet en tu bolsillo". Eliminó el teclado físico y redefinió la Mobile UI. Gesto de "pinch-to-zoom", tap, swipe: la NUI táctil se convirtió en estándar global.
2011–2015: Asistentes de voz y VUI
Siri (2011), Google Now (2012), Cortana (2014), Alexa (2014). La VUI entró en los hogares. Los smart speakers cambiaron el paradigma de interacción doméstica.
2016–hoy: AR/VR y UI espacial
Oculus Rift, HoloLens, ARKit/ARCore. El diseño para 3 dimensiones requiere nuevas reglas: no hay "pantalla", el espacio es el canvas. Apple Vision Pro (2024) propone la "computación espacial".
2022–hoy: CUI generativa con IA
ChatGPT (2022) redefinió las expectativas de las CUI. Por primera vez la conversación con IA parece natural. Surge el diseño de "prompts" como nueva disciplina y la integración de IA en toda interfaz.

Las 10 Heurísticas de Nielsen

Teoría, violaciones reales en productos conocidos y cómo auditarlas

Contexto: Jakob Nielsen publicó estas 10 heurísticas en 1994 junto con Rolph Molich. No son reglas absolutas, sino principios generales para identificar problemas de usabilidad. Se usan en la Evaluación Heurística, donde 3-5 expertos analizan una interfaz sin usuarios reales.
  • 01
    Visibilidad del estado del sistema
    Principio: El sistema siempre debe mantener informados a los usuarios sobre lo que está ocurriendo, mediante retroalimentación oportuna y adecuada. El usuario nunca debe preguntarse "¿pasó algo?" o "¿está cargando?"

    Por qué importa: La incertidumbre genera ansiedad. Si el usuario no sabe si su acción tuvo efecto, puede repetirla (duplicar pedidos, doble clic en botones) o abandonar el sistema.

    ✅ Ejemplos buenos: Barra de progreso en subida de archivos, indicador de "Escribiendo..." en WhatsApp, confirmación "¡Guardado!" en Google Docs.
    ❌ Ejemplos malos: Botón que no cambia de estado al hacer clic, formulario que no indica si se envió, operación bancaria sin confirmación visual.
  • 02
    Coincidencia con el mundo real
    Principio: El sistema debe hablar el lenguaje del usuario: palabras, frases y conceptos que ya conoce de su experiencia cotidiana. Evitar jerga técnica interna.

    Metáforas de escritorio: "Carpeta" para agrupar archivos, "Papelera" para eliminar, "Escritorio" para el área de trabajo. Estas metáforas son tan efectivas que hoy nadie necesita explicación.

    Riesgo: Las metáforas tienen límites. La "papelera" vacía y la "carpeta" no tienen peso real, pero la metáfora funciona porque el comportamiento es análogo al objeto físico.

    ✅ Bien: "Archivar" email en lugar de "FLAG_ARCHIVE_001". ❌ Mal: "Error 0x800704CF" en lugar de "No hay conexión a internet".
  • 03
    Control y libertad del usuario
    Principio: Los usuarios eligen funciones por error. Necesitan salidas de emergencia claras: deshacer y rehacer son fundamentales. El usuario debe sentir que tiene control y que los errores no son catastróficos.

    Concepto de "tolerancia al error": Un sistema bien diseñado hace que los errores sean fáciles de corregir, no de cometer. Esto aumenta la confianza del usuario para explorar.

    ✅ Ejemplos: Ctrl+Z universal, "Deshacer envío" de Gmail (30 segundos), botón "Cancelar" siempre visible en diálogos modales, navegación hacia atrás en apps móviles.
    ❌ Error clásico: Eliminar definitivamente sin confirmación y sin posibilidad de recuperar (violación combinada con heurística #5).
  • 04
    Consistencia y estándares
    Principio: Los usuarios no deberían preguntarse si distintas palabras, situaciones o acciones significan lo mismo. Seguir las convenciones de la plataforma reduce la carga cognitiva.

    Dos tipos de consistencia:
    • Interna: El mismo elemento se comporta igual en toda la aplicación.
    • Externa: La app sigue las convenciones de la plataforma (ej: el menú está arriba en desktop, abajo en mobile).

    ✅ Bien: Los botones de acción primaria siempre azules, siempre a la derecha. ❌ Mal: "Guardar" en una pantalla, "Salvar" en otra, "Conservar cambios" en una tercera.
  • 05
    Prevención de errores
    Principio: Mejor que un buen mensaje de error es un diseño que evite que el error ocurra. Hay dos niveles: (1) eliminar condiciones propensas a error, (2) confirmar antes de acciones destructivas.

    Tipos de errores a prevenir:
    • Deslices (slips): El usuario sabe qué quiere hacer pero se equivoca en la acción (clic en botón equivocado por proximidad).
    • Equivocaciones (mistakes): El usuario tiene un modelo mental incorrecto del sistema.

    ✅ Bien: Deshabilitar botón "Enviar" si campos requeridos están vacíos, confirmación "¿Eliminar este archivo? Esta acción no se puede deshacer".
    ❌ Mal: Botón "Cancelar" y "Eliminar" adyacentes con el mismo estilo visual.
  • 06
    Reconocimiento antes que recuerdo
    Principio: Minimizar la carga de memoria del usuario haciendo visible la información, las acciones y las opciones necesarias. Es más fácil reconocer algo que recordarlo desde cero.

    Fundamento cognitivo: La memoria de reconocimiento es mucho más potente que la memoria de recuerdo libre. Por eso las GUI (donde reconocés íconos) son más fáciles que las CLI (donde debés recordar comandos exactos).

    ✅ Bien: Historial de búsquedas recientes, autocompletado en formularios, tooltips en íconos, menús contextuales con opciones visibles.
    ❌ Mal: Atajos de teclado sin forma de descubrirlos, formularios de múltiples pasos donde no podés volver a ver lo ingresado anteriormente.
  • 07
    Flexibilidad y eficiencia de uso
    Principio: Los aceleradores (atajos de teclado, gestos, macros) permiten a usuarios expertos trabajar más rápido, sin interferir con los novatos que no los conocen.

    El desnivel de experticia: Un novato y un experto tienen necesidades radicalmente distintas. Los novatos necesitan guía; los expertos necesitan velocidad. Un buen diseño sirve a ambos sin sacrificar a ninguno.

    ✅ Bien: Photoshop con atajos (B = brush, V = selection) mientras el toolbar es visible. Gmail con j/k para navegar emails. Formularios con autocompletado y tabIndex.
    ❌ Mal: Obligar a todos los usuarios a completar un wizard de 5 pasos aunque el 80% haga siempre lo mismo.
  • 08
    Diseño estético y minimalista
    Principio: Los diálogos no deben contener información irrelevante o raramente usada. Cada unidad extra de información compite con la información relevante y reduce su visibilidad relativa.

    No significa "simple": Esta heurística no dice que la UI deba ser simple, sino que debe ser relevante. Photoshop tiene cientos de herramientas y no viola esta heurística porque cada una tiene su razón de ser para los usuarios objetivo.

    ✅ Bien: Google Search: solo la caja de búsqueda. Confirmar transacción: solo monto, destino y botones confirmar/cancelar.
    ❌ Mal: Dashboard con 30 métricas donde el usuario solo necesita 3. Pop-ups de bienvenida, banners de cookies, newsletter y descuento al mismo tiempo.
  • 09
    Ayuda a reconocer, diagnosticar y recuperarse de errores
    Principio: Los mensajes de error deben: (1) expresarse en lenguaje llano (no código), (2) indicar con precisión el problema, (3) sugerir constructivamente una solución.

    El trío del buen error: ¿QUÉ pasó? + ¿POR QUÉ pasó? + ¿QUÉ puede hacer el usuario?

    ❌ Mal
    "Error: HTTP 422 Unprocessable Entity. Stack: ValidationException at line 47"
    ✅ Bien
    "El email ingresado no es válido. Por favor usá el formato: nombre@dominio.com"
  • 10
    Ayuda y documentación
    Principio: Aunque es mejor si el sistema puede usarse sin documentación, puede ser necesario brindar ayuda. Debe ser: fácil de buscar, orientada a la tarea del usuario, concreta y lo más breve posible.

    Prioridad: Esta heurística está al final porque la mejor ayuda es no necesitarla. Si el diseño es lo suficientemente intuitivo (heurísticas 1-9), la documentación es el último recurso.

    ✅ Bien: Tooltips en íconos complejos, ayuda contextual "¿Qué significa esto?" en formularios, guías de inicio rápido, FAQs organizadas por tarea.
    ❌ Mal: Manual PDF de 200 páginas como única documentación, soporte solo por ticket con 48h de respuesta.
Windows Update — Múltiples violaciones
Heurística #1 violada: Windows (versiones antiguas) iniciaba actualizaciones sin aviso, reiniciaba el equipo, y el usuario perdía su trabajo.
Heurística #3 violada: "Reiniciar ahora" sin opción de posponer indefinidamente. El usuario no tenía control.
Heurística #5 violada: No se prevenía el error de "reinicio en medio de trabajo no guardado".

Impacto real: Millones de usuarios perdieron trabajo. Microsoft fue objeto de burlas públicas. En Windows 10/11 mejoraron: "Active Hours" para no reiniciar cuando el usuario trabaja, notificaciones previas y tiempo de posponer.
Healthcare.gov — El lanzamiento fallido de 2013
Contexto: El sitio de inscripción a Obamacare se cayó en su lanzamiento. Miles de personas no podían completar el registro.

Heurística #1 violada: Sin feedback durante los largos tiempos de espera (la página simplemente "colgaba").
Heurística #9 violada: Mensajes de error técnicos inútiles para usuarios no técnicos.
Heurística #5 violada: El sistema no prevenía que el usuario ingresara información inválida hasta el final del formulario de 20+ pasos.

Resultado: El gobierno de Obama tuvo que contratar un equipo de rescate en Silicon Valley (USDS) para reconstruir el sistema. Costo estimado: $677 millones solo en el lanzamiento fallido.
Snapchat Redesign 2018 — Heurística #4
Situación: Snapchat rediseñó radicalmente su interfaz en 2018, mezclando contenido de amigos con contenido de marcas en la misma pantalla.

Heurística #4 violada: El nuevo diseño rompió la consistencia que los usuarios habían aprendido. Los usuarios sabían que "izquierda = cámara, derecha = stories". El rediseño lo cambió sin lógica clara.

Heurística #6 violada: Los usuarios ya no podían reconocer dónde estaba cada función; tenían que recordar la nueva ubicación.

Resultado: Kylie Jenner twitteó "no abro más Snapchat ¿y ustedes?" → Snapchat perdió $1.3 billion en valor de mercado en un día. La empresa tuvo que hacer un rediseño parcial meses después.
Avianca Airlines — Heurística #2 y #9
Caso clásico de HCI: Un formulario de check-in online preguntaba "¿Tiene tarifas especiales? (Y/N)" usando la convención anglosajona Y/N (Yes/No), pero en un sitio en español para usuarios latinoamericanos.

Heurística #2 violada: Y/N no es el lenguaje del usuario hispanohablante. Muchos usuarios ponían "N" queriendo decir "No" cuando necesitaban poner "Y" (sí tienen tarifas especiales).

Lección: La localización no es solo traducir texto. Es adaptar convenciones, formatos de fecha (DD/MM/YYYY vs MM/DD/YYYY), separadores decimales (coma vs punto) y metáforas al contexto cultural del usuario.
¿Qué es la Evaluación Heurística? Es un método de inspección de usabilidad donde 3-5 evaluadores expertos revisan una interfaz comparándola con las 10 heurísticas. Nielsen demostró que con 5 evaluadores se detecta el 75% de los problemas de usabilidad.
Proceso paso a paso
1Preparación
Definir el scope de evaluación (¿toda la app o flujo específico?). Reclutar evaluadores (idealmente con expertise en UX). Preparar formulario de registro de hallazgos con: heurística violada, severidad (1-4), descripción, evidencia.
2Evaluación individual
Cada evaluador revisa la interfaz de forma INDEPENDIENTE (sin influenciarse entre sí). Típicamente 1-2 horas. Se recorre el sistema 2 veces: primera pasada para entenderlo, segunda para identificar problemas heurísticos.
3Consolidación
Reunión donde se agregan todos los hallazgos individuales. Se eliminan duplicados. Se discuten puntos de desacuerdo. El resultado es una lista consolidada con severidad ponderada (promedio de evaluadores).
4Priorización y reporte
Se priorizan problemas por severidad: 4=Catastrófico (debe corregirse), 3=Mayor, 2=Menor, 1=Cosmético. Se genera reporte con recomendaciones de mejora para cada hallazgo.
Escala de severidad de Nielsen: 0=No es problema, 1=Solo cosmético (corregir si hay tiempo), 2=Menor (baja prioridad), 3=Mayor (alta prioridad), 4=Catástrofe de usabilidad (imperativo corregir antes de lanzar).

Principios de Tognazini

Bruce "Tog" Tognazini — AskTog.com · Principios de diseño de interacción con análisis profundo

1. Anticipación
Las aplicaciones deben prever las necesidades del usuario y presentar información y herramientas antes de que se soliciten explícitamente. El software proactivo reduce la fricción.
Ej: Google Docs sugiere autocompletar frases. Netflix pre-carga el próximo episodio. El GPS calcula rutas alternas antes de que haya tráfico visible.
2. Autonomía
Los usuarios deben sentir que controlan el sistema. Ofrecer suficientes opciones sin abrumar. El software no debe ser paternalista ni forzar flujos innecesarios. Respetar las decisiones del usuario.
Ej: Permitir guardar un archivo en cualquier formato aunque no sea el predeterminado. No forzar tutoriales de bienvenida que no se pueden cerrar.
3. Ceguera al cambio / Percepción de color
Nunca usar el color como único canal de información. Un 8% de los hombres tiene alguna forma de daltonismo. Combinar color con forma, ícono, texto o patrón.
Ej: Los gráficos de barras con solo colores rojo/verde son inaccesibles. Solución: agregar etiquetas de texto o usar patrones de relleno distintos además del color.
4. Consistencia
Los usuarios deben poder aplicar lo aprendido en una parte del sistema a las demás. Comportamientos, vocabulario y patrones visuales deben ser uniformes en toda la aplicación.
Ej: Si en la pantalla de Clientes el botón "Nuevo" está arriba a la derecha, en la pantalla de Productos debe estar en el mismo lugar y tener el mismo estilo.
5. Eficiencia del usuario
Optimizar el tiempo del usuario, no el del sistema. El costo del tiempo humano es mayor que el costo del CPU. Evitar diálogos de espera innecesarios. Nunca hacer esperar al usuario por procesos que pueden hacerse en segundo plano.
Ej: Al enviar un email, mostrar "Enviado" inmediatamente mientras el proceso ocurre en background. No mostrar spinner durante 3 segundos antes de confirmar.
6. Interfaces explorables
Los usuarios deben poder explorar sin miedo a consecuencias permanentes. Si toda acción es reversible, el usuario se atreve a descubrir funcionalidades. Las interfaces explorables generan más engagement y usuarios más expertos con el tiempo.
Ej: Figma permite deshacer infinitas acciones. Los juegos bien diseñados tienen "checkpoints" frecuentes. Google Maps permite explorar sin "comprometerse" a una ruta.
7. Ley de Fitts
El tiempo para alcanzar un objetivo es función de su tamaño y distancia: T = a + b × log₂(D/W + 1). Las implicaciones: botones importantes deben ser grandes. Los bordes y esquinas de pantalla son "infinitamente grandes" porque el cursor choca con ellos.
Ej: El menú de macOS en el borde superior es más rápido de alcanzar que en cualquier otra posición. En móvil, los controles principales van abajo (zona del pulgar).
8. Aprendizaje
Las interfaces deben ser fáciles de aprender inicialmente y no requerir re-aprendizaje constante. Favorecer reconocimiento sobre recuerdo. Las metáforas y patrones conocidos reducen la curva de aprendizaje.
Ej: WhatsApp se aprendió en minutos porque usó metáforas del SMS y el chat existentes. No requirió manual de usuario.
9. Metáforas de uso
Usar objetos y metáforas del mundo físico para hacer la interfaz familiar. Pero no abusar al punto de limitar capacidades digitales. La "papelera" es una metáfora útil, pero en lo digital podés recuperar lo que tirás (ventaja sobre el mundo físico).
Ej: El "carrito de compras" en e-commerce es una metáfora perfecta. El "ícono de diskette" para guardar ya no aplica como metáfora para generaciones jóvenes.
10. Protección del trabajo del usuario
El sistema nunca debe permitir que el usuario pierda trabajo no guardado. Auto-guardar periódicamente, confirmar antes de cerrar con cambios pendientes, recuperar sesión al abrir de nuevo.
Ej: Google Docs guarda automáticamente cada cambio. Notion tiene historial de versiones. VS Code pregunta "¿Guardar antes de cerrar?" y restaura pestañas al reabrir.
11. Legibilidad
El texto debe ser siempre legible: contraste adecuado (≥4.5:1 WCAG AA), tamaño mínimo 16px en pantalla, fuentes optimizadas para pantalla. No sacrificar legibilidad por estética. El contenido es más importante que el decorado.
Ej: Texto gris claro sobre fondo blanco "moderno" puede ser WCAG Fail. Solución: ajustar la paleta sin sacrificar el diseño.
12. Seguimiento del estado
El sistema debe recordar lo que el usuario ha hecho y el estado actual. Al regresar después de una interrupción, retomar desde donde se dejó: posición de scroll, sección activa, formulario parcialmente completado.
Ej: Netflix recuerda hasta qué minuto ibas en cada serie. Duolingo guarda tu racha y posición en la lección. YouTube continúa el video desde el segundo donde lo dejaste.
13. Objetos visibles
Lo que el usuario puede hacer debe ser visible. Evitar funcionalidades ocultas que requieran comandos secretos, clics en lugares no obvios, o combinaciones de teclas que nadie descubre solo.
Ej: El menú contextual (clic derecho) es una funcionalidad visible pero no totalmente obvia: hay que enseñar que existe. Los "Easter eggs" violan este principio intencionalmente.
14. Configurabilidad
Permitir que el usuario personalice la experiencia según sus necesidades y preferencias: atajos, orden de elementos, tamaño de fuente, tema, idioma. Los usuarios no son todos iguales.
Ej: VS Code es altamente configurable (settings.json). Slack permite personalizar notificaciones por canal. La accesibilidad es una forma de configurabilidad obligatoria.
15. Cambios visibles de estado
Cuando la pantalla cambia de estado, el usuario debe percibirlo claramente. Usar animaciones o transiciones para comunicar cambios (carga, apertura, eliminación). El ojo humano detecta movimiento mejor que cambios estáticos.
Ej: Al eliminar un item de lista, animarlo hacia afuera (no que desaparezca instantáneamente). Al abrir un modal, animarlo desde el botón que lo originó.
16. Respuesta rápida percibida
El sistema debe responder inmediatamente aunque la operación tarde. Un feedback visual instantáneo (cursor de carga, cambio de estado del botón) evita que el usuario piense que el sistema se colgó. Percepción ≠ realidad.
Ej: Instagram muestra el "like" al instante en el cliente antes de confirmar con el servidor (optimistic UI). El botón se desactiva y cambia de color al hacer clic.
Caso Profundo — Ley de Fitts en el diseño de interfaces reales
Fórmula: T = a + b × log₂(2D/W) — donde T=tiempo, D=distancia al objetivo, W=ancho del objetivo.

Aplicación en macOS: La barra de menú de macOS está pegada al borde superior de la pantalla. Esto la hace efectivamente "de ancho infinito" en dirección vertical (no podés pasarte de ella). Mover el cursor hacia arriba a máxima velocidad y soltar siempre llega al menú. Esto es mucho más rápido que en Windows donde el menú está dentro de cada ventana (más pequeño y más lejos).

Aplicación en móvil: La zona inferior de la pantalla (zona del pulgar) es donde deben ir las acciones más frecuentes. Requiere menos tiempo de alcance y menos cambio de agarre. Por eso Material Design y HIG ubican la navegación principal en la parte inferior.

Aplicación en botones: Un botón de 48×48px que está a 10px del cursor actual tarda ~200ms en alcanzar. El mismo botón a 200px tarda ~350ms. En una app donde ese botón se usa 50 veces por sesión, eso son 7.5 segundos adicionales de fricción por sesión.
❌ Violación de Fitts
Botón "Confirmar pago" de 24×24px ubicado en la esquina superior derecha de una app móvil. Difícil de alcanzar con el pulgar, pequeño, propenso a error.
✅ Aplicación correcta
Botón "Pagar" de ancho completo (100% del ancho de pantalla, 56px de alto) ubicado en la parte inferior de la pantalla, en la zona del pulgar.
Caso — Google Docs y la Protección del trabajo
Situación: Antes de Google Docs, el estándar era "Guardar" manualmente (Ctrl+S). Si el software crasheaba o la luz se iba, perdías el trabajo no guardado.

Innovación de Tognazini aplicada: Google Docs implementó guardado automático continuo ("todos los cambios guardados en Drive"). El usuario nunca tiene que pensar en guardar. Adicionalmente, el historial de versiones permite ver y restaurar cualquier versión anterior.

Impacto: Este cambio redujo el estrés cognitivo de los usuarios de oficina dramáticamente. El usuario puede cerrar el laptop en mitad de un documento sin ansiedad. La productividad aumentó porque el usuario invierte energía mental en el contenido, no en la gestión del archivo.

Lección: Proteger el trabajo del usuario no es solo técnico, es una decisión de diseño que tiene impacto emocional y psicológico profundo.

Problemas de Facilidad de Uso

Análisis profundo con casos reales, métricas de impacto y soluciones concretas

1. Navegación confusa y desorientación
Causa: Falta de jerarquía de información, menús sin estructura lógica, ausencia de breadcrumbs, terminología inconsistente en los ítems del menú.
Consecuencia medida: Nielsen Norman Group reporta que el 70% de los carritos de compra se abandonan, y la navegación confusa es la causa #1 en e-commerce.
Síntomas en el usuario: "No encuentro cómo volver", "¿Dónde está la configuración?", uso excesivo del botón de búsqueda cuando debería encontrarse por menú.
Solución: Card sorting con usuarios reales para definir taxonomía. Breadcrumbs en todos los niveles. Barra de búsqueda prominente. Máximo 7 ítems en menú principal (Miller's Law).
❌ Antes
Menú con 15 ítems al mismo nivel, sin categorías. Usuario tarda 45 segundos en encontrar "Cambiar contraseña".
✅ Después
Menú agrupado: Cuenta > Seguridad > Cambiar contraseña. Con breadcrumb visible. Tiempo promedio: 8 segundos.
2. Sobrecarga cognitiva
Base teórica: La Ley de Miller (1956) establece que la memoria de trabajo humana puede procesar 7±2 ítems simultáneamente. Interfaces que superan ese límite generan errores y abandono.
Manifestaciones: Pantallas con 20+ opciones, formularios con todos los campos visibles a la vez, dashboards con 30 métricas, pop-ups simultáneos.
Concepto de "progressive disclosure": Mostrar primero lo esencial (acción principal), revelar opciones avanzadas solo cuando el usuario las solicita.
Solución: Chunking (agrupar elementos relacionados), progressive disclosure, wizards para tareas complejas (dividir en pasos), eliminar opciones raramente usadas o moverlas a "Avanzado".
3. Falta de retroalimentación (Feedback)
Umbral humano: Si la respuesta tarda más de 100ms, el usuario percibe un "lag". Más de 1 segundo pierde el "flujo mental". Más de 10 segundos: abandono probable.
Tipos de feedback necesario:
• Feedback inmediato (≤100ms): cambio visual al hacer clic.
• Feedback de proceso (≤1s): spinner o barra de progreso.
• Feedback de resultado: confirmación o mensaje de error claro.
• Feedback de sistema: toasts, notificaciones de eventos relevantes.
Solución: Optimistic UI (mostrar resultado antes de confirmar con servidor), skeleton screens durante carga, toasts de confirmación, estados de botones (default → loading → success/error).
4. Mensajes de error inútiles
Anatomía de un mal error: Solo indica qué pasó sin decir por qué ni qué hacer. Usa jerga técnica. Es genérico (aplica a múltiples situaciones diferentes). Asusta al usuario con tono culpabilizador.
Impacto: Forrester Research estima que el 55% de los usuarios abandona un proceso cuando encuentra un error que no entiende, aunque pudiera corregirlo fácilmente.
Solución: Mensajes en lenguaje humano. Estructura: QUÉ pasó + POR QUÉ + QUÉ hacer. Tono colaborativo ("Ingresá un email válido, por ejemplo: tu@mail.com"). Validación inline en tiempo real.
❌ Error inútil
"Error 422: Validation failed. Field 'email' does not match regex pattern RFC5322."
✅ Error útil
"El email no tiene el formato correcto. Revisá que tenga @ y un dominio, por ejemplo: nombre@empresa.com"
5. Accesibilidad deficiente
Alcance del problema: Según la OMS, 1 de cada 6 personas en el mundo vive con alguna discapacidad. En Uruguay, aproximadamente 400.000 personas. No diseñar accesiblemente excluye activamente a este segmento.
Principales fallas: Contraste insuficiente (ratio <4.5:1), sin etiquetas aria para lectores de pantalla, sin navegación por teclado, videos sin subtítulos, formularios sin labels visibles.
Marco legal: WCAG 2.1, Ley 18.651 en Uruguay (accesibilidad en sitios del Estado).
Solución: Contraste mínimo 4.5:1, etiquetas aria-label/aria-describedby, focus visible en navegación por teclado, alt text en imágenes, subtítulos en videos. Herramientas: axe DevTools, Lighthouse, NVDA.
6. Formularios mal diseñados
Estadística: Baymard Institute encontró que el checkout promedio en e-commerce tiene 14.88 campos (muchos innecesarios). Reducirlo a 7-8 aumenta la conversión entre 20-60%.
Errores comunes: Label dentro del input que desaparece al escribir (sin placeholder de referencia), campos requeridos solo marcados con * sin leyenda, validación solo al enviar (no en tiempo real), orden de campos sin lógica (apellido antes que nombre).
Principio: Cada campo es una fricción. Solicitar solo lo mínimo necesario para el paso actual.
Solución: Labels flotantes (visible siempre), validación inline, campos mínimos, autocompletado (autocomplete HTML), teclado numérico para DNI/teléfono en móvil, guardar progreso en formularios largos.
Caso Amazon 1-Click: Eliminando fricción en formularios
Problema original: El proceso de checkout en e-commerce requería ingresar dirección, método de pago, confirmar, etc. en cada compra. Alta fricción = abandono de carrito.

Solución innovadora: Amazon patentó en 1999 el sistema "1-Click": con un solo clic se completaba la compra usando la dirección y método de pago guardados. Eliminó todos los pasos intermedios para compras repetidas.

Impacto medido: La patente de Amazon 1-Click fue tan valiosa que Apple pagó licencia para implementarla en iTunes. Cuando la patente expiró en 2017, todos los e-commerce la adoptaron masivamente.

Principios aplicados: Eficiencia del usuario (Tognazini #5), Flexibilidad y eficiencia de uso (Nielsen #7), Progressive disclosure (mostrar el formulario completo solo si el usuario quiere cambiar datos).
Twitter y el límite de 140 caracteres: restricción como diseño
Origen: El límite de 140 caracteres fue técnico (SMS = 160 caracteres, 20 reservados para el usuario). Pero se convirtió en una decisión de diseño que definió la identidad del producto.

Efecto en usabilidad: La restricción forzó concisión. Eliminó la sobrecarga cognitiva (#8 Nielsen). Hizo los mensajes escaneables y rápidos de consumir. El "diseño minimalista por restricción" mejoró la experiencia del lector.

Cuando rompieron el principio: En 2017 Twitter amplió a 280 caracteres. Los usuarios lo pidieron, pero el impacto fue negativo para la lectura: los tweets largos generan menos engagement que los cortos, según datos del propio Twitter.

Lección: A veces las restricciones son buenos diseñadores. La facilidad de uso no siempre significa "más opciones". A veces significa "menos pero mejor".
Sistema de check-in de aerolíneas: usabilidad bajo presión
Contexto: El check-in de aerolíneas es un proceso crítico: el usuario tiene presión de tiempo, puede estar en un aeropuerto ruidoso y distraído, y un error (seleccionar asiento equivocado, perder vuelo por no completar el proceso) tiene consecuencias graves.

Problemas documentados:
• Formularios que no guardan el progreso (viola Tognazini #10): si la sesión expira, empieza de cero.
• Pantallas de pago que se abren en nueva pestaña, perdiendo el contexto.
• Timeout de 10 minutos sin aviso visual claro (viola Nielsen #1).
• Botón "Continuar" que lleva al upgrade de asiento cuando el usuario quiere ir directo a selección (bait de compra involuntario, viola Nielsen #3).

Buena práctica observada (Emirates): Barra de progreso clara (Paso 2 de 5), guardado automático, re-envío de email si el proceso se interrumpe, confirmación por múltiples canales (email + SMS).
Métricas de usabilidad: La usabilidad se puede y debe medir. No es una opinión subjetiva, es una característica medible del sistema. Las métricas más usadas en industria son:
Tiempo en tarea
¿Cuánto tarda un usuario promedio en completar una tarea específica? Ej: "Encontrar y comprar un producto en menos de 3 minutos".
Tasa de éxito
Porcentaje de usuarios que completan la tarea sin ayuda externa. Una tasa <70% indica problema grave de usabilidad.
Tasa de error
¿Cuántos errores comete el usuario intentando completar la tarea? ¿Son recuperables o catastróficos?
SUS Score
System Usability Scale: 10 preguntas Likert, puntaje 0-100. Promedio industria: 68. Por encima de 80.3 = "A" (excelente).
Tasa de abandono
Porcentaje de usuarios que inician un flujo pero no lo completan. En e-commerce: ~70% de carritos abandonados es el promedio global.
Satisfacción (NPS/CSAT)
Net Promoter Score o Customer Satisfaction. Mide la percepción subjetiva de usabilidad. Complementa las métricas objetivas.
Herramientas de diagnóstico
Pruebas de usuario (User Testing)
El usuario real realiza tareas específicas mientras el evaluador observa. Puede ser presencial (laboratorio de usabilidad con eye tracking) o remoto (Zoom + grabación de pantalla). Con 5 usuarios se detecta el 80% de los problemas (Nielsen). Se usa protocolo "think aloud" donde el usuario verbaliza lo que piensa mientras actúa.
Eye Tracking
Tecnología que registra el movimiento ocular del usuario. Genera "heatmaps" de atención visual (dónde mira la gente) y "gaze plots" (secuencia de miradas). Revela qué elementos atraen la atención, cuáles pasan desapercibidos y cómo el usuario escanea el contenido.
A/B Testing
Se presentan dos versiones (A y B) de un elemento a grupos de usuarios diferentes. Se mide cuál tiene mejor rendimiento en métricas predefinidas (tasa de conversión, tiempo en tarea, clicks). Amazon, Google y Netflix hacen cientos de A/B tests simultáneos. Es el método más objetivo porque usa usuarios reales en condiciones reales.
Card Sorting
Técnica para diseñar la arquitectura de información. Los participantes organizan tarjetas con temas/secciones en grupos según su lógica. Revela cómo los usuarios mentalmente categorizan la información, lo que informa el diseño del menú y la estructura de navegación.

Mobile-First vs Responsive Design
Responsive Design (2010)
Concepto de Ethan Marcotte: Diseñar una sola UI que se adapta a cualquier tamaño de pantalla usando media queries, fluid grids e imágenes flexibles.

Enfoque: Generalmente se diseña para desktop y luego se "encoge" para móvil. El resultado es que el móvil recibe una versión reducida del desktop.

Problema: La versión móvil suele ser inferior porque se diseñó como adaptación, no como experiencia propia.
Mobile-First Design (Luke W.)
Concepto de Luke Wroblewski: Diseñar primero para las restricciones del móvil. Luego enriquecer para pantallas más grandes. La restricción del móvil fuerza priorización del contenido.

Ventaja: Si algo funciona bien en 375px de ancho, funcionará bien en 1440px. Al revés no siempre es cierto.

Principio CSS: Estilos base para móvil, @media (min-width: 768px) para expandir.
Restricciones únicas del diseño móvil
Pantalla reducida
375-430px de ancho típico. El contenido debe priorizarse brutalmente. "Above the fold" es más crítico que en desktop. El espacio es un recurso escaso.
Interacción táctil
Sin hover, sin clic preciso de ratón. El dedo cubre ~44px de área. Los elementos pequeños generan "fat finger errors". Los menús de flyover no existen.
Conectividad variable
El usuario puede pasar de 4G a 3G a sin señal en segundos. Las apps deben funcionar en modo offline o degradar graciosamente. Service Workers + Cache API.
Batería limitada
Animaciones complejas, GPS constante y videos en loop consumen batería. Diseñar con conciencia de consumo energético: modo oscuro, reducción de animaciones.
Contexto de uso externo
El móvil se usa al sol, en movimiento, con distracciones. Contraste mínimo 7:1 para uso exterior. Texto grande. Interacciones de un solo toque cuando sea posible.
Sensores únicos
GPS, acelerómetro, cámara, NFC, huella digital. El diseño móvil puede aprovechar estos sensores para experiencias imposibles en desktop (check-in por GPS, pago por NFC).
Tamaños mínimos de área de toque
Apple HIG
Mínimo absoluto: 44×44 puntos (pt) de CSS.
Esto equivale a 44×44 px en pantallas 1x, 88×88 px en pantallas Retina 2x.

El componente visual puede ser más pequeño, pero el área interactiva (hitbox) debe ser 44×44 mínimo. Esto se logra con padding.
Material Design 3
Mínimo: 48×48 dp (density-independent pixels).
Espacio mínimo entre elementos: 8dp de separación entre áreas de toque adyacentes.

Los FABs (Floating Action Button) son 56dp de alto: el elemento más importante de la pantalla debe ser el más grande y más accesible.
¿Por qué 44-48px?
El ancho del dedo índice adulto promedio es ~44mm a la altura de la yema. En una pantalla típica de 160 DPI (1 px ≈ 0.16mm), 44px ≈ 7mm, que es aproximadamente el tamaño de la yema que hace contacto efectivo.

Ejemplos: Instagram, YouTube, Spotify.

Cuándo usar: Muchas secciones secundarias que no caben en bottom nav. NUNCA para las secciones más importantes.
Problema documentado: Oculta la navegación, reduce el uso de las secciones no visibles hasta en un 66% (NNGroup, 2016).
Alternativa: Combinar bottom nav (principales) + hamburger (secundarias).

Uber — Diseño para el contexto de uso extremo
Contexto de uso real: El usuario de Uber típicamente usa la app parado en la vereda, con la mano extendida para frenar el taxi, mirando el teléfono intermitentemente, posiblemente de noche o bajo la lluvia.

Decisiones de diseño basadas en el contexto:
• Texto grande y contraste alto: Legible de un vistazo bajo sol directo o noche.
• Botón de confirmación enorme: El botón "Confirmar" ocupa casi todo el ancho inferior de pantalla. Imposible perderse con el pulgar.
• Mapa prominente: El usuario verifica visualmente que la dirección es correcta sin leer texto (más rápido).
• Detección automática de ubicación: El campo "¿Dónde estás?" se llena automáticamente con GPS. El usuario solo ingresa el destino.
• Interacciones mínimas: El flujo completo desde abrir la app hasta confirmar el viaje requiere 3-4 taps. Sin fricción innecesaria.

Principio aplicado: El diseño del flujo principal fue optimizado para el caso de uso más difícil (exterior, movimiento, tiempo límite). Si funciona ahí, funciona en cualquier contexto.
Instagram — La evolución del bottom nav y el abandono del hamburger
Historia: En 2013, Instagram usaba hamburger menu para navegación. Las estadísticas mostraban que los usuarios de la primera versión usaban Features como Explorar el 47% menos que en versiones previas.

Cambio en 2014: Migraron a bottom navigation bar con 5 íconos siempre visibles. El engagement en Explorar subió dramáticamente.

Por qué funcionó: El bottom nav aplica la Ley de Fitts (accesible con el pulgar), aplica el principio de "Objetos visibles" de Tognazini (las secciones siempre están a la vista), y reduce la carga cognitiva (no hay que recordar qué funciones existen).

Lección: La visibilidad de las opciones de navegación impacta directamente en cuánto se usan. Ocultar = reducir uso.
PWA — Progressive Web Apps: el mejor de ambos mundos
¿Qué es una PWA? Una aplicación web que aprovecha APIs modernas del navegador para ofrecer capacidades propias de apps nativas.

Capacidades clave:
• Instalable: Se agrega al home screen sin pasar por App Store/Play Store.
• Offline: Service Workers cachean recursos para funcionar sin conexión.
• Push Notifications: Como una app nativa, puede enviar notificaciones.
• Acceso a hardware: Cámara, GPS, acelerómetro (con permisos).

Casos de éxito: Twitter Lite (PWA) redujo el tamaño de la app de 60MB a 600KB, redujo el uso de datos en 70%, y aumentó los tweets publicados en 75% en mercados emergentes con datos limitados.
