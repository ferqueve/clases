Práctica guiada

Estos principios guían el diseño de software mantenible, extensible y de bajo acoplamiento. Los principios SRP, OCP, LSP e ISP forman parte de los principios SOLID.

Principio 1
Minimize Coupling
Definición
El acoplamiento mide el grado de dependencia entre módulos. Minimizarlo significa diseñar componentes que conozcan lo menos posible sobre los demás.
Acoplamiento fuerte (malo)
  • Una clase instancia directamente otras clases concretas
  • Cambiar la implementación obliga a cambiar el cliente
  • Dificulta las pruebas unitarias
  • Alta resistencia al cambio
Acoplamiento débil (bueno)
  • Programar contra interfaces, no implementaciones
  • Inyección de dependencias (DI)
  • Fácil de sustituir implementaciones
  • Testeable en aislamiento
Tipos de acoplamiento (de peor a mejor)

Contenido → Común → Control → Estampa → Datos → Sin acoplamiento

Minimize Coupling
Ejemplo en C#
❌ TIGHT COUPLING
C#
public class OrderService
{
  // Instancia concreta: fuerte acoplamiento
  private SqlDatabase _db = new SqlDatabase();
  private GmailSender _mail = new GmailSender();

  public void Process(Order order)
  {
    _db.Save(order);
    _mail.Send(order.Email, "Confirmado");
  }
}
✓ LOOSE COUPLING
C#
public interface IDatabase  { void Save(Order o); }
public interface IMailSender { void Send(string t, string m); }

public class OrderService
{
  private readonly IDatabase  _db;
  private readonly IMailSender _mail;

  public OrderService(IDatabase db, IMailSender m)
    => (_db, _mail) = (db, m); // Inyección de dependencias

  public void Process(Order order)
  {
    _db.Save(order);
    _mail.Send(order.Email, "Confirmado");
  }
}

Beneficio: Ahora se puede cambiar SqlDatabase por MongoDatabase sin tocar OrderService, y testear con mocks.

Principio 2
Maximize Cohesion
Definición
La cohesión mide cuán relacionadas están las responsabilidades dentro de un módulo. Alta cohesión = todos los métodos y atributos trabajan hacia un único propósito bien definido.
Baja cohesión (God Class)
  • Una clase hace "todo": UI, BD, emails, lógica de negocio
  • Métodos sin relación entre sí
  • Difícil de mantener y entender
  • Alta probabilidad de introducir bugs al cambiar
Alta cohesión
  • Cada clase tiene un único propósito claro
  • Los métodos usan los atributos de la clase
  • Código reutilizable y comprensible
  • Fácil de cambiar sin efectos secundarios
Tipos de cohesión (de mayor a menor calidad)

Funcional → Secuencial → Comunicacional → Procedimental → Temporal → Lógica → Coincidental

Maximize Cohesion
Ejemplo en C#
❌ BAJA COHESIÓN
C#
public class Employee
{
  public string Name { get; set; }
  public decimal Salary { get; set; }

  // Lógica de negocio
  public decimal CalculateTax() => Salary * 0.25m;

  // Acceso a datos (otra responsabilidad)
  public void Save() { /* SQL directo */ }

  // Notificaciones (otra responsabilidad)
  public void SendWelcomeEmail() { /* SMTP */ }

  // Reportes (otra responsabilidad)
  public string GeneratePdfReport() => "...";
}
✓ ALTA COHESIÓN
C#
public class Employee  // solo datos + lógica propia
{
  public string Name { get; set; }
  public decimal Salary { get; set; }
  public decimal CalculateTax() => Salary * 0.25m;
}

public class EmployeeRepository // persistencia
{
  public void Save(Employee e) { /* DB */ }
}

public class EmployeeNotifier   // notificaciones
{
  public void SendWelcome(Employee e) { /* Email */ }
}

public class EmployeeReporter   // reportes
{
  public string GeneratePdf(Employee e) => "...";
}
Principio 3
Law of Demeter
Definición
"No hables con desconocidos." Un objeto debe interactuar solo con sus colaboradores directos, nunca navegar por cadenas de objetos para acceder a datos.
Un método solo puede llamar a:
  • 1Métodos del propio objeto (this)
  • 2Métodos de sus atributos directos
  • 3Métodos de objetos recibidos como parámetros
  • 4Métodos de objetos creados localmente en el método
❌ Violación LoD
// "Cadena de trenes"
string city = customer
  .GetAddress()
  .GetCity()
  .GetName();  // ❌
✓ Cumple LoD
// Customer expone lo necesario
string city = customer
  .GetCityName();   // ✓

// Customer internamente accede
// a Address y City
Law of Demeter
Ejemplo completo en C#
❌ VIOLA LoD
C#
public class Invoice
{
  public void Print(Customer customer)
  {
    // Viaja por Customer→Address→City→Name
    var city = customer
      .GetAddress()
      .GetCity()
      .GetName();  // ❌ 3 niveles de profundidad

    Console.WriteLine($"Ciudad: {city}");
  }
}
✓ CUMPLE LoD
C#
public class Customer
{
  private Address _address;

  // Customer delega internamente
  public string GetCityName()
    => _address.GetCityName();
}

public class Invoice
{
  public void Print(Customer customer)
  {
    // Solo habla con el colaborador directo
    var city = customer.GetCityName();  // ✓
    Console.WriteLine($"Ciudad: {city}");
  }
}
SOLID — S
Single Responsibility Principle
Definición (Robert C. Martin)
"Una clase debe tener una, y solo una, razón para cambiar."
❌ VIOLA SRP
C#
public class Report
{
  public string Title;

  // Responsabilidad 1: lógica de negocio
  public string GenerateContent() => "...";

  // Responsabilidad 2: persistencia
  public void SaveToDb() { /* SQL */ }

  // Responsabilidad 3: presentación
  public void PrintToPdf() { /* PDF lib */ }
}
✓ CUMPLE SRP
C#
public class Report        // solo lógica
{
  public string Title;
  public string GenerateContent() => "...";
}

public class ReportRepository  // persistencia
{
  public void Save(Report r) { /* SQL */ }
}

public class ReportPrinter     // presentación
{
  public void PrintToPdf(Report r) { }
}

"Razón para cambiar": Si cambia el formato PDF, solo toca ReportPrinter. Si cambia la BD, solo toca ReportRepository.

SOLID — O
Open/Closed Principle
Definición (Bertrand Meyer)
"El software debe estar abierto para extensión pero cerrado para modificación."
❌ VIOLA OCP
C#
public class AreaCalc
{
  public double Calculate(object shape)
  {
    if (shape is Circle c)
      return Math.PI * c.Radius * c.Radius;
    if (shape is Rectangle r)
      return r.Width * r.Height;
    // ❌ Hay que editar aquí por cada forma nueva
    return 0;
  }
}
✓ CUMPLE OCP
C#
public abstract class Shape
{
  public abstract double Area();
}

public class Circle : Shape
{
  public double Radius;
  public override double Area()
    => Math.PI * Radius * Radius;
}
public class Triangle : Shape  // ✓ Nueva forma: no modifica nada
{
  public double Base, Height;
  public override double Area() => Base * Height / 2;
}
SOLID — L
Liskov Substitution Principle
Definición (Barbara Liskov, 1987)
"Los objetos de una subclase deben poder reemplazar a los de su clase base sin alterar el comportamiento correcto del programa."
❌ VIOLA LSP
C#
public class Rectangle
{
  public virtual int Width  { get; set; }
  public virtual int Height { get; set; }
  public int Area() => Width * Height;
}
public class Square : Rectangle
{
  public override int Width
  { set { base.Width = base.Height = value; } }
  public override int Height
  { set { base.Width = base.Height = value; } }
}
// Resize(r, 5, 3) → espera área 15
// Con Square devuelve 9 ❌
✓ CUMPLE LSP
C#
public abstract class Shape
{
  public abstract int Area();
}
public class Rectangle : Shape
{
  public int Width, Height;
  public override int Area() => Width * Height;
}
public class Square : Shape
{
  public int Side;
  public override int Area() => Side * Side;
}
// ✓ Ambas sustituibles como Shape
SOLID — I
Interface Segregation Principle
Definición (Robert C. Martin)
"Los clientes no deben ser forzados a depender de interfaces que no utilizan."
❌ INTERFAZ GORDA
C#
public interface IWorker
{
  void Work();
  void Eat();
  void Sleep();
}
public class Robot : IWorker
{
  public void Work()  { /* OK */ }
  public void Eat()   // ❌ Los robots no comen
    => throw new NotImplementedException();
  public void Sleep() // ❌ Los robots no duermen
    => throw new NotImplementedException();
}
✓ INTERFACES SEGREGADAS
C#
public interface IWorkable  { void Work(); }
public interface IFeedable  { void Eat(); }
public interface ISleepable { void Sleep(); }

public class Robot : IWorkable  // ✓ Solo lo necesario
{
  public void Work() { /* OK */ }
}

public class HumanWorker : IWorkable, IFeedable, ISleepable
{
  public void Work()  { }
  public void Eat()   { }
  public void Sleep() { }
}

Ejercicio 1 Single Responsibility Principle Cohesión
Identificar y Refactorizar

Consigna: La siguiente clase UserManager viola el SRP. Identifica cuántas responsabilidades tiene y refactoriza separándolas en clases de alta cohesión.

C# — Código a refactorizar
public class UserManager
{
  private List<User> _users = new();

  public void AddUser(User u)   { _users.Add(u); }
  public void RemoveUser(User u) { _users.Remove(u); }

  public void SaveToDatabase(User u)
    { /* Conexión SQL, INSERT INTO users... */ }

  public void SendWelcomeEmail(User u)
    { /* Conexión SMTP, envío de email */ }

  public string GenerateUserReport()
    { return "Reporte de usuarios..."; }

  public bool ValidatePassword(string password)
    { return password.Length >= 8; }
}
Solución

La clase tiene 4 responsabilidades: gestión de usuarios, persistencia, notificaciones y reportes. Se separan así:

C# — Refactorizado
public class UserService          // gestión + validación
{
  private List<User> _users = new();
  public void AddUser(User u)    { _users.Add(u); }
  public void RemoveUser(User u) { _users.Remove(u); }
  public bool ValidatePassword(string p) => p.Length >= 8;
}
public class UserRepository       // persistencia
{
  public void Save(User u) { /* SQL */ }
}
public class UserNotifier         // notificaciones
{
  public void SendWelcomeEmail(User u) { /* SMTP */ }
}
public class UserReporter         // reportes
{
  public string GenerateReport() => "Reporte...";
}
Ejercicio 2 Minimize Coupling Inyección de Dependencias
Reducir Acoplamiento

Consigna: NotificationService está fuertemente acoplado. Refactoriza para que pueda funcionar con cualquier sistema de notificación (Email, SMS, Push) sin modificar la clase.

C# — Código con acoplamiento fuerte
public class NotificationService
{
  private GmailClient _gmail = new GmailClient();   // ❌
  private TwilioSms   _sms   = new TwilioSms();     // ❌

  public void Notify(string user, string message)
  {
    _gmail.SendEmail(user, message);
    _sms.SendText(user, message);
  }
}
C# — Bajo acoplamiento
public interface INotifier
{
  void Notify(string user, string message);
}

public class GmailNotifier  : INotifier { public void Notify(string u, string m) { /* Gmail */ } }
public class SmsNotifier    : INotifier { public void Notify(string u, string m) { /* SMS */ } }
public class PushNotifier   : INotifier { public void Notify(string u, string m) { /* Push */ } }

public class NotificationService
{
  private readonly IEnumerable<INotifier> _notifiers;

  public NotificationService(IEnumerable<INotifier> notifiers)
    => _notifiers = notifiers;  // ✓ DI

  public void Notify(string user, string msg)
    => _notifiers.ToList().ForEach(n => n.Notify(user, msg));
}

Ahora se puede agregar WhatsAppNotifier sin tocar NotificationService. Aplica también OCP.

Ejercicio 3 Law of Demeter
Corregir Cadenas de Llamadas

Consigna: El método PrintInvoice viola la Ley de Demeter en tres lugares. Identifícalos y refactoriza aplicando delegación.

C# — Código con violaciones LoD
public class InvoicePrinter
{
  public void PrintInvoice(Order order)
  {
    // Violación 1: navegar Order → Customer → Address → City
    string city = order.GetCustomer().GetAddress().GetCity();

    // Violación 2: navegar Order → Items → first → Product → Name
    string firstItem = order.GetItems()[0].GetProduct().GetName();

    // Violación 3: navegar Order → Payment → Method → Description
    string payDesc = order.GetPayment().GetMethod().GetDescription();

    Console.WriteLine($"{city} | {firstItem} | {payDesc}");
  }
}
C# — Con delegación (LoD)
public class Order
{
  public string GetCustomerCity()      => _customer.GetCity();
  public string GetFirstItemName()     => _items[0].GetProductName();
  public string GetPaymentDescription() => _payment.GetDescription();
}

public class InvoicePrinter
{
  public void PrintInvoice(Order order)
  {
    string city     = order.GetCustomerCity();       // ✓
    string firstItem = order.GetFirstItemName();     // ✓
    string payDesc   = order.GetPaymentDescription();// ✓
    Console.WriteLine($"{city} | {firstItem} | {payDesc}");
  }
}

InvoicePrinter ahora solo habla con Order. Si cambia la estructura interna de Customer o Payment, InvoicePrinter no necesita cambiar.

Ejercicio 4 Liskov Substitution Principle
Detectar Violación de LSP

Consigna: Analiza este diseño de jerarquía de aves. ¿Qué ocurre cuando se llama a MakeItFly() con un Pingüino? ¿Cómo se soluciona?

C# — Violación LSP
public class Bird
{
  public virtual void Fly() => Console.WriteLine("Volando...");
}

public class Eagle  : Bird { } // ✓ un águila vuela

public class Penguin : Bird
{
  public override void Fly()  // ❌ El pingüino no puede volar
    => throw new InvalidOperationException("¡No puedo volar!");
}

// El código cliente explota con Penguin:
public void MakeItFly(Bird bird) => bird.Fly(); // ❌ lanza excepción
C# — Jerarquía corregida
public abstract class Bird
{
  public abstract void Move();  // todos los pájaros se mueven
}

public interface IFlyable { void Fly(); }

public class Eagle : Bird, IFlyable
{
  public override void Move() => Fly();
  public void Fly() => Console.WriteLine("Volando...");
}
public class Penguin : Bird   // ✓ No implementa IFlyable
{
  public override void Move() => Console.WriteLine("Nadando...");
}

// Solo las aves que vuelan reciben IFlyable:
public void MakeItFly(IFlyable bird) => bird.Fly(); // ✓ seguro

Separar la capacidad de volar en IFlyable aplica también ISP. El compilador garantiza que nadie llame a Fly() en un pingüino.

Ejercicio 5 Open / Closed Principle
Extender sin Modificar

Consigna: La clase Discount viola OCP: cada vez que se agrega un tipo de descuento hay que editar Calculate(). Refactoriza para que nuevos tipos se agreguen sin modificar código existente.

C# — Viola OCP
public class Discount
{
  public decimal Calculate(string type, decimal price)
  {
    if (type == "Student")   return price * 0.80m;
    if (type == "Employee")  return price * 0.70m;
    if (type == "VIP")       return price * 0.50m;
    // ❌ Cada nuevo tipo requiere editar este método
    return price;
  }
}
C# — Cumple OCP
public abstract class Discount
{
  public abstract decimal Calculate(decimal price);
}

public class StudentDiscount  : Discount
  { public override decimal Calculate(decimal p) => p * 0.80m; }

public class EmployeeDiscount : Discount
  { public override decimal Calculate(decimal p) => p * 0.70m; }

public class VIPDiscount      : Discount
  { public override decimal Calculate(decimal p) => p * 0.50m; }

// ✓ Nuevo tipo: solo agregar clase, sin tocar las existentes
public class SeniorDiscount   : Discount
  { public override decimal Calculate(decimal p) => p * 0.75m; }

// Uso:
public decimal ApplyDiscount(Discount d, decimal price)
  => d.Calculate(price);
Ejercicio 6 Interface Segregation Principle
Dividir una Interfaz Gorda

Consigna: IMultifunctionDevice obliga a todas las impresoras a implementar fax y escáner, aunque no tengan esa capacidad. Aplica ISP para resolverlo.

C# — Interfaz gorda
public interface IMultifunctionDevice
{
  void Print(Document doc);
  void Scan(Document doc);
  void Fax(Document doc);
  void Copy(Document doc);
}

public class OldPrinter : IMultifunctionDevice
{
  public void Print(Document doc) { /* OK */ }
  public void Scan(Document doc)  => throw new NotSupportedException();  // ❌
  public void Fax(Document doc)   => throw new NotSupportedException();  // ❌
  public void Copy(Document doc)  => throw new NotSupportedException();  // ❌
}
C# — Interfaces segregadas
public interface IPrinter { void Print(Document d); }
public interface IScanner { void Scan(Document d);  }
public interface IFax     { void Fax(Document d);   }
public interface ICopier  { void Copy(Document d);  }

// Impresora básica: solo IPrinter
public class OldPrinter : IPrinter
{
  public void Print(Document d) { /* OK ✓ */ }
}

// Impresora multifunción: implementa todo
public class AllInOne : IPrinter, IScanner, IFax, ICopier
{
  public void Print(Document d) { }
  public void Scan(Document d)  { }
  public void Fax(Document d)   { }
  public void Copy(Document d)  { }
}
Ejercicio 7 Cohesión + Acoplamiento Diseño integrador
Reestructurar un Módulo de Pagos

Consigna: La clase PaymentProcessor tiene baja cohesión y alto acoplamiento. Identifica los problemas y propón el diseño refactorizado aplicando todos los principios vistos.

C# — Diseño con múltiples problemas
public class PaymentProcessor
{
  private MySqlConnection _conn = new MySqlConnection(); // AC

  public void ProcessVisa(decimal amount)  { /* Visa API */ }
  public void ProcessMaster(decimal amount){ /* Master API*/ }
  public void SaveTransaction(Tx tx) { _conn.Execute("INSERT..."); }
  public void SendReceipt(string email)  { /* SMTP directo */ }
  public string GenerateReport() { return "reporte"; }
  public bool ValidateCard(string number) { return number.Length==16; }
}
Diagnóstico de problemas
  • Coupling fuerte: MySqlConnection instanciada directamente.
  • Baja cohesión / SRP: procesa pagos, persiste, notifica y genera reportes.
  • OCP: métodos separados por tarjeta (si llega PayPal, hay que modificar la clase).
C# — Diseño refactorizado
public interface IPaymentGateway { void Process(decimal amount); }
public class VisaGateway    : IPaymentGateway { public void Process(decimal a){} }
public class MasterGateway  : IPaymentGateway { public void Process(decimal a){} }

public class CardValidator   { public bool IsValid(string n) => n.Length==16; }
public class TransactionRepo { public void Save(Tx t) { /* inyecta IDbContext */ } }
public class ReceiptSender   { public void Send(string e) { /* inyecta IMailer */  } }
public class PaymentReporter { public string Generate() => "reporte"; }

public class PaymentProcessor  // ✓ alta cohesión: solo orquesta
{
  private readonly IPaymentGateway _gateway;
  private readonly TransactionRepo _repo;
  private readonly ReceiptSender   _mailer;
  public PaymentProcessor(IPaymentGateway gw, TransactionRepo r, ReceiptSender m)
    => (_gateway, _repo, _mailer) = (gw, r, m);
  public void Process(decimal amount, string email)
  {
    _gateway.Process(amount);
    _repo.Save(new Tx { Amount = amount });
    _mailer.Send(email);
  }
}
