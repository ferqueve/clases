¿Qué es un patrón?

Es una guía general para resolver un problema común dentro de un contexto específico de diseño de software.

Sí es

Una solución probada, nombrable, comunicable y reutilizable conceptualmente.

No es

Un fragmento de código mágico que se copia y pega sin entender el problema.

¿Para qué sirven?


Evitar reinventar la rueda

Mejorar comunicación técnica

Código más mantenible y flexible
Aplicarlos mal puede agregar complejidad. Primero se entiende el problema; luego se elige el patrón.

Repaso: principios SOLID

SRP — una clase debería tener una sola razón para cambiar.
OCP — abierta a extensión, cerrada a modificación.
LSP — una subclase debe poder sustituir a su superclase.
ISP — mejor interfaces específicas que interfaces gigantes.
DIP — los módulos de alto nivel no dependen de detalles; ambos dependen de abstracciones.

Familias de patrones

Creacionales

Controlan cómo se crean objetos separando instanciación de lógica. Ej.: Singleton, Factory, Builder, Prototype.

Estructurales

Organizan clases u objetos para formar estructuras flexibles. Ej.: Adapter, Bridge, Decorator, Facade, Proxy, DAO, Repository.

Comportamiento

Definen cómo interactúan los objetos y distribuyen responsabilidades. Ej.: Observer, Command, State, Strategy.

MVC: patrón de arquitectura

Organiza la aplicación en Modelo, Vista y Controlador. Separa datos y reglas de negocio de la presentación y de la entrada del usuario.

Modelo
datos, reglas, comportamiento no visual
Controlador
eventos, coordinación, acciones
Vista
HTML, UI, visualización

Idea clave: la Vista presenta; el Controlador interpreta acciones; el Modelo no debería depender de la interfaz.

Patrones creacionales

Singleton

Garantiza una única instancia y un punto global de acceso. Útil en cola de impresión, motor de juego o configuración.

Factory Method

Encapsula la creación de objetos y permite decidir qué clase concreta instanciar.

Builder

Construye objetos complejos paso a paso sin crear constructores interminables.

Prototype

Crea objetos copiando prototipos existentes cuando construir desde cero es costoso o complejo.

Patrones estructurales

Adapter
Hace compatibles interfaces que no encajan.
Bridge
Separa abstracción e implementación.
Decorator
Agrega responsabilidades sin modificar la clase original.
Facade
Da una entrada simple a un subsistema complejo.
Proxy
Controla el acceso a otro objeto.
DAO / Repository
Aíslan el acceso a datos y la persistencia.

Patrones de comportamiento

Se ocupan de algoritmos, comunicación e interacción entre objetos, distribuyendo responsabilidades para reducir acoplamiento.

Chain of Responsibility

Command

Observer

Mediator

Memento

State

Strategy

Visitor

Command en una idea

Convierte una solicitud en un objeto independiente que contiene toda la información necesaria para ejecutarla.

interface Comando { ejecutar(); }
class EncenderLuz implements Comando {
  ejecutar(){ luz.encender(); }
}
controlRemoto.setComando(new EncenderLuz());
controlRemoto.presionarBoton();

Sirve para desacoplar quién pide una acción de quién sabe realizarla, y facilita colas, historial y deshacer.

Cierre de la unidad

Los patrones ayudan a nombrar soluciones, comunicar diseños y reducir acoplamiento. Pero la decisión correcta no es “usar patrones”, sino entender el problema y elegir una estructura que haga el sistema más claro.

Actividad sugerida: tomar una funcionalidad conocida, identificar responsabilidades, dependencias y proponer un patrón aplicable justificando por qué.
