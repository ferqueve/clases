Antes de empezar

DevOps para tontos

No sos tonto. Es que nadie te explicó esto empezando por el principio. Acá va, en orden, sin dar nada por sabido.

La idea en una frase

Antes, un equipo escribía el software (Desarrollo) y otro equipo distinto lo hacía funcionar en los servidores (Operaciones), y se llevaban mal porque uno quería cambiar cosas rápido y el otro quería que nada se rompa. DevOps es la forma de que esos dos mundos trabajen juntos, con herramientas que automatizan todo el camino entre "escribí código" y "ya lo está usando la gente".

El mapa completo

1 · Qué es DevOps→ 2 · Despliegues→ 3 · Git→ 4 · Docker→ 5 · GitHub Actions→ 6 · Python/Flask→ 7 · Quiz

El orden importa: primero entendés por qué existe todo esto (1-2), después las herramientas que lo hacen posible (3-5), y por último un poco de código de ejemplo (6).

Paso 1

¿Qué es DevOps, en serio?

Ni una herramienta, ni un puesto de trabajo. Es una forma de trabajar.

Analogía

Pensá en una fábrica de autos donde el diseñador y el que arma el auto en la línea de producción nunca hablan entre sí. El diseñador manda el plano por mail una vez al año y el de la línea se las arregla como puede. Resultado: autos con errores, entregas tardías, y los dos equipos peleados. DevOps es juntar a esas dos personas en el mismo pasillo, con un proceso claro y automatizado para pasar del plano al auto terminado.

Definición "de libro"

"DevOps es la unión de Personas, Procesos y Productos para hacer posible la entrega de valor a nuestros usuarios finales." — Donovan Brown

Las 4 ideas que sí o sí tenés que tener claras

Colaboración

Desarrollo (Dev) y Operaciones (Ops) dejan de ser equipos separados que se tiran la pelota.

Automatización

Todo lo que se hace a mano y se repite (testear, empaquetar, subir a producción) se automatiza.

Despliegue frecuente

En vez de un lanzamiento gigante cada 6 meses, se suben cambios chicos todo el tiempo.

Infraestructura como código

Los servidores se configuran con archivos de texto (código), no clickeando a mano en una pantalla.

Mitos que tenés que poder desmentir

"Es solo para empresas tipo Netflix" "Reemplaza a las metodologías Ágiles" "Elimina el área de Operaciones" "Es lo mismo que Infraestructura como Código"

Todo falso. Ágil es un facilitador de DevOps (no un competidor), y Operaciones no desaparece: se vuelve más importante, porque ahora participa en todo el ciclo de vida del software, no solo al final.

De dónde viene esto (rapidito)

CuándoQué pasó
1946–1975Toyota inventa su sistema de producción (LEAN): pedir solo lo necesario, mejora continua, cero desperdicio.
2001Nace el Manifiesto Ágil: priorizar el software funcionando por sobre la documentación eterna.
2008Patrick Debois y Andrew Shafer empiezan a aplicar ideas ágiles a la infraestructura de servidores.
2009Charla "10+ Deploys per Day" en Flickr muestra que Dev y Ops pueden trabajar juntos. Nace la palabra "DevOps" en Ghent, Bélgica.

¿Para qué sirve todo esto al final?

Para poder responder rápido cuando el mercado cambia. Necesitás: lanzar cosas rápido (Time To Market), que el servicio no se caiga (SLA) y poder probar ideas sin miedo (experimentación).

Paso 2

Gestión de despliegues

"Desplegar" = poner el software a correr en algún lado. Acá está toda la teoría de cómo hacerlo bien.

Analogía

Es como mudarte de casa. Podés tirar todos los muebles viejos a la calle y meter los nuevos de golpe (arriesgado, si algo no entra por la puerta estás en problemas), o podés armar la casa nueva primero, con calma, y recién cuando está lista mudarte vos (mucho más seguro). Las estrategias de despliegue son distintas formas de "mudarte" sin dejar a la gente sin casa en el medio.

Dos palabras que no son lo mismo

Desplegar

Instalar una versión del software en algún ambiente (puede ser uno de prueba).

Liberar

Que los usuarios reales empiecen a usar esa funcionalidad. Implica tener un plan B (rollback) por si sale mal.

El camino que recorre el código

Integración→ Aceptación→ UAT→ Staging→ Producción

En cada flecha hay una "compuerta": alguien (o algo automático) tiene que aprobar que el código pase a la siguiente etapa.

Las estrategias, explicadas simple

RedespliegueApagás todo y volvés a instalar la última versión que funcionaba. Simple, pero hay downtime (el servicio queda caído un rato).
Blue-GreenTenés dos copias idénticas del sistema (azul y verde). Los usuarios usan la azul mientras probás todo en la verde. Cuando estás seguro, un router redirige el tráfico a la verde. Volver atrás = redirigir de nuevo.
CanaryComo Blue-Green, pero en vez de mover a todos de golpe, mandás solo un 10-20% del tráfico real a la versión nueva primero, para ver si explota algo antes de afectar a todos.
Rolling updateTípico de contenedores: vas reemplazando servidores viejos por nuevos de a uno, sin apagar todo junto. El servicio nunca se cae del todo.
Feature togglesUn "interruptor" en el código. Subís la funcionalidad apagada, y la prendés cuando querés — sin volver a desplegar nada.
Despliegue a oscurasSubís la funcionalidad a producción pero invisible para el usuario, solo para probar que aguanta el tráfico real, antes de mostrarla.

Regla de oro para arreglos urgentes (hotfix)

Aunque tengas apuro, no te saltes el proceso (probar → desplegar → testear). Muchas veces es más seguro hacer rollback a la versión anterior que meter un arreglo apurado sin probar.

Paso 3

Git — la base de todo

Antes de hablar de Docker o de automatizar nada, necesitás Git: es donde vive el código.

Analogía

Git es una máquina del tiempo para tus archivos. Cada vez que hacés un commit, guardás una "foto" de cómo estaba todo en ese momento. Si rompés algo, podés volver a cualquier foto anterior. Y como varias personas pueden trabajar en "ramas" (branches) distintas al mismo tiempo, es como tener universos paralelos que después se juntan (merge).

Los comandos que realmente vas a usar

ComandoQué hace, en criollo
git clone <url>Traé una copia del repositorio a tu compu
git status¿Qué cambié y qué falta guardar?
git add <archivo>"Poné este cambio en la lista para guardar"
git commit -m "mensaje"Guardá la foto, con una nota de qué cambiaste
git pushSubí tus fotos guardadas al repositorio remoto (GitHub)
git pullTraé los cambios que subieron otros
git checkout -b <rama>Creá tu propio universo paralelo para probar algo
git merge <rama>Juntá esa rama con la que estás parado ahora
git logVer el historial de fotos guardadas
git revert <commit>Deshacer un cambio puntual, sin borrar el historial

Todo lo demás (rebase, reflog, cherry-pick...) lo aprendés cuando lo necesites. Con esta lista sobrevivís el 90% de los casos.

Paso 4

Docker — empaquetar tu app

El problema que Docker resuelve: "en mi compu funciona" y en el servidor no.

Analogía

Un contenedor Docker es como una caja de mudanza sellada: adentro va tu aplicación con TODO lo que necesita para funcionar (versión exacta de Python, librerías, configuración). No importa a qué "casa" (servidor) lleves la caja: al abrirla, todo funciona exactamente igual, porque no depende de lo que ya había en esa casa.

El flujo básico

Dockerfile (la receta)— build → Imagen (la caja armada)— run → Contenedor (la caja funcionando)

Un Dockerfile explicado línea por línea

# De qué "base" partimos
FROM python:3.8-slim

# Carpeta de trabajo adentro del contenedor
WORKDIR /usr/src/app

# Copiamos la lista de dependencias
COPY requirements.txt .

# Las instalamos
RUN pip install --no-cache-dir -r requirements.txt

# Copiamos el resto del código
COPY . .

# Puerto que la app va a usar
EXPOSE 5000

# Comando que arranca la app
CMD ["python", "app.py"]

Los dos comandos que hacen todo

# 1. Armar la caja (la imagen) a partir de la receta
docker build -t mi-app .

# 2. Abrir la caja y ponerla a funcionar (el contenedor)
docker run -d --name mi-app-corriendo -p 5000:5000 mi-app
No te olvides: parar los contenedores que no estás usando (docker stop), o te comen recursos de la máquina.
Paso 5

GitHub Actions — el robot que hace el trabajo

Ya tenés el código (Git) y sabés empaquetarlo (Docker). Ahora falta que nadie tenga que hacer nada a mano.

Analogía

Es como dejar un robot contratado que vive adentro de GitHub. Vos le decís "cada vez que alguien suba código nuevo, corré los tests, y si pasan, armá la caja de Docker y mandala al servidor". El robot lo hace solo, sin que nadie tenga que acordarse de hacerlo a mano ni cometer el error de saltearse un paso.

Vocabulario básico

PalabraQué es
WorkflowEl proceso completo, escrito en un archivo YAML dentro de .github/workflows/
Event (evento)Lo que dispara el robot: push, pull_request, un horario (schedule), o un botón manual
JobUn grupo de tareas que corre en una máquina virtual (el "runner")
StepUn paso individual: un comando, o una "acción" ya hecha por otros

Un workflow real, comentado

# .github/workflows/ci.yml
name: CI

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - name: Clonar el repo
        uses: actions/checkout@v4

      - name: Configurar Python
        uses: actions/setup-python@v5
        with:
          python-version: '3.11'

      - name: Instalar dependencias
        run: pip install -r requirements.txt

      - name: Correr tests
        run: pytest

Traducido: "cada vez que alguien haga push o abra un pull request contra main, cloná el repo, instalá Python, instalá las dependencias, y corré los tests". Si algo falla, GitHub avisa antes de que ese código llegue a producción.

Casos prácticos (para qué se usa en la vida real)

1 · Integración continua (CI)Correr tests automáticamente en cada cambio, antes de aprobar el merge.
2 · Build & push de imagen DockerArmar la imagen y subirla a un registry cuando se aprueba un cambio en main.
3 · Despliegue automatizado (CD)Conectarse al servidor y aplicar un rolling update o Blue-Green automáticamente tras el build exitoso.
4 · Tareas programadasBackups nocturnos, chequeos de salud de un servicio — con on: schedule.
5 · Control de calidadCorrer un linter o análisis de seguridad en cada pull request, bloqueando el merge si falla.
6 · Disparo manualUn botón en GitHub (workflow_dispatch) para lanzar un despliegue a demanda, por ejemplo un hotfix ya aprobado.
Paso 6

Python & Flask — la parte de código

Flask es la forma más simple de exponer tu código como algo que se puede llamar por internet (una API).

Una ruta Flask, mínima

from flask import Flask, jsonify, request
app = Flask(__name__)

@app.route('/hello')
def hello():
    return jsonify({"mensaje": "Hola!"})

# con un parámetro en la URL
@app.route('/square/<int:num>')
def square(num):
    return jsonify({"resultado": num ** 2})

# recibiendo datos (POST)
@app.route('/libro', methods=['POST'])
def libro():
    datos = request.get_json()
    return jsonify(datos), 201

Automatización simple con Python (lo que usarías en DevOps real)

  • os.system("ping -c 2 " + host) → ¿este servidor responde?
  • shutil.copy(origen, destino) → hacer un backup de un archivo de configuración
  • subprocess.run([...], capture_output=True) → correr un comando del sistema y leer el resultado (ej. systemctl is-active)

Nada de esto es magia: son las mismas herramientas de siempre, aplicadas a "administrar servidores" en vez de "resolver un ejercicio".
