La consigna

Qué se pide al grupo

Dentro de un proyecto llamado deploy-de-app-python, con Dokku ya instalado:

Parte A · con fork

Hacer un fork de openshift/django-ex en tu cuenta personal de GitHub, con el nombre django-exarcc-nombregrupo. Desde ese fork, desplegar la aplicación Python de ejemplo en Dokku usando la ruta por defecto.

Parte B · sin fork

Desplegar jjasghar/cloud-native-python-example-app sin hacer un fork, también con la ruta por defecto.

Qué se entrega

Un PDF por grupo con las configuraciones de lo pedido y los nombres de todos los integrantes. Incluí imágenes de todo el procedimiento, incluido el fork del proyecto.

«Ruta por defecto». Es la URL que Dokku asigna a la aplicación sin que configures dominios extra. Se ve al final del git push.

Atención · el repositorio cambió

django-ex ya no tiene el código en master

Si hacés el fork con la configuración por defecto y desplegás master, Dokku no encuentra una aplicación Python: esa rama hoy es solo un README.

Al hacer el fork

Dónde vive hoy

El README indica que el proyecto se mantiene en sclorg/django-ex. La consigna pide openshift/django-ex, que sigue existiendo con las mismas ramas.

Parte A · paso 1 de 5

Hacer el fork en GitHub

Abrí el repositorio

Entrá a https://github.com/openshift/django-ex con tu cuenta personal.

Pulsá «Fork»

En la pantalla de creación, cambiá el nombre a django-exarcc-grupo1 (con el nombre de tu grupo).

Desmarcá «Copy the master branch only»

Es la casilla que impide que se copien las demás ramas. Si la dejás marcada, no tendrás 4.2.x.

Creá el fork y capturá

Captura 1: la página del fork mostrando tu usuario y el nombre django-exarcc-grupo1.

Si ya lo hiciste con master solamente

No hace falta borrarlo. En la página del fork, usá Sync fork y buscá la rama 4.2.x en el selector de ramas. Si no aparece, borrá el fork y repetí sin la casilla marcada.

Por qué se hace un fork. En esta parte vas a agregar un archivo (el Procfile). Con el fork tenés un repositorio propio donde guardar el cambio.
Parte A · paso 2 de 5

Clonar el fork y cambiar a la rama 4.2.x

Creamos la carpeta del proyecto, clonamos tu fork (no el original) y pasamos a la rama con el código.

$ cd deploy-de-app-python
$ git clone https://github.com/TU-USUARIO/django-exarcc-grupo1.git
$ cd django-exarcc-grupo1
$ git checkout 4.2.x
$ ls

Los archivos manage.py, requirements.txt, y las carpetas project y welcome. Es una aplicación Django.

Parte A · paso 3 de 5

Decirle a Dokku cómo arrancar la aplicación

El proyecto trae todo lo necesario para correr en OpenShift, pero no un Procfile. Sin él, el buildpack de Python instala las dependencias pero no sabe qué proceso web iniciar. Lo agregamos en la raíz del proyecto.

máquina de trabajo · carpeta del fork
$ printf '%s\n' 'web: python manage.py migrate --noinput && gunicorn project.wsgi --bind 0.0.0.0:$PORT --log-file -' > Procfile
$ cat Procfile
$ git add Procfile
$ git commit -m "Agrega Procfile para Dokku"
$ git push origin 4.2.x
Parte del comandoQué hace
web:Es el tipo de proceso que recibe tráfico HTTP
python manage.py migrate --noinputCrea las tablas de la base de datos al arrancar. Sin esto, la página de bienvenida falla
gunicorn project.wsgiServidor de producción para Django (en el módulo project/wsgi.py)
--bind 0.0.0.0:$PORTEscucha en el puerto que Dokku asigna en la variable $PORT
Fin de línea. Creá el archivo con el comando de arriba o con un editor que use final de línea LF. En Windows, usá Git Bash.
Parte A · paso 4 de 5

Crear la aplicación en Dokku y desplegar

Primero, en el servidor Dokku: creamos la aplicación y le decimos qué rama debe desplegar.

root@servidor Dokku
# dokku apps:create django-exarcc-grupo1
# dokku git:set django-exarcc-grupo1 deploy-branch 4.2.x

Después, en la máquina de trabajo, dentro de la carpeta del fork: agregamos el remote y subimos la rama.

máquina de trabajo · carpeta del fork
$ git remote add dokku dokku@192.168.5.186:django-exarcc-grupo1
$ git push dokku 4.2.x

Por qué git:set

Dokku despliega una rama concreta. El valor por defecto no es 4.2.x, así que se lo indicamos. Sin esto, el push termina sin construir nada.

Parte A · paso 5 de 5

Comprobar y observar

Abrí en el navegador la URL que mostró el push. Deberías ver la página de bienvenida de Django con el nombre del contenedor y un contador de visitas.

root@servidor Dokku
# dokku logs django-exarcc-grupo1 -t     # Ctrl+C para salir
# dokku ps:report django-exarcc-grupo1
# dokku apps:list

Experimento para el informe

Recargá la página varias veces y mirá cómo sube el contador. Después hacé un nuevo despliegue (git commit --allow-empty -m "redeploy" y git push dokku 4.2.x) y volvé a mirar el contador.

¿Qué pasó con el contador? Vuelve a cero. La aplicación guarda sus datos en un archivo SQLite dentro del contenedor, y cada despliegue crea un contenedor nuevo. Es lo que vimos en los 12 factores: el estado tiene que vivir afuera. Con un servicio como PostgreSQL enlazado, los datos sobrevivirían.

Parte B · paso 1 de 3

Clonar sin fork y mirar qué trae

Acá no hay fork: clonamos el repositorio original y solo lo enviamos a Dokku. No vamos a subir nada al repositorio ajeno.

máquina de trabajo · carpeta deploy-de-app-python
$ cd ..
$ git clone https://github.com/jjasghar/cloud-native-python-example-app.git
$ cd cloud-native-python-example-app
$ ls
$ cat Procfile Dockerfile app.py

app.py

Una aplicación Flask mínima. Responde en / y en /healthz, y escucha en el puerto 8080.

Procfile

Dice web: python app.py.

Dockerfile

Parte de la imagen python:3.7.7-slim, instala las dependencias y expone el puerto 8080.

Tiene Procfile y Dockerfile a la vez. Dokku, ante un Dockerfile, construye con él y deja de lado a los buildpacks. Es el principal contraste con la parte A.
Parte B · paso 2 de 3

Crear la aplicación y desplegar

root@servidor Dokku
# dokku apps:create cloud-native-python
# dokku git:set cloud-native-python deploy-branch master
máquina de trabajo · carpeta del repositorio clonado
$ git remote add dokku dokku@192.168.5.186:cloud-native-python
$ git push dokku master

La rama es master

El repositorio original usa master. Comprobalo con git branch si no estás seguro.

Va a tardar

Se construye una imagen de Docker con varias dependencias (entre ellas numpy y pandas). Esperá a que termine el push.

No hagas git push origin. El remote origin es el repositorio de otra persona. Solo usás el remote dokku.
Parte B · paso 3 de 3

Comprobar y resolver los problemas probables

Abrí la URL que mostró el push. Si todo salió bien, la página muestra el texto KubeCon2023. La ruta /healthz responde ok.

root@servidor Dokku
# dokku logs cloud-native-python
# dokku ports:report cloud-native-python
# dokku apps:list

La construcción falla en apt-get

La imagen base python:3.7.7-slim usa una versión de Debian muy antigua. Si el paso apt-get update da errores 404, cambiá en tu copia local la primera línea del Dockerfile a FROM python:3.7-slim-bookworm, hacé un commit y volvé a subir con git push dokku master.

Error 502 al abrir la página

El contenedor arrancó pero nginx no encuentra el puerto. La aplicación escucha en 8080. Verificá con ports:report y, si hace falta, mapealo: dokku ports:set cloud-native-python http:80:8080.

Para el informe. Si tuviste que cambiar algo para que funcione, documentalo: qué falló, qué mensaje apareció y qué cambiaste.
Para reflexionar

Dos aplicaciones, dos formas de construir

Parte A · django-exParte B · cloud-native-python
Cómo se construyeBuildpack de Python (detecta requirements.txt)Dockerfile del propio repositorio
Quién decide el entornoLa plataforma (versión de Python, sistema base)El autor de la aplicación (en la imagen)
Cómo se iniciaProcfile que agregamosCMD del Dockerfile
PuertoDokku lo entrega en $PORTLo fija la imagen (EXPOSE 8080)
Qué tuviste que tocarAgregar el Procfile y elegir la ramaNada, salvo que haya problemas con la imagen base
Dónde guardás los cambiosEn tu forkEn ningún repositorio propio
Idea de fondo. Un buildpack ahorra el trabajo del Dockerfile a cambio de aceptar las decisiones de la plataforma. Un Dockerfile da control total y también la responsabilidad de mantener la imagen.
