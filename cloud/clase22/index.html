Qué entrega un PaaS

Lo que hiciste en nueve módulos, empaquetado

construir

Del código a la imagen

Detecta el lenguaje, instala dependencias y arma lo ejecutable. Sin escribir un Dockerfile.

ejecutar

Procesos con red y balanceo

Asigna dirección, certificado y reparte pedidos entre réplicas (módulo 7).

operar

Escalado, logs, reinicios

Más réplicas con un número, logs agregados y reinicio automático si algo falla (módulo 8).

Ejemplos: Heroku, Google App Engine, Azure App Service, AWS Elastic Beanstalk, Render, Fly.io. En un servidor propio: Cloud Foundry o Dokku.

El contrato con la plataforma

La plataforma pide cosas a tu aplicación

lo que ganás

Velocidad y menos operación

  • Publicar es un comando o un push a Git
  • Sin parches del sistema operativo
  • Escalar es cambiar un número
  • Equipos chicos operan servicios grandes
lo que cedés

Control y libertad

  • Solo lenguajes y versiones soportados
  • Sin acceso al servidor ni a su disco
  • La app debe seguir las reglas de la plataforma
  • Mudarse a otro proveedor cuesta (dependencia)
Las reglas · 12 factores

Una aplicación pensada para la nube

Un decálogo de diseño que se hizo famoso con Heroku. Los cinco que más pesan en la práctica:

III · configuración

En variables de entorno

Nada de contraseñas ni direcciones dentro del código. El mismo programa corre en dev y producción.

IV · servicios de apoyo

Recursos conectables

La base de datos es un recurso al que se llega por una URL. Se cambia sin tocar el código.

VI · procesos

Sin estado local

Una réplica puede morir en cualquier momento. Lo que importa se guarda fuera.

IX · descartabilidad

Arranque rápido, cierre limpio

Las réplicas aparecen y desaparecen todo el tiempo.

XI · logs

Salida estándar

La app escribe en stdout y la plataforma los recoge. No administra archivos de log.

Configuración

Un mismo artefacto, distintos entornos

la misma imagen, dos configuraciones
# desarrollo
docker run -e WHOAMI_NAME=dev  imagen
# producción
docker run -e WHOAMI_NAME=prod imagen

# Lo que NO se hace:
# una imagen distinta para cada entorno,
# con la contraseña escrita adentro
por qué

Si cada entorno tiene su propia imagen, lo que probaste no es lo que desplegás. Con una sola imagen, lo único que cambia son las variables.

los secretos

Las variables sensibles las guarda la plataforma, o un gestor de secretos. Nunca el repositorio.

Procesos sin estado

Las réplicas son intercambiables

con estado local

El contador vive en la réplica

Cada réplica cuenta por su lado, y si una se reinicia, pierde todo. El resultado depende de a cuál le tocó el pedido.

estado afuera

El contador vive en un servicio

Todas las réplicas escriben en el mismo sitio. Se puede matar cualquiera sin perder datos.

Conecta con el módulo 7. Escalar horizontalmente solo funciona si las instancias son intercambiables. Las sesiones y los archivos subidos se guardan fuera: base de datos, caché u objetos.

Construir, publicar, ejecutar

Del código a un proceso en marcha

buildcódigo + dependencias → imagen
releaseimagen + configuración → versión
runla versión se ejecuta como procesos
rollbackvolver a una versión anterior
buildpacks

Detectan el lenguaje al ver archivos como package.json y arman la imagen sin Dockerfile. Es lo que usan Heroku y Cloud Foundry; el estándar abierto es Cloud Native Buildpacks.

cada release se numera

Código y configuración forman una versión con número. Volver atrás es activar la anterior, no reconstruir.

Servicios gestionados

Los datos no se gestionan en la plataforma

NecesidadServicio gestionadoQué se evita
Base de datosPostgreSQL, MySQL o MongoDB como servicioInstalar, respaldar, parchear, replicar
Caché y colasRedis, mensajeríaOperar clústeres propios
ArchivosAlmacenamiento de objetos (módulo 3)Guardar en el disco de una réplica
IdentidadAutenticación como servicioAlmacenar contraseñas propias

Se paga por conveniencia. Un servicio gestionado cuesta más que instalarlo vos, pero incluye respaldos, alta disponibilidad y parches. Es una cuenta de FinOps (Clase 13): el costo del tiempo de tu equipo cuenta.

Escalar y desplegar

Cómo cambia una versión sin cortar el servicio

escalado

Horizontal, por número

"Quiero 3 réplicas." La plataforma las crea y las pone detrás del balanceador. Algunas escalan solas por CPU o pedidos.

rolling

De a poco

Reemplaza las réplicas una por una. Hay mezcla de versiones por un rato, pero siempre hay servicio.

blue-green

Dos entornos completos

La versión nueva arranca aparte. Cuando está lista, se cambia el tráfico. Volver atrás es cambiarlo de nuevo.

Todo esto exige que la versión nueva y la vieja puedan coexistir: si cambia el esquema de la base, hay que hacerlo en pasos compatibles.

Cuándo elegir PaaS

Un criterio, no una regla

conviene PaaS

Aplicaciones web estándar

  • Equipo chico, sin personal de operaciones
  • Prototipos y productos nuevos
  • Aplicación que sigue los 12 factores
  • La velocidad vale más que el control fino
conviene IaaS o contenedores

Necesidades especiales

  • Software heredado que necesita el sistema operativo
  • Requisitos de red o hardware particulares
  • Costo alto a gran escala
  • Evitar la dependencia de un proveedor

Un camino intermedio es el de contenedores gestionados, como Kubernetes: más control que PaaS y menos trabajo que IaaS.

Práctica 2 · Réplicas, balanceo y estado afuera

PowerShell
# Limpiar la práctica anterior
docker rm -f app-dev app-prod app-staging

# Configuración de nginx: reparte entre las réplicas de "app"
@'
upstream apps { server app:80; }
server {
  listen 80;
  location / { proxy_pass http://apps; }
}
'@ | Out-File nginx.conf -Encoding ascii

# El archivo que describe la plataforma
@'
name: paas
services:
  app:
    image: traefik/whoami
    environment:
      WHOAMI_NAME: app-${VERSION:-v1}
    mem_limit: 64m
    networks: [red]
  proxy:
    image: nginx:alpine
    ports: ["8090:80"]
    volumes: ["./nginx.conf:/etc/nginx/conf.d/default.conf:ro"]
    depends_on: [app]
    networks: [red]
  db:
    image: redis:alpine
    mem_limit: 64m
    volumes: [datos:/data]
    networks: [red]
networks:
  red: {}
volumes:
  datos: {}
'@ | Out-File paas.yml -Encoding ascii

docker compose -f paas.yml config --quiet

# Ejercicio 2 levanta todo con 3 réplicas de app

# Los pedidos se reparten entre las réplicas
1..6 | ForEach-Object { curl.exe -s http://localhost:8090 | Select-String "Hostname" }

# El estado vive en db, no en las réplicas
docker compose -f paas.yml exec db redis-cli incr visitas
docker rm -f paas-app-1
docker compose -f paas.yml up -d --scale app=3
docker compose -f paas.yml exec db redis-cli get visitas
qué observar

Los seis pedidos muestran tres Hostname distintos, repartidos. Al borrar una réplica y recrearla, el contador de db se conserva.

captura

Los seis pedidos repartidos y el valor de visitas antes y después de borrar la réplica.

DocenteProbar antes de clase. nginx resuelve el nombre app al arrancar: levantar con las 3 réplicas desde el principio. Si se recrea una réplica y cambia su IP, reiniciar el proxy con restart proxy. El nombre paas-app-1 puede variar según la versión de Compose.

Práctica 3 · Publicar una versión, mirar los logs, volver atrás

PowerShell
# Versión actual: v1
curl.exe -s http://localhost:8090 | Select-String "Name"

# Publicar v2: solo cambia la configuración (ejercicio 3)

# Todas las réplicas cambiaron de versión
1..6 | ForEach-Object { curl.exe -s http://localhost:8090 | Select-String "Name" }

# Logs agregados de todas las réplicas (los logs salen por stdout)
docker compose -f paas.yml logs --tail 20 app

# Volver atrás: activar otra vez la versión anterior
$env:VERSION = "v1"
docker compose -f paas.yml up -d --scale app=3
curl.exe -s http://localhost:8090 | Select-String "Name"
qué observar

Antes del cambio las respuestas muestran app-v1. Después, app-v2. Al volver atrás, otra vez app-v1.

no es un rolling real

Compose recrea los contenedores cambiados casi a la vez, y puede haber un corte breve. Una plataforma real los reemplaza de a uno, esperando que cada nuevo responda antes de seguir.

CapturaLas respuestas con v1, con v2 y de nuevo con v1.
DocenteTras recrear las réplicas puede hacer falta docker compose -f paas.yml restart proxy para que nginx tome las IP nuevas. Probarlo y, si es necesario, indicarlo a los estudiantes.

Práctica 4 · Del código a la imagen con buildpacks

PowerShell
# Una aplicación mínima en Node.js, sin Dockerfile
mkdir miapp; cd miapp
@'
{ "name": "miapp", "version": "1.0.0", "scripts": { "start": "node server.js" } }
'@ | Out-File package.json -Encoding ascii
@'
const http = require("http");
http.createServer((req, res) => {
  res.end("Hola desde " + (process.env.ENTORNO || "sin entorno") + "\n");
}).listen(process.env.PORT || 8080);
'@ | Out-File server.js -Encoding ascii

# Ejercicio 4: construir la imagen con buildpacks

# Ejecutarla con su configuración
docker run -d --name miapp -e PORT=8080 -e ENTORNO=prueba -p 8095:8080 miapp
curl.exe http://localhost:8095

# Inspeccionar qué armó, sin que escribas nada
pack inspect miapp
docker history miapp --no-trunc | Select-Object -First 5
qué hace pack

Mira package.json, deduce que es Node.js, instala el entorno y las dependencias y construye una imagen. Tu aplicación sigue el contrato: toma el puerto y la configuración de variables.

instalación

winget install Buildpacks.pack-cli o descargar el ejecutable desde el sitio de Buildpacks.

DocenteNo probado: el comando de instalación, el nombre del builder y la cantidad de descarga (más de 1 GB la primera vez). Verificar que el entorno Node del builder encuentre package.json sin package-lock.json. Si falla, se puede dejar esta práctica como opcional o de demostración.
