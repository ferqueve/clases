Por dentro de la nube:
capas, piezas y "tamaños"

La Clase 1 nos dio el vocabulario. Hoy abrimos la caja: qué capas componen una arquitectura cloud, qué es un "flavor" de instancia y cómo se arman las aplicaciones pensadas para este mundo elástico.

Capas de arquitectura Flavors / instance types Patrones de aplicación
La caja por dentro

Las capas de una arquitectura cloud

Front-end

Lo que usa el cliente: navegador, app móvil, cliente de escritorio. Habla con el back-end vía APIs.

Back-end

Servidores, bases de datos, lógica de negocio — todo lo que corre del lado del proveedor.

Red / middleware

Conecta ambos lados: balanceadores, gateways de API, protocolos de comunicación.

Capa de virtualización

Convierte hardware físico en recursos lógicos: VMs, contenedores, redes virtuales.

Gestión y orquestación

Automatiza aprovisionamiento, escalado y monitoreo de todos los recursos anteriores.

Idea clave

Cada capa puede ser de un proveedor distinto. La arquitectura cloud rara vez es un solo bloque monolítico.

Los cuatro componentes que sostienen todo

Compute · Storage · Red · Virtualización

Compute

El poder de procesamiento: CPU y RAM asignados a cada carga de trabajo. Se empaqueta en "flavors" — lo vemos en un momento.

Storage

Discos de bloque, objetos (tipo S3) y sistemas de archivos, con distintos niveles de durabilidad y velocidad.

Red

Redes virtuales, subredes, firewalls y balanceadores que conectan todo sin cableado físico que vos toques.

Virtualización

El hipervisor: la pieza que le hace creer a cada VM que tiene el hardware para ella sola.

El concepto que vinimos a instalar hoy

¿Qué es un "flavor"?

Un flavor (o "instance type") es un perfil predefinido de recursos: cuánta CPU, cuánta RAM y cuánto disco recibe una instancia. En vez de armar cada VM "a medida", elegís de un catálogo de tamaños — como elegir talle de ropa en vez de mandarla a hacer.

Por qué existen

Simplifican la facturación, la capacidad y la planificación del proveedor — y te dan un punto de partida claro a vos.

Se eligen por carga de trabajo

Un servidor web liviano no necesita el mismo flavor que una base de datos o un proceso de cómputo intensivo.

Se pueden cambiar

"Resize" o "redimensionar" una instancia a otro flavor, sin rearmar todo desde cero — otra ventaja frente a hardware propio.

El mismo concepto, distintos nombres

Flavors según el proveedor

OpenStack

Se llaman flavors directamente: m1.small, m1.medium, m1.large — cada uno define vCPU, RAM y disco.

AWS

Se llaman instance types: t3.micro, m5.large, c5.xlarge — la letra indica familia (general, cómputo, memoria).

Azure

Se llaman VM sizes: Standard_B1s, Standard_D2s_v3 — mismo principio, distinta nomenclatura.

Distinto nombre, misma idea: un catálogo cerrado de combinaciones CPU/RAM/disco. En el laboratorio de virtualización vamos a crear nuestros propios flavors en Proxmox y medir cómo cambia el rendimiento real según el perfil elegido.

Pensar en distribución, no en un solo lugar

Regiones y zonas de disponibilidad

Región

Un área geográfica con uno o más centros de datos del proveedor (ej. "sur de Brasil", "este de EE.UU.").

Zona de disponibilidad

Centros de datos físicamente separados dentro de una misma región, con energía y red independientes.

Por qué importa

Distribuir tu aplicación entre zonas te protege de que un solo incidente físico tumbe todo el servicio.

Latencia

Elegir la región más cercana al usuario final reduce el tiempo de respuesta percibido.

Cómo se gobierna todo esto

Consola, CLI y API

Consola web

Buena para explorar y aprender, lenta para operar a escala o repetir tareas.

CLI

Comandos scripteables: crear, listar, redimensionar y borrar recursos desde una terminal.

API / Infra as Code

Todo recurso cloud es, en el fondo, una llamada a una API — la base de herramientas como Terraform.

En los laboratorios vamos a usar principalmente CLI: es donde realmente se entiende qué está pasando debajo de cada clic.

Cómo se arma software para este mundo

Patrones de aplicaciones en cloud

Monolito

Todo en una sola unidad desplegable. Simple al inicio, más rígido para escalar por partes.

Multi-tier

Capas separadas (presentación, lógica, datos), cada una escalable de forma independiente.

Microservicios

Servicios pequeños e independientes que se comunican por red — máxima elasticidad, más complejidad operativa.

Balanceo de carga elástico

Distribuye tráfico entre instancias y suma/quita instancias según demanda real.

Auto-scaling

Reglas automáticas que cambian la cantidad de instancias (o su flavor) sin intervención manual.
