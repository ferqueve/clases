Módulo 8 · por qué monitorear

No se puede operar lo que no se ve

métricas

Números en el tiempo

CPU, memoria, pedidos por segundo, latencia. Livianas y baratas. Responden: ¿cuánto y desde cuándo?

logs

Eventos con texto

Un renglón por cosa que pasó: un error, un acceso, un arranque. Responden: ¿qué pasó exactamente?

trazas

El camino de un pedido

Siguen un pedido entre servicios y miden cada tramo. Responden: ¿dónde se demora?

Son los tres pilares de la observabilidad de la Clase 9. En este módulo practicamos métricas y logs; las trazas aparecen cuando hay varios servicios.

Módulo 8 · métricas

Anatomía de una métrica

un dato de CloudWatch
namespace   Lab/App
métrica     Latencia
dimensión   Servicio = web
valor       120
unidad      Milliseconds
marca       2026-10-26T15:04:00Z
namespace

Agrupa métricas de un mismo origen. Los servicios del proveedor tienen los suyos, como AWS/EC2.

dimensiones

Etiquetas que dividen una métrica: por servicio, por instancia, por zona. Cada combinación distinta es una serie distinta.

resolución

Por defecto, un dato cada 5 minutos para una instancia, o cada minuto con monitoreo detallado.

Módulo 8 · estadísticas

El promedio esconde a los usuarios lentos

EstadísticaQué responde
AverageEl valor típico del período
MaximumEl peor caso observado
SumTotal: errores, bytes
SampleCountCuántos datos hubo
p99Lo que supera solo 1 de cada 100
un ejemplo

100 pedidos: 98 tardan 100 ms y 2 tardan 5000 ms. El promedio es 198 ms, que parece normal. El p99 es 5000 ms: esos dos usuarios esperaron 5 segundos.

para qué sirve cada una

Sum para contar errores. Average para uso de CPU. Percentiles para latencia.

Módulo 8 · qué medir

Cuatro señales doradas

latencia

¿Cuánto tarda?

Tiempo de respuesta, separando los pedidos exitosos de los fallidos.

tráfico

¿Cuánta demanda hay?

Pedidos por segundo, conexiones activas.

errores

¿Cuánto falla?

Proporción de respuestas con error, como las 5xx de un balanceador.

saturación

¿Cuánto falta para el límite?

CPU, memoria, disco o conexiones respecto del máximo.

Conecta con SLI y SLO de la Clase 9: el SLI es una de estas señales y el SLO es el valor que te comprometés a mantener.

Módulo 8 · alarmas

Una alarma vigila una métrica

OKla métrica está dentro del límite
ALARMsuperó el umbral las veces necesarias
INSUFFICIENT_DATAno llegan datos para decidir
acciónal cambiar de estado, se ejecuta algo

Cuándo falta el dato. Si una instancia cae, deja de enviar su métrica. La alarma queda en INSUFFICIENT_DATA y no avisa. Con treat-missing-data se decide si la ausencia cuenta como falla o como normalidad.

Módulo 8 · evaluación

Cuántas veces tiene que pasar para que salte

ParámetroValor
métricaCPU, Average
período60 s
umbral> 70 %
períodos evaluados3
datapoints para alarmar3
lectura

Cada minuto se calcula el promedio. La alarma salta si los últimos 3 minutos seguidos superaron el 70 %.

un pico aislado

Un solo minuto de 95 % no alcanza. Evita alarmar por picos breves, a cambio de tardar unos minutos en reaccionar.

Módulo 8 · logs

Logs: grupos, flujos y retención

grupo de logs

Agrupa los logs de una aplicación o servicio, como /lab/web. Acá se define la retención.

flujo (stream)

Los logs de una fuente concreta dentro del grupo, por ejemplo una instancia: web-1.

retención

Sin configurar, se guardan para siempre y se cobra el almacenamiento. Conviene fijar días: 14, 30, 90.

Módulo 8 · auditoría

Quién hizo qué, y desde dónde

registro de auditoría

Cada llamada a la API queda anotada

Quién (qué identidad del módulo 6), qué acción, sobre qué recurso, desde qué IP y cuándo. Responde: ¿quién borró ese volumen?

flow logs

Cada conexión de red queda anotada

Origen, destino, puerto y si el grupo de seguridad o la ACL la aceptó o la rechazó (módulo 5).

Se separan de los logs de la aplicación. Un atacante que entra a una instancia puede borrar sus logs locales. Los registros de auditoría viven fuera de ella y se protegen con permisos aparte. Conecta con la Clase 12.

Módulo 8 · buenas prácticas

Alarmar de menos y de más es un problema

fatiga de alertas

Demasiadas alarmas

Si suenan veinte por día, nadie las mira y se pierde la que importa. Una alarma debe pedir una acción humana.

alarmar por síntoma

Lo que siente el usuario

Errores y latencia primero. La CPU al 80 % no es un problema si el usuario no nota nada.

Además, monitorear cuesta: cada métrica personalizada y cada GB de logs se cobra. Una dimensión con muchos valores, como el ID de cada usuario, multiplica el costo (Clase 13).

Módulo 9 · por qué IaC

Lo que se hace a mano no se puede repetir

a mano, con la consola

Pasos que nadie recuerda

  • No hay registro de qué se hizo y en qué orden
  • Armar un segundo entorno es empezar de cero
  • Dos personas hacen lo mismo de forma distinta
  • Si se pierde la red, no se sabe cómo era
como código

Un archivo que describe todo

  • Se versiona en Git: quién cambió qué y cuándo
  • Se revisa antes de aplicarlo
  • Se repite: desarrollo, prueba y producción iguales
  • Se borra y se reconstruye con un comando

Es la forma de aplicar a la infraestructura lo que se hace con el código de una aplicación.

Módulo 9 · declarativo

Describir el resultado, no los pasos

imperativo

"Hacé esto, después esto"

Una lista de comandos: crear la VPC, crear la subred, adjuntar el gateway. Si se ejecuta dos veces, falla o duplica todo.

declarativo

"Quiero que exista esto"

Se describe el estado final. La herramienta compara con lo que hay y hace solo lo que falta.

Idempotencia. Aplicar el mismo archivo dos veces da el mismo resultado: la segunda vez no cambia nada. Es lo que permite repetir un despliegue sin miedo.

Módulo 9 · una plantilla

Parámetros, recursos y salidas

red.yaml (CloudFormation)
Parameters:
  Entorno: { Type: String, Default: dev }
Resources:
  Vpc:
    Type: AWS::EC2::VPC
    Properties: { CidrBlock: 10.2.0.0/16 }
  Subred:
    Type: AWS::EC2::Subnet
    Properties:
      VpcId: { Ref: Vpc }
      CidrBlock: 10.2.1.0/24
Outputs:
  VpcId: { Value: { Ref: Vpc } }
Parameters

Valores que cambian entre entornos: un nombre, un tamaño. La misma plantilla sirve para dev y producción.

Resources

Lo que debe existir. Cada recurso tiene tipo y propiedades.

Ref

La subred apunta a la VPC con Ref. La herramienta deduce el orden: crea la VPC primero.

Outputs

Datos que se informan al terminar, como un ID o una dirección.

Módulo 9 · el ciclo

Planificar, aplicar y destruir

planqué va a cambiar, sin tocar nada
applyaplicar los cambios necesarios
cambioeditar el archivo y volver a aplicar
destroyborrar todo lo que creó el archivo
el estado

La herramienta recuerda qué recursos creó. CloudFormation lo guarda en una pila (stack); Terraform, en un archivo de estado. Con ese registro sabe qué cambiar y qué borrar.

en un cambio, mirá el plan

Cambiar una propiedad a veces implica reemplazar el recurso: borrarlo y crearlo de nuevo. Con una base de datos, eso pierde datos.

Módulo 9 · deriva

Cuando la realidad se aparta del código

Alguien abre el puerto 22 en un grupo de seguridad desde la consola, "solo un rato". El archivo sigue diciendo que está cerrado. Esa diferencia se llama deriva (drift).

por qué es un problema

El código ya no describe lo que existe. Un despliegue posterior puede borrar el cambio sin avisar, o conservar un agujero de seguridad que nadie recuerda.

cómo se detecta

Las herramientas comparan el estado real con la plantilla y muestran las diferencias.

cómo se evita

Con una regla de equipo: la infraestructura se cambia solo editando el archivo. Los permisos del módulo 6 pueden impedir las modificaciones manuales.

Práctica 1 · Enviar y consultar métricas

PowerShell
# Preparar la terminal (si no lo hiciste ya)
$env:AWS_ENDPOINT_URL      = "http://localhost:4566"
$env:AWS_ACCESS_KEY_ID     = "test"
$env:AWS_SECRET_ACCESS_KEY = "test"
$env:AWS_DEFAULT_REGION    = "us-east-1"
mkdir modulo-monitoreo; cd modulo-monitoreo

# Cinco mediciones de latencia del servicio web
120,95,110,4800,105 | ForEach-Object {
  aws cloudwatch put-metric-data --namespace Lab/App --metric-name Latencia `
    --unit Milliseconds --value $_ --dimensions Servicio=web
}

# Consultar: promedio y máximo del último rato
$ini = (Get-Date).ToUniversalTime().AddMinutes(-30).ToString("yyyy-MM-ddTHH:mm:ssZ")
$fin = (Get-Date).ToUniversalTime().AddMinutes(5).ToString("yyyy-MM-ddTHH:mm:ssZ")
aws cloudwatch get-metric-statistics --namespace Lab/App --metric-name Latencia `
  --dimensions Name=Servicio,Value=web --start-time $ini --end-time $fin `
  --period 3600 --statistics Average Maximum SampleCount `
  --query "Datapoints[].[Average,Maximum,SampleCount]" --output table
qué observar

Un promedio de unos 1000 ms y un máximo de 4800. Una sola medición alta arrastra el promedio y deja claro por qué miramos también el máximo y los percentiles.

período

Todas las mediciones del rango caen en un solo tramo de 3600 segundos, así que hay un único dato agregado.

Práctica 2 · Logs: guardar y buscar

PowerShell
# Grupo y flujo, con retención de 14 días
aws logs create-log-group --log-group-name /lab/web
aws logs put-retention-policy --log-group-name /lab/web --retention-in-days 14
aws logs create-log-stream --log-group-name /lab/web --log-stream-name web-1

# Tres renglones de log
$ts = [DateTimeOffset]::UtcNow.ToUnixTimeMilliseconds()
aws logs put-log-events --log-group-name /lab/web --log-stream-name web-1 `
  --log-events "timestamp=$ts,message=INFO pedido GET /inicio 200" `
               "timestamp=$($ts+1),message=ERROR no se pudo conectar a la base" `
               "timestamp=$($ts+2),message=INFO pedido GET /salud 200"

# Leer todo el grupo
aws logs filter-log-events --log-group-name /lab/web `
  --query "events[].message"
timestamp

En milisegundos desde 1970. Las tres líneas llevan el mismo valor más 0, 1 y 2 para conservar el orden.

retención

Sin put-retention-policy los logs se guardarían indefinidamente. Es un gasto invisible que crece solo.

Práctica 3 · Alarmas por API

PowerShell
# Un tema de notificaciones
$TOPIC = aws sns create-topic --name avisos-lab `
  --query TopicArn --output text

# Alarma de CPU: promedio > 70 % tres minutos seguidos
aws cloudwatch put-metric-alarm --alarm-name cpu-alta `
  --namespace Lab/App --metric-name CPU --dimensions Name=Servicio,Value=web `
  --statistic Average --period 60 --evaluation-periods 3 --datapoints-to-alarm 3 `
  --threshold 70 --comparison-operator GreaterThanThreshold `
  --treat-missing-data breaching --alarm-actions $TOPIC

# Su estado actual
aws cloudwatch describe-alarms --alarm-names cpu-alta `
  --query "MetricAlarms[].[AlarmName,StateValue,Threshold]" --output table

# Forzar el estado para ver qué muestra
aws cloudwatch set-alarm-state --alarm-name cpu-alta --state-value ALARM `
  --state-reason "prueba de laboratorio"
aws cloudwatch describe-alarm-history --alarm-name cpu-alta --max-items 3
--treat-missing-data breaching

Si la instancia deja de enviar datos, la ausencia cuenta como falla. Es la solución al problema de la diapositiva de alarmas.

la acción

El tema SNS recibe el aviso. En una nube real, desde ahí se envía un correo o un mensaje al equipo.

DocenteProbar si Floci acepta sns, set-alarm-state y describe-alarm-history. Para vincular con el módulo 7, el valor de --alarm-actions puede ser el ARN de la política sube-1.

Práctica 4 · Una alarma que evalúa de verdad

PowerShell
# Una instancia que consume medio núcleo sin parar
docker run -d --name carga --cpus 0.5 alpine sh -c "while true; do :; done"

# La alarma: umbral 40 %, 3 muestras seguidas, una cada 5 s
$umbral = 40; $seguidas = 0
1..14 | ForEach-Object {
  $cpu = [double]((docker stats carga --no-stream --format "{{.CPUPerc}}") -replace '%','')
  if ($cpu -gt $umbral) { $seguidas++ } else { $seguidas = 0 }
  $estado = if ($seguidas -ge 3) { "ALARM" } else { "OK" }
  "{0:HH:mm:ss}  cpu={1,5:N0}%  seguidas={2}  estado={3}" -f (Get-Date), $cpu, $seguidas, $estado
  Start-Sleep 5
}

# En otra terminal, a mitad de la ejecución: "se escaló" y baja la carga
docker stop carga
qué esperar

Los primeros renglones muestran OK mientras seguidas sube a 1 y 2. Al tercer renglón seguido sobre el umbral, el estado pasa a ALARM.

la recuperación

Después de docker stop carga la CPU cae, seguidas vuelve a 0 y el estado vuelve a OK.

CapturaLa salida completa del script, donde se vean el paso de OK a ALARM y la vuelta a OK.
DocenteProbar antes de clase: el porcentaje que informa docker stats depende del equipo. Si no supera el 40 %, bajar el umbral a 30.

idempotencia

deriva y reparación

Después de borrar lab-web-2 a mano, el siguiente up detecta que falta y la recrea.
