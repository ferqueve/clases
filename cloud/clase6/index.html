La pieza que hace posible todo lo anterior

Ya usamos virtualización con las manos en el laboratorio de VirtualBox. Hoy le ponemos la teoría completa: tipos, cómo se acelera por hardware, y por qué a veces conviene un contenedor en vez de una VM.

Lo que ya vimos en la práctica

Repaso rápido del laboratorio de VirtualBox

VM

Una computadora simulada por software, con su propio CPU/RAM/disco virtual, aislada del resto.

Hipervisor

El software que crea y administra VMs — vimos tipo 1 (bare-metal, como Proxmox/ESXi) vs. tipo 2 (hosted, como VirtualBox — el que usamos en el laboratorio).

QEMU + KVM

El motor que emula hardware (QEMU) y lo acelera con soporte del procesador real (KVM) — hoy vemos por qué esto importa tanto.

No todas las virtualizaciones son iguales

Tres formas de virtualizar

Virtualización completa

El hipervisor emula hardware completo. El SO invitado no sabe que está virtualizado — puede correr sin modificaciones (lo que hace VirtualBox o QEMU/KVM).

Paravirtualización

El SO invitado está al tanto de que corre virtualizado y coopera con el hipervisor mediante drivers especiales — más eficiente, pero requiere un SO modificado.

Virtualización a nivel de SO

No hay VMs completas: se aíslan procesos dentro del mismo kernel del host. Esto es, en esencia, un contenedor (Docker).

Por qué una VM no es lentísima

Virtualización asistida por hardware

Los procesadores modernos incluyen extensiones específicas para virtualización: Intel VT-x y AMD-V. Le permiten al hipervisor ejecutar instrucciones de la VM casi directamente en el CPU real, en vez de traducir cada instrucción por software.

Sin aceleración

Cada instrucción se traduce por software — mucho más lento, casi inutilizable para cargas reales.

Con aceleración (KVM)

El CPU real ejecuta directamente, con el hipervisor interviniendo solo cuando hace falta — de ahí el rendimiento casi nativo.

Justamente por esto elegimos VirtualBox (tipo 2) para el laboratorio en vez de un hipervisor bare-metal: al correr directo sobre el sistema operativo de cada notebook, no depende de virtualización anidada ni de hardware de servidor — mucho más parejo entre las máquinas de todo el grupo.
Por qué nos importa tanto

Beneficios de virtualizar

Consolidación

Varias VMs en un solo servidor físico, aprovechando hardware que antes quedaba ocioso.

Aislamiento

Si una VM se cae o es comprometida, las demás siguen funcionando sin verse afectadas.

Snapshots

Punto de restauración instantáneo antes de un cambio riesgoso — lo usamos en el laboratorio.

Portabilidad

Clonar o mover una VM es copiar un archivo, no reinstalar un sistema operativo entero.

Exportar / clonar

Mover o duplicar una VM completa entre equipos como un archivo portable — lo hicimos con VBoxManage export y clonevm.

Base de todo lo demás

Elasticidad, escalabilidad y multi-tenancy — todo lo que vimos en clases anteriores— depende de estos beneficios.

No es "uno mejor que el otro"

Cuándo usar cada uno

Conviene VM cuando...

Necesitás un sistema operativo distinto al del host, aislamiento fuerte por seguridad/compliance, o correr software legado que espera una máquina completa.

Conviene contenedor cuando...

Vas a escalar rápido, desplegar frecuentemente, o correr microservicios que comparten el mismo SO base.

En la práctica, muchas arquitecturas combinan ambos: contenedores corriendo dentro de VMs, para sumar el aislamiento fuerte de la VM con la agilidad del contenedor.
