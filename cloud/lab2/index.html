Laboratorio práctico

Réplicas, escalado y una falla provocada

Vamos a armar un cluster de Docker Swarm, desplegar un servicio con réplicas, escalarlo en caliente y después tirar abajo un nodo a propósito para ver el failover en vivo.

Docker Swarm CLI: docker service / node Failover real
Antes de empezar

Requisitos del laboratorio

3 nodos (mínimo)

Pueden ser 3 VMs (por ejemplo, sobre el Proxmox del laboratorio anterior) o 3 contenedores Docker-in-Docker.

Red entre nodos

Los 3 nodos deben poder verse entre sí por IP, con los puertos 2377, 7946 y 4789 abiertos.

Docker Engine

Instalado en los 3 nodos — Swarm es un modo nativo de Docker, no requiere instalar nada extra.

Paso 1

Inicializar el cluster (manager)

El primer nodo que inicializa el swarm se convierte automáticamente en manager: es quien va a distribuir el trabajo hacia los workers.

 en el nodo1 (manager)
docker swarm init --advertise-addr IP-DEL-NODO1

# El comando devuelve un token para sumar workers, algo como:
# docker swarm join --token SWMTKN-1-xxxx IP-DEL-NODO1:2377
Paso 2

Sumar los workers

 en el nodo2 y nodo3 (workers)
docker swarm join --token SWMTKN-1-xxxx IP-DEL-NODO1:2377
 verificar desde el manager
docker node ls
Paso 3

Desplegar un servicio con réplicas

Un service en Swarm es la unidad que gestiona réplicas de un contenedor. Le decimos cuántas copias queremos y Swarm decide en qué nodos las corre.

 ejemplo (no lo ejecuten todavía, viene como ejercicio)
docker service create --name demo --replicas 2 --publish 8080:80 nginx
Ejercicio 1

Crear el servicio "web" con 3 réplicas

Escribí el comando para crear un servicio llamado web, con imagen nginx, 3 réplicas, publicando el puerto 8080 hacia el 80 del contenedor.

Ejercicio 2

Escalar en caliente

Sin tocar el contenedor ni reiniciar nada, le pedimos a Swarm más (o menos) réplicas del mismo servicio.

Escribí el comando para escalar el servicio web a 5 réplicas.

Paso 4 · La falla provocada

Tirar abajo un nodo a propósito

Vamos a poner un worker en modo "drain" (deja de recibir trabajo) para simular una caída controlada y observar cómo Swarm redistribuye las réplicas automáticamente hacia los nodos que siguen sanos.

 desde el manager
docker node update --availability drain nodo3

# Observar cómo se reprograman las réplicas:
watch docker service ps web
Ejercicio 3

Verificar dónde quedaron las réplicas

Escribí el comando para ver en qué nodos están corriendo (o reprogramándose) las réplicas del servicio web.

Entregable del laboratorio

Checklist para aprobar

  • Cluster Swarm de 3 nodos armado y verificado con docker node ls
  • Servicio "web" desplegado con 3 réplicas iniciales
  • Servicio escalado a 5 réplicas en caliente
  • Un nodo puesto en modo drain y redistribución observada
  • Captura de docker service ps web antes y después del drain
  • Breve informe: qué pasó con las réplicas del nodo caído
